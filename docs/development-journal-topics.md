# 개발 과정에서 얻은 재사용 가능한 글감

데스크톱 애플리케이션과 연결형 백엔드를 개발하며 얻은 시행착오, 설계 판단과 기술 지식을
다른 프로젝트에도 적용할 수 있는 `주제 + 참고사항` 형태로 정리한다. 각 참고사항은 특정 제품의
개발 일지를 전제로 하지 않고, 그 자체만으로 AI가 문제의 배경과 해결 방향을 이해해 실용적인 글로
확장할 수 있도록 작성한다.

글을 만들 때에는 특정 구현을 정답처럼 소개하기보다 다음 흐름을 우선한다.

- 어떤 환경에서 문제가 발생하는가
- 처음에는 무엇을 오해하기 쉬운가
- 잘못 설계하면 어떤 위험이나 운영 비용이 생기는가
- 일반적으로 적용할 수 있는 해결 원칙과 구조는 무엇인가
- 선택지별 장단점과 도입 전 확인할 사항은 무엇인가

실제 secret, token, project 정보, 개인 데이터와 악용 가능한 운영 세부사항은 포함하지 않는다.
API 명칭, 지원 범위와 정책처럼 바뀔 수 있는 정보는 글을 작성하는 시점의 공식 문서로 다시
확인한다.

## 저장소와 인증 정보

### Secret 저장소만 믿으면 안 되는 이유: 반환 범위와 API 계약의 최소 권한 설계

**참고사항**

배포된 데스크톱 애플리케이션의 코드와 설정 파일은 사용자가 열어볼 수 있으므로 서버용 API key,
service role key와 외부 서비스의 장기 자격증명을 안전하게 숨길 수 없다. 이를 해결하기 위해
서버리스 함수나 백엔드 프록시의 Secret 저장소에 자격증명을 보관하는 경우가 많다. 그러나 Secret
저장소는 값을 서버 내부에서 보호할 뿐이다. 함수가 전체 설정을 응답하거나, 클라이언트가 임의의
URL·endpoint·query를 지정할 수 있게 하거나, 외부 API의 원본 응답을 그대로 전달하면 보호하던
권한을 다른 형태로 다시 노출하게 된다.

글에서는 `어디에 저장했는가`와 `어떤 기능까지 사용할 수 있게 했는가`를 별개의 보안 문제로
설명한다. 범용 프록시 하나를 만드는 대신 `뉴스 검색`, `상품 조회`처럼 사용자 기능 단위의 좁은
endpoint를 만들고, 서버가 호출할 외부 host와 path를 고정하며, 허용된 입력만 검증해야 한다.
응답 또한 화면에 필요한 필드만 새 객체로 구성해 provider의 내부 식별자, quota 정보와 디버그
데이터가 우연히 전달되지 않게 한다.

인증과 권한 확인, 요청 횟수 제한, timeout, 응답 크기 제한, cache, 감사 로그와 오류 형식도 API
계약의 일부다. 로그에는 secret, Authorization header와 원본 개인정보를 기록하지 않는다. 외부
서비스가 실패했을 때 다른 고권한 자격증명으로 조용히 우회하기보다 허용된 fallback만 사용하고,
권한 경계가 불명확하면 fail-closed하는 편이 안전하다. 핵심 교훈은 Secret 저장소가 최소 권한 API
설계를 대신하지 않으며, 안전성은 `저장 위치 + 호출 가능 범위 + 반환 범위 + 운영 통제`의 결합으로
만들어진다는 것이다.

### 설치형 데스크톱 OAuth에서 Client ID와 Client Secret을 이해하는 방법

**참고사항**

서버 애플리케이션은 운영자가 통제하는 환경에서 client secret을 보관할 수 있는 confidential
client다. 반면 설치형 데스크톱 애플리케이션은 실행 파일과 네트워크 요청을 사용자가 관찰할 수
있는 public client이므로, 설치 파일에 포함된 값을 진정한 비밀로 간주할 수 없다. 일부 OAuth
공급자가 설치형 앱에도 `client_secret`이라는 이름의 값을 발급하더라도, 이것만으로 복제된 앱을
신뢰하거나 사용자 토큰을 보호할 수 있다고 생각하면 안 된다. Client ID는 보통 애플리케이션을
식별하는 공개 값에 가깝다.

일반적인 설치형 앱은 시스템 브라우저에서 Authorization Code Flow를 시작하고 PKCE를 사용한다.
앱은 매 요청마다 무작위 `code_verifier`를 만들고 그 해시인 `code_challenge`를 인증 요청에 보내며,
인가 코드를 교환할 때 원래 verifier를 제시한다. 공격자가 redirect나 로그에서 인가 코드를
가로채도 verifier 없이는 토큰으로 바꾸기 어렵다. 여기에 정확한 redirect URI, loopback callback,
`state` 검증, 최소 scope, 짧은 인가 코드 유효시간과 OS 기본 브라우저 사용을 함께 적용한다.

Client 설정을 원격 DB에서 아무 클라이언트나 읽을 수 있게 제공하는 것은 PKCE와 별개의 노출
문제다. 공개되어도 되는 Client ID는 빌드 입력 또는 제한된 공개 설정으로 관리하고, 사용자별
refresh token은 OS keychain이나 적절히 보호된 사용자 저장소에 둔다. 설정 교체 시에는 기존 앱의
로그인 지속 여부, refresh token의 유효성, 새 redirect 등록, 사용자 재연결 필요성과 구버전 지원
기간을 함께 검토한다. 서버 프록시는 모든 OAuth에 무조건 필요한 것이 아니라, 서버만 수행해야
하는 고권한 작업이나 중앙 정책 집행이 필요한 경우에 선택한다는 점도 설명한다.

### Access Token과 Refresh Token으로 이해하는 OAuth 2.0 세션 수명주기

**참고사항**

Access token은 API를 호출할 때 제시하는 비교적 수명이 짧은 bearer credential이고, refresh token은
사용자가 매번 로그인하지 않아도 새 access token을 발급받게 해 주는 장기 자격증명이다. 둘을 모두
단순한 `API key`처럼 취급하면 만료 처리, 저장 위치와 연결 해제 정책을 잘못 설계하기 쉽다.

글에서는 사용자가 동의 화면에서 scope를 승인하고, 앱이 인가 코드를 토큰으로 교환하며, access
token 만료 전에 또는 401 응답 후 refresh를 시도하는 전체 흐름을 설명한다. Refresh token은 최초
동의, offline access 조건과 공급자 정책에 따라 매번 반환되지 않을 수 있으며, token rotation을
사용하는 공급자에서는 새 refresh token을 받았을 때 이전 값을 안전하게 교체해야 한다. Refresh가
거부되면 무한 재시도하지 말고 연결 만료 상태로 전환해 재인증을 요청한다.

Scope는 토큰이 행사할 수 있는 권한이므로 필요한 API 범위만 요청한다. 사용자별 토큰은 서버
공용 client 설정과 분리하고, 평문 로그·오류 응답·분석 도구에 남기지 않는다. 로그아웃 또는 연결
해제 시 로컬 값만 지우는 것과 공급자에게 token revoke를 요청하는 것의 차이도 구분한다. 여러
계정, 토큰 만료, 사용자의 권한 철회, 비밀번호 변경과 공급자 장애를 정상적인 상태 전이로 다루면
OAuth 오류를 예외적인 버그가 아니라 관리 가능한 세션 수명주기로 설계할 수 있다.

### 데스크톱 앱에 장기 API Key를 넣지 않고 단기 접근 토큰을 사용하는 구조

**참고사항**

데스크톱 앱이 사내 API나 유료 데이터 API를 직접 읽어야 할 때 서버의 장기 API key를 설치 파일에
넣는 방식은 간단하지만 안전하지 않다. 실행 파일에서 key가 추출되면 정식 앱이 허용받은 읽기
기능뿐 아니라 같은 key가 가진 관리·수집·export 권한까지 악용될 수 있고, key를 회전할 때 모든
설치본을 업데이트해야 할 수도 있다.

일반적인 대안은 token broker를 두는 것이다. 데스크톱 앱은 기존 사용자 세션, 라이선스 또는
기기 등록처럼 서버가 검증할 수 있는 자격을 broker에 제시한다. Broker는 자격과 사용 권한을
확인한 뒤 수명이 짧고 scope가 제한된 서명 토큰을 발급한다. 앱은 토큰을 디스크에 장기 보관하지
않고 메모리에서 제한적으로 재사용하며, 대상 API는 다음 항목을 모두 검증한다.

```text
Desktop application
  -> 사용자 또는 설치 자격 증명
Token broker
  -> 짧은 수명과 제한된 scope의 접근 토큰 발급
Desktop application
  -> Authorization: Bearer <short-lived token>
Protected API
  -> signature, issuer, audience, expiry, scope 검증 후 허용된 기능만 실행
```

JWT를 사용한다면 서명만 확인해서는 부족하다. `exp`·`nbf`, issuer, audience와 scope를 검증하고,
알고리즘과 key 선택 규칙을 서버가 제한해야 한다. 토큰 payload는 암호화된 비밀 공간이 아니므로
민감 정보를 넣지 않는다. Development에서 발급한 토큰이 Production에서 통과하지 않도록 환경별
issuer, audience와 signing key도 분리한다.

단기 토큰은 유출 가능성을 없애는 것이 아니라 피해 시간과 권한 범위를 줄인다. 토큰을 무제한
발급할 수 있는 signing key와 broker의 인증 우회는 개별 접근 토큰보다 더 큰 위험이므로 더 강하게
보호해야 한다. Rate limit, 발급 감사 로그, key rotation, clock skew, 재발급 폭주와 broker 장애 시
동작까지 다루면 단순한 JWT 소개가 아니라 운영 가능한 권한 위임 구조를 설명할 수 있다.

### 값의 민감도와 사용 범위를 함께 보고 저장 위치를 결정하는 법

**참고사항**

환경 설정을 준비할 때 이름에 `KEY`가 들어간 모든 값을 Secret으로 넣거나, 반대로 프런트엔드에
필요하다는 이유로 모두 공개 설정으로 처리하기 쉽다. 올바른 분류를 위해서는 두 축을 나눠야 한다.
`Repository`와 `Environment`는 값이 어느 저장소·배포 단계에서 사용되는지를 나타내고, `Secret`과
`Variable`은 노출되었을 때 보호가 필요한지를 나타낸다.

예를 들어 브라우저나 데스크톱 클라이언트에 포함되는 공개 API URL, OAuth Client ID와 제한된
publishable key는 공개되어도 권한 경계가 유지되도록 설계해야 하며 CI Variable 후보가 될 수 있다.
반면 DB password, service role key, 개인 access token, 배포용 PAT와 외부 provider의 서버 key는
노출만으로 권한을 행사할 수 있으므로 Secret이어야 한다. 사용자·업무 데이터는 CI 설정이 아니라
DB와 row-level access policy가 관리하고, 사용자별 OAuth token은 공용 빌드 Secret이 아니라 사용자
저장소가 관리한다. 개발자 PC의 비공개 빌드 입력은 Git에서 제외한 환경 파일이나 OS credential
store가 담당한다.

각 값에 대해 `누가 생성하는가`, `어디에서 소비하는가`, `클라이언트에 전달되는가`, `노출 시 가능한
행동은 무엇인가`, `회전 방법과 영향 범위는 무엇인가`, `로그에 나타날 수 있는가`를 표로 만들면
저장 위치가 명확해진다. 공개 client key는 공개되어도 안전하도록 서버의 RLS, scope, origin 정책과
rate limit이 받쳐줘야 하며, Secret 역시 과도한 권한을 갖지 않아야 한다. CI에서는 값의 원문을
출력하지 않은 채 존재와 형식만 사전검증하고, Production 값은 환경 승인과 최소 권한으로 제한한다.

### 이름이 비슷한 외부 API를 인증 계약과 사용 목적으로 구분하는 법

**참고사항**

한 회사가 `검색 API`라는 비슷한 이름으로 여러 제품을 제공하더라도 발급 체계, 인증 방식, quota와
지원 endpoint는 서로 다를 수 있다. 이를 하나의 설정이나 fallback key로 합치면 인증 오류를
반복하거나, 비용·요청 한도를 잘못 계산하거나, 한 기능의 장애가 다른 기능으로 번질 수 있다.

네이버 검색 생태계는 이 문제를 설명하기 좋은 사례다. 글을 작성하는 시점의 공식 문서를 다시
확인한다는 전제에서 다음처럼 구분할 수 있다.

- **Naver Developers Search OpenAPI**: Client ID와 Client Secret을 사용하며 Blog, News,
  Shopping 등의 콘텐츠 검색 endpoint를 제공한다.
- **Naver Search Ads API**: API Key, Secret Key와 Customer ID를 사용하고 요청 signature를
  요구하며, 광고 키워드의 검색량과 연관 후보 같은 지표를 다룬다.
- **NAVER API Hub Search API**: 위 두 제품과 별도의 발급·인증 계약을 가지며, API Hub가 제공하는
  검색 데이터 용도로 사용한다.

사용자 화면에서는 모두 `블로그 검색`이나 `키워드 분석`처럼 보일 수 있지만, 콘텐츠 문서를 찾는
검색과 키워드 수요·경쟁도를 계산하기 위한 데이터 수집은 목적이 다르다. 자격증명을 서로 fallback
하거나 이름이 비슷하다는 이유로 하나의 환경 변수에 저장하면 안 된다. API를 도입하기 전에
`공식 제품명 + 발급 콘솔 + 인증 방식 + base URL/endpoint + 사용 기능 + quota/비용 + 데이터 최신성
+ 장애 시 fallback` 표를 만들고, 코드와 Secret도 기능별 adapter 경계로 분리하는 방법을 설명한다.

## 외부 서비스와 미디어 연동

### Google Drive 공유 링크를 SNS API의 이미지 호스팅으로 사용할 수 있을까

**참고사항**

SNS 발행 API가 이미지 파일 업로드를 직접 받지 않고 공개 URL만 요구하면, 이미 Google 계정과
연결된 애플리케이션에서는 Google Drive를 임시 이미지 저장소로 활용하고 싶어진다. 이때
`브라우저에서 공유 링크가 열린다`는 사실만으로 SNS API도 이미지를 가져갈 수 있다고 판단하거나,
반대로 일반 Drive 공유 링크가 미리보기 화면을 보여준다는 이유만으로 Drive 전체를 사용할 수
없다고 단정하기 쉽다. 두 판단 모두 접근 권한과 미디어 전송 계약을 섞은 것이다.

Drive 권한은 파일 소유자와 애플리케이션만 업로드·수정·삭제할 수 있게 유지하면서, 해당 파일에
`type=anyone`, `role=reader` 권한을 추가해 익명 사용자에게 읽기만 허용할 수 있다. 애플리케이션이
직접 만든 파일만 다룬다면 전체 Drive 권한 대신 범위가 좁은 `drive.file` OAuth scope를 우선
검토한다. 다만 `webViewLink` 같은 일반 공유·미리보기 주소와 바이너리 파일의 브라우저 다운로드용
`webContentLink`는 용도가 다르다. SNS API가 요구하는 것은 로그인 화면이나 HTML 미리보기가 아니라
인증 없이 실제 이미지 바이트를 반환하는 HTTPS URL이다.

이 가설은 문서 해석만으로 확정하지 말고 최소한의 disposable PoC로 검증한다.

1. 대상 Google Cloud 프로젝트에서 Drive API가 활성화되어 있는지 확인한다.
2. 애플리케이션의 기존 OAuth 연결과 `drive.file` scope로 작은 임시 PNG 한 장을 업로드한다.
3. 그 파일에만 `anyone:reader` 권한을 적용한다.
4. Drive가 반환한 `webContentLink`를 인증 헤더와 로그인 쿠키 없이 요청한다.
5. HTTP 200, `Content-Type: image/*`, 충분한 응답 크기와 PNG/JPEG 같은 실제 파일 signature를
   함께 검사한다. 화면에 보인다는 사실이나 파일 확장자만 확인해서는 안 된다.
6. 최초 URL, redirect 유무와 최종 host를 기록하되 접근 token이나 민감한 query 값은 로그에
   남기지 않는다.
7. 성공과 실패에 관계없이 `finally` 성격의 정리 단계에서 임시 파일을 삭제한다.

실제 검증에서는 첫 요청이 HTTP 403으로 실패했다. OAuth 연결이나 scope 문제가 아니라 Google
Cloud 프로젝트에서 Drive API가 비활성화된 것이 원인이었다. API를 활성화한 뒤 같은 절차를 다시
실행하자 `anyone:reader` 적용과 익명 다운로드가 성공했고, 요청은 `drive.google.com`에서
`drive.usercontent.google.com`으로 이동한 뒤 HTTP 200, `image/png`와 유효한 PNG 바이트를 반환했다.
테스트 파일도 검증 직후 삭제되었다. 이 과정은 `Google 계정 연결 완료`와 `필요한 Google API
활성화 완료`가 서로 다른 준비 조건이라는 점도 보여준다.

그러나 이 결과가 곧 특정 SNS 발행 서비스와의 완전한 호환성을 의미하지는 않는다. 외부 서비스가
redirect를 따르는지, 최종 다운로드 주소를 안정적으로 처리하는지, 여러 이미지를 순서대로 가져가는지
실제 end-to-end 테스트가 남는다. 공급자가 `공개·직접·안정적인 URL`을 요구한다면 익명 요청뿐 아니라
redirect, content type, 파일 크기 제한, URL 수명과 예약 발행 시점까지의 가용성을 확인해야 한다.
글을 작성할 때에는 Google Drive와 연결 대상 SNS API의 최신 공식 문서를 다시 확인한다.

임시 파일의 수명주기도 핵심이다. 즉시 발행은 외부 서비스가 파일을 정상적으로 가져가고 발행 결과가
확정된 뒤 삭제할 수 있다. 예약·대기열 발행은 실제 발행 시점까지 파일을 유지해야 한다. Timeout처럼
성공 여부가 모호한 경우에는 곧바로 삭제하거나 같은 발행 요청을 반복하면 이미지 누락이나 중복
게시가 생길 수 있으므로, 결과를 재조회하고 정리 여부를 결정한다. 공개 기간에는 링크를 아는 누구나
파일을 읽을 수 있으므로 무작위 파일 ID를 접근 통제로 오해하지 않고, 최소 공개 시간·사용자 안내와
정리 실패 재시도도 함께 설계한다.

구현에서는 카드뉴스 생성과 저장소, SNS 발행을 한 덩어리로 묶지 않는다. `로컬 파일을 임시 공개
URL로 전환`, `외부 발행`, `결과 확정 후 정리`를 분리하면 Google Drive, WordPress 미디어,
Cloudflare R2나 전용 CDN을 상황에 따라 교체할 수 있다. Google Drive는 기존 사용자 계정과 좁은
권한을 재사용할 수 있다는 장점이 있지만 CDN을 목적으로 한 제품은 아니므로, 안정성·대량 처리·예약
보존이 중요해지면 객체 저장소와 비용, 개인정보, 운영 복잡도를 다시 비교한다.

## BlogGenius를 만들며 얻은 제품 개발 경험

아래 주제는 BlogGenius의 실제 개발 과정에서 문제를 발견하고 대안을 비교해 결정한 사례다. 결과가
구현·검증된 주제는 그 결과와 남은 확인 범위를 함께 적었다. 특정 라이브러리나 구현 방식을 보편적인
정답으로 단정하기보다, 당시 제품 조건과 선택 이유를 중심으로 글을 구성한다.

이 문서는 완성 원고가 아니라 충분한 맥락을 담은 글쓰기 자료다. 공개 글로 옮길 때에는 내부 화면·모듈·저장
모델의 이름과 세부 구조를 그대로 공개하지 않고, 사용자가 겪는 문제와 일반화할 수 있는 설계 원칙으로
풀어쓴다. 계정·키·token·개인정보·사설 endpoint 및 공개 전 운영 정보는 글감이나 글에 넣지 않는다.
완료된 결과와 제안/보류 중인 선택을 구분하고, 외부 서비스의 현재 정책은 발행 전에 최신 공식 자료로
다시 확인한다.

### 블록 편집기 라이브러리를 고르는 일은 편집기를 고르는 일과 달랐다

**참고사항**

BlogGenius는 기존에 바닐라 JavaScript 중심으로 구성되어 있었다. 원고를 블록 단위로 편집하고
Markdown으로도 다룰 수 있는 편집기를 찾으면서 Tiptap과 Milkdown의 Crepe를 검토했다. 이름이나
기능표만 비교하지 않고 같은 한국어 샘플 원고, 유사한 서식 범위와 실제 조작 가능한 prototype으로
비교했다. 문서의 Markdown 왕복, 문장 선택 후 서식 적용, 한글 입력, 키보드 동작, 이미지 블록 표현,
스타일 적용성과 제품 번들 영향이 비교 항목이었다.

Crepe는 비교 당시 바로 사용할 수 있는 완성도 높은 기본 편집 UI를 제공했지만, 기본 화면은 현재
제품이 제공하려는 단순한 글쓰기 범위보다 많은 서식과 블록을 한꺼번에 드러냈다. 설정으로 기능을
줄일 수는 있었으나 BlogGenius 스타일에 맞춘 화면과 선택지를 조정하는 비용도 함께 고려해야 했다.
Tiptap은 편집 엔진을 바탕으로 필요한 조작 UI를 직접 구성할 수 있었고, 실제 prototype에서 간결한
도구막대가 제품의 방향과 더 잘 맞았다. 그래서 Tiptap을 우선 후보로 선택했다. 이는 모든 제품에
Tiptap이 더 낫다는 결론이 아니라, 편집기 기능의 폭보다 제품이 통제할 수 있는 UX가 중요했던 당시의
선택이다.

Toast UI Editor는 Markdown/WYSIWYG 전환 경험을 참고했지만, 저장소의 유지보수 상태를 우려해
라이브러리 의존성으로 채택하지 않았다. Tiptap의 공식 UI 구성요소도 검토했으나 React 기반이라
UI만을 위해 앱에 React를 도입하는 것은 피했다. 후보들을 함께 빌드한 prototype 번들은 제품의
실제 번들 크기와 같지 않으므로, 최종 채택 판단과 제품 빌드 영향 분석을 분리했다.

**결과와 검증**: Tiptap을 vanilla JavaScript에서 연결하고 BlogGenius가 정한 최소 도구막대를 직접
구성하는 방향을 선택했다. 이후 paste·folder 입력이 공통 원고 작업공간을 사용하도록 이어졌고,
Tiptap은 앱이 소유한 원고 문서 모델의 편집기 adapter로 다뤘다. Prototype은 별도 개발 경로에 두어
비교 단계에서 production 글쓰기나 발행 동작을 바꾸지 않았다. 비교 기록은
`docs/plans/archive/2026-09-28-manuscript-editor-prototype-01-development.md`에 있다.

### Headless 편집기는 저절로 좋은 글쓰기 화면이 되지 않는다

**참고사항**

Headless editor가 제공하는 것은 주로 문서 상태와 편집 동작을 제어하는 기반이지, 사용자가 바로
쓸 수 있는 완성 UI 전체가 아니다. Tiptap을 선택한 뒤 실제 제품 작업은 제목과 본문 캔버스, 블록
삽입 affordance, 도구막대 위치, 선택·활성 상태, 키보드 접근성, 반응형 배치까지 직접 정하는 일이었다.
도구막대를 편집기 엔진에 맡기면 빠르지만 앱의 기존 디자인과 맞지 않거나 불필요한 기능을 노출할 수
있고, 모두 직접 만들면 디자인과 동작 계약을 일관되게 책임져야 한다.

제품에서 필요한 기본 서식은 문단, 소제목, 굵게·기울임, 목록, 인용, 실행 취소·다시 실행 등으로
좁혔다. 링크나 이미지처럼 본문 내용을 바꾸는 동작은 원고 모델과 발행 결과까지 함께 생각해야 하므로
그냥 toolbar command를 추가하는 것으로 끝나지 않는다. 툴바의 '사용 가능한 기능'은 출판 결과에서도
의미가 유지되어야 한다. 지원이 불확실한 표·임베드·복잡한 서식 등을 무심코 노출하면 편집기에서는
보이지만 발행 단계에서 사라지는 차이가 생길 수 있다.

**결과와 검증**: BlogGenius 스타일의 custom toolbar를 vanilla JavaScript로 구성하고, block,
Markdown, 보기 모드를 서로 연결했다. 이미지는 별도 custom node UI로 다루되 AI 생성과 파일 관리는
편집기 안에 비즈니스 로직으로 넣지 않고 공통 Draft/image service에 위임하는 경계를 택했다.
Markdown import/export, 모드 전환, 이미지 블록과 사용자 입력을 prototype 및 browser smoke에서
검증하며 toolbar와 document model을 분리해 발전시켰다.

### Markdown 편집 모드를 넣고 싶지만, Markdown 변환을 믿어도 될까

**참고사항**

블록 편집과 Markdown 원문 편집을 함께 제공하면 사용자는 익숙한 방식으로 원고를 다룰 수 있다.
하지만 두 표현이 같은 내용을 정확히 왕복한다는 보장은 별개다. 편집기 문서에는 일반 Markdown으로
표현하기 어려운 이미지 지시문과 내부 asset 연결이 있고, 확장 문법을 파서가 놓치거나 serializer가
다르게 출력하면 저장하지 않은 편집 내용이 조용히 달라질 수 있다. Markdown extension이 beta였다는
점도 완전한 왕복을 당연시하지 않게 한 요인이었다.

처음 검토한 선택지는 라이브러리 JSON을 직접 저장하기, Markdown을 원본으로 두기, 앱 고유 문서
모델을 두기 등이었다. 편집기 내부 JSON에 영속성을 묶으면 라이브러리 교체가 어려워지고, Markdown만
정본으로 삼으면 이미지 asset identity와 revision을 표현하기 까다롭다. 그래서 앱 소유의 canonical
문서 계약을 두고 편집기와 Markdown을 그 문서에 대한 서로 다른 편집 표면/adapter로 취급했다.

**결과와 검증**: block → Markdown → block 변환을 기능 계약으로 테스트하고, 이미지 지시문에는 앱의
공통 원고 규칙을 적용했다. 붙여넣기 경로에서는 번호 없는 이미지 marker도 다룰 수 있게 하고,
폴더 import에서는 파일명을 자동 대응하기 위해 순번이 필요하다는 차이를 유지했다. 모든 임의 Markdown의
무손실 왕복을 보장한다고 주장하지 않고, 실제 지원 구문을 fixture와 사용자 원고로 확인하는 방향으로
범위를 한정했다. 미지원 구문을 조용히 삭제하지 않는 것이 설계 원칙이다.

### 이미지 순번이 바뀌어도 원고의 이미지를 잃지 않으려면

**참고사항**

초기 폴더 원고의 `IMAGE_N` 표시는 Markdown 순서와 폴더의 이미지 파일을 연결하는 데 유용하다.
그러나 편집 중 블록을 삽입·이동·삭제하면 순번은 달라질 수 있다. 순번 자체를 이미지의 영구 identity로
사용하면 파일이 잘못된 문단에 붙거나 기존 이미지가 다른 슬롯으로 이동할 위험이 생긴다.

해결을 위해 import 단계에서 원본 폴더를 읽기 전용 입력으로 취급하고, 앱 소유 Draft 작업본으로
가져왔다. import 시점의 순번은 기존 이미지를 처음 찾는 데만 사용한 다음 안정적인 block ID와 별도
asset ID를 부여했다. 편집 이후에는 문서 순서가 아니라 이 ID 연결로 이미지와 prompt를 보존한다.
폴더 원본을 직접 수정하지 않고, Draft의 revision을 이용해 동시 변경과 낡은 응답을 감지한다.

**결과와 검증**: 폴더에서 이미지가 일부 누락된 원고, zero-based `IMAGE_0`, 이미지 이동·교체·제외·복원,
실패 후 마지막 정상 상태 보존을 단위 및 browser flow에서 검증했다. 미사용 asset을 정리할 때도
앱이 소유한 파일과 사용자가 가져온 원본을 구분했다. 폴더 입력과 붙여넣기 입력이 달라도 같은 Draft/
이미지 작업공간을 재사용하되, source별 importer의 책임은 분리했다.

### 편집기 안에서 이미지를 만들되, 발행 중에 몰래 생성하지 않기

**참고사항**

원고에 이미지 생성 지시가 있다고 해서 발행 버튼을 누르는 순간 AI 생성이 암묵적으로 시작되면 안 된다.
사용자는 비용이 들거나 시간이 걸리는 작업을 명시적으로 통제할 수 있어야 하고, 어느 이미지가 준비됐는지
미리 확인할 수 있어야 한다. 또한 이미지 관리 UI를 원고 본문과 완전히 분리하면 실제 삽입 위치를
찾기 어렵고, 본문 안에서만 처리하면 카드뉴스 등 기존 이미지 조작과 시각·동작이 달라질 수 있다.

공통 이미지 블록에 prompt, 이미지 asset, 진행 상태와 사용자 선택 상태를 연결하고 이미지 생성·선택·교체
동작은 공유 서비스로 위임했다. 생성 전 prompt 저장이 먼저 완료되게 하고, 같은 슬롯에서 중복 요청을
막으며, 중지 확인·실패·재시도 상태를 분명히 했다. 생성 실패 때 이전 이미지나 마지막으로 유효했던
결과를 무조건 지우지 않는 것도 중요했다. 기존 하단 이미지 관리 영역은 inline 작업공간이 안정화되는
동안 남겨 두어 한 번에 검증 범위를 넓히지 않았다.

**결과와 검증**: 이미지 생성/선택과 발행 준비를 분리했다. 이미지가 비어 있는 경우 사용자가 슬롯을
명시적으로 제외하면 발행 가능한 상태가 될 수 있으며, 미완성 이미지를 몰래 생성하거나 발행하지 않는다.
상태 문구의 위치 고정, 중복 placeholder 억제, 취소/계속 동작과 inline 및 하단 영역의 상태 일치도
여러 차례 실제 화면 피드백과 browser smoke를 거쳐 다듬었다.

### 이미지가 빠졌을 때 자동 발행과 임시 저장 사이에서 무엇을 선택할까

**참고사항**

원고의 이미지 슬롯이 비어 있으면 발행 전에 자동 생성하는 것이 친절해 보일 수 있지만, AI 호출 비용과
대기 시간을 사용자가 예상하지 못한 채 부담할 수 있다. 반대로 모든 미완성 슬롯을 이유로 발행 자체를
막으면 사용자가 의도적으로 이미지를 생략하려는 경우까지 방해한다. ‘이미지 생성 비활성화’와 ‘발행 대상
이미지 누락’도 같은 상태가 아니다. 생성 기능이 꺼져 있다고 해서 이미지 없는 원고를 반드시 임시 저장으로
바꿔야 하는 것은 아니며, 사용자가 명시적으로 제외한 이미지는 미완성으로 세지 않아야 한다.

설계는 먼저 각 슬롯을 준비됨, 누락, 제외됨 등 실제 발행 의미가 있는 상태로 구분한다. 그다음 발행할
이미지가 누락된 경우에만 결과가 임시 저장이 될 수 있음을 실행 전에 알리고, 발행 옵션과 주 버튼의
라벨을 같은 상태로 맞춘다. 사용자가 누락 이미지를 채우거나 해당 슬롯을 명시적으로 제외해 문제를
해결한 뒤에도 이전 발행 방식으로 자동 복귀시키지 않고, 즉시 발행/예약 발행 선택은 사용자가 다시
확인하도록 한다. 상태가 비동기로 바뀔 때 이전 선택을 몰래 되살리는 일을 막기 위해서다.

**결과와 검증**: Blog Beta에서는 공통 Draft의 이미지 슬롯 상태를 기준으로 preview와 발행 snapshot을
맞추고, unresolved 이미지가 있을 때만 임시 저장 결과를 안내하도록 했다. `이미지 생성 비활성화`,
`이미지 슬롯 제외`, `실제 이미지 업로드 실패`를 서로 다른 조건으로 테스트했다. 자동 이미지 생성은
발행 작업과 분리해 명시적으로 시작하게 하고, 안전한 자동 임시 저장이 선택되더라도 완료 화면과
알림에서 실제 provider 결과와 다른 성공 문구를 쓰지 않도록 했다.

### 같은 원고라도 네이버와 워드프레스에 같은 형식으로 보내면 안 됐다

**참고사항**

블록 편집기 도입 후 연관글이 `[제목](URL)` Markdown 링크로 원고에 저장됐다. 워드프레스는 링크
표현을 정상적으로 처리했지만 네이버 자동화 경로에서는 Markdown 문법이 문자로 입력될 수 있었다.
모든 URL을 발행 직전에 바꾸자는 접근은 사용자가 직접 쓴 본문 링크까지 건드릴 위험이 있고,
canonical 원고 자체를 바꾸면 블록/Markdown/보기와 타 플랫폼 결과에 영향을 준다.

우리는 원고의 `함께 보면 좋은 글` 섹션에서 생성한 연관글 항목만 대상으로 삼았다. 네이버 발행 직전
발행용 복사본에서 해당 bullet 링크를 URL 단독 줄로 바꾸고, 기존 자동화가 URL을 링크 카드로 바꾸는
동작을 재사용했다. 워드프레스 경로와 저장된 원고에는 변환을 적용하지 않는다. 즉, 공통 원고 형식과
플랫폼별 발행 표현을 분리했다.

**결과와 검증**: 범위가 지정된 순수 변환 함수와 테스트를 추가했다. 연관글 섹션 밖 링크와 일반 문장은
그대로 유지되는지, 원고 재열기와 워드프레스 출력이 달라지지 않는지를 확인 대상으로 삼았다.
네이버 실발행에서 링크 카드가 만들어지는 hands-on 확인은 자동 테스트와 별도로 남겨뒀다. 이 사례는
사용자에게 보이는 편집기 형식을 통일하면서도 각 플랫폼의 입력 제약은 adapter에서 흡수하는 방법을
보여준다.

### 브라우저 기반 OAuth가 Electron 내장 창에서 막힌 이유

**참고사항**

Google Spreadsheet 연결을 단순화하면서 인증과 파일 선택을 하나의 사용자 흐름으로 묶었다. 처음에는
앱 내부 브라우저에서 인증하면 자연스러울 것으로 생각하기 쉽지만, Google은 Electron의 내장 브라우저를
지원하지 않는 브라우저로 판단해 로그인을 차단할 수 있다. 이때 OAuth scope나 계정 연결 자체를 먼저
의심하면 원인과 해결책이 엇갈린다.

**결과와 검증**: 인증은 OS 기본 브라우저에서 진행하고, 앱은 loopback callback과 flow 상태 조회로
완료 결과를 받도록 변경했다. 사용자가 인증 창을 닫거나 취소하는 경우 대기 중인 앱 UI가 계속 잠긴 채
남지 않도록 `인증 취소` 동작도 제공했다. 앱은 Google Picker 같은 내부 구현명을 UI 카피에 노출하지
않고, 기존 파일 선택이라는 사용자 목적을 표현한다. 시스템 기본 브라우저 선택은 인증 제공자의 보안
정책과 데스크톱 앱의 완료 UX를 함께 고려한 결과다.

### 최소 권한 OAuth가 기존 사용자의 파일 연결에는 어떤 의미인가

**참고사항**

`drive.file`은 앱이 만든 파일만 다루는 권한이라고 오해하기 쉽지만, 사용자가 파일 선택 UI를 통해
앱에 명시적으로 제공한 기존 파일에도 적용될 수 있다. 반대로 사용자가 자기 계정으로 소유한 파일이라도
앱이 그 파일을 알거나 접근할 권한을 자동으로 얻는 것은 아니다. 계정 인증, API 활성화, 파일별 앱
접근 승인은 서로 다른 전제다.

실험에서는 `drive.file`만으로 앱 생성 파일의 읽기/쓰기가 되는지와 기존 사용자 파일을 선택한 뒤
접근할 수 있는지를 각각 테스트했다. Google Sheets scope를 무조건 추가하는 대신, Drive 기반 파일
선택과 앱이 접근하도록 승인된 파일을 이용할 수 있는지 검증했다. 사용자가 만든 파일을 앱이 몰래
검색하거나, 사용자의 동의 없이 새 파일을 만드는 흐름은 피했다.

**결과와 검증**: 별도의 테스트 앱에서 파일을 만들고 선택해 읽기·쓰기 동작을 실험한 뒤 제품 설정의
새 파일 생성/기존 파일 선택 흐름으로 옮겼다. 기존 사용자에게는 같은 파일을 한 번 다시 선택하도록
안내했다. 새 파일 선택이 성공하기 전에는 기존 URL 연결을 삭제하거나 덮어쓰지 않고, 동일 파일 선택
후에 전환 완료를 기억해 반복 안내하지 않도록 했다. Scope와 Picker API 요구사항은 변할 수 있으므로
글 발행 시점의 Google 공식 문서와 실제 동의 화면으로 다시 확인한다.

### 상태 표시를 잘못하면 성공한 기능도 미완료처럼 보인다

**참고사항**

Spreadsheet 연결 UI에서는 파일 URL이 있다는 사실, 새 권한 방식으로 파일을 선택한 사실, 최근 접근
검증 결과가 각각 다른 상태다. 단순히 URL 존재 여부만으로 '연결됨'을 표시하면 새 권한 방식으로
전환되지 않은 사용자를 완료로 오해시킬 수 있다. 반대로 전환이 끝난 다음에도 Dashboard에서 계속
경고하거나 카드에 '연결됨'을 과하게 표시하면 이미 끝난 일을 반복해서 요구하는 느낌을 준다.

**결과와 검증**: 미전환 상태에서만 `전환 필요` 배지와 강조 테두리를 보이고, 기존 파일명을 확인한 뒤
전환을 시작할 수 있게 했다. 전환이 완료되면 다른 준비 카드처럼 일반 번호와 기본 스타일로 돌아간다.
설정 화면은 구체적인 안내와 동작을 맡고 Dashboard는 완료 여부를 요약한다. 사용자의 반복적인 시각
피드백에서 '연결된 Spreadsheet'라는 문구가 아직 전환할 파일 앞에 놓이면 이미 연결 완료로 오해될 수
있다는 점을 발견해, 상태 정보와 대상 파일 표시도 나눠 개선했다.

### macOS 설정 단축키를 두 번 눌렀을 때 앱이 종료되는 문제

**참고사항**

macOS에서 `Command + ,`는 설정으로 이동하는 익숙한 단축키다. 한 번 눌렀을 때 설정으로 잘 이동한다고
해서 같은 키를 한 번 더 누르는 상황도 안전하다고 볼 수 없다. 첫 동작이 창이나 화면 상태를 바꾸는
동안 두 번째 이벤트가 도착하거나, 이미 처리된 Promise rejection이 renderer 시작 오류로 전파될 수
있다. 배포 앱에서 재현된 시작 오류 화면은 사용자에게는 원인을 알려주지 못하는 내부 진단 문구를
그대로 노출하고 있었다.

**결과와 검증**: 반복 실행 시 예외가 앱 전체 종료로 번지지 않도록 macOS 설정 단축키 경로의 오류
경계를 보완했다. `Command + ,`를 반복해도 이미 열려 있는 설정 화면의 상태를 안정적으로 유지해야
한다는 동작 계약을 테스트에 추가했다. 실제 패키징된 앱의 hands-on 확인은 다음 dev 배포에서 수행할
계획으로 남겼다. 자동화된 renderer 계약 통과와 실제 macOS 패키지의 검증을 구분해 기록할 수 있는
사례다.

### AI 작업의 ‘취소’ 버튼은 화면만 멈추는 버튼이 아니었다

**참고사항**

AI 원고나 이미지 생성을 오래 기다리면 사용자는 취소할 수 있기를 기대한다. 버튼만 비활성화하거나
진행 표시를 감추는 것은 실제 provider 요청이 계속 실행되는 경우 취소가 아니다. 생성 단계, 전송 계층,
서버 작업, 재시도와 UI 상태가 각각 어떤 취소 계약을 갖는지 확인해야 한다. 특히 사용자가 취소한 뒤에도
늦게 도착한 응답이 화면의 새 결과를 덮어쓰지 않도록 작업 ID나 최신 실행 확인도 필요하다.

**결과와 검증**: Blog Beta 원고와 이미지 생성 흐름에 작업 수명주기와 취소 전달을 확장하고, 사용자가
중지를 누르면 확인 단계와 실제 중단 완료 상태를 구별하도록 했다. 마지막 유효 결과를 새 요청 실패로
지우지 않는 원칙도 적용했다. 부분 진행 결과, 중복 실행 방지, 중지 확인, 취소 후 늦은 응답 방지와
provider별 실제 취소 가능 범위를 테스트·사용자 확인으로 나눠 검증했다. 사용자가 본문이나 이미지를
직접 생성하는 기능에서는 “중지”라는 라벨이 실제 작업 수명주기까지 관통해야 한다는 교훈이다.

### UI 피드백은 한 번의 수정으로 끝나지 않는다 — 눈에 보이는 상태를 함께 설계하기

**참고사항**

Dashboard 연결 상태와 Google 설정 카드처럼 작아 보이는 UI도 색, 뱃지, 설명문이 서로 모순되면 기능
상태를 잘못 전달한다. 낮은 채도의 작은 점은 색상 구분이 어려울 수 있고, 상태를 설명하려고 문장을
카드 안에 길게 넣으면 정상 상태에서도 주변 요소와 밀도가 달라진다. 사용자가 반복적으로 “이건 완료된
것 아닌가?”라고 묻는 것은 카피 문제가 아니라 상태 모델과 시각 위계가 맞지 않을 수 있다는 신호다.

**결과와 검증**: 연결이 필요한 경우에만 경고를 강조하고, 완료 시에는 인접 카드의 기본 디자인과
일관되게 했다. Dashboard의 주요 행동은 카드 문맥에 맞춰 우측 하단에 놓고, 상세 설명은 설정으로
보냈다. 연결 상태 점의 크기·채도, WordPress와 Naver 아이콘의 실제 시각 크기, tooltip에 내부 파일
경로나 JSON 파싱 세부내용이 노출되지 않는지 등도 실제 화면 피드백을 따라 조정했다. 이 항목은 미세한
스타일 변경 모음이라기보다 “상태 모델 → 상태 카피 → 시각 위계 → 사용자 오해 검증”이 한 사이클임을
보여준다.

### 앱이 ‘떴다’와 ‘사용할 준비가 됐다’는 다른 상태였다

**참고사항**

Windows 설치형 앱에서 사용자는 시작 아이콘을 눌렀는데 화면이 나타나지 않거나, 시작 오류 창만
보는 문제를 겪었다. 기존에는 창이 열렸거나 페이지 이동이 끝났다는 신호만으로 시작을 성공 처리할 수
있었다. 그러나 창의 틀이 보인다는 것과 실제 화면이 핵심 초기화를 마치고 반응할 수 있다는 것은 다르다.
반대로 분석·추천·알림처럼 부가 기능의 외부 연결이 실패했다고 첫 화면까지 늦추거나 막는 것도 좋은
시작 경험이 아니다.

**결과와 검증**: 성공 신호를 핵심 화면의 준비 완료로 다시 정의하고, 처음 쓸 수 있는 화면을 먼저 띄운
뒤 부가 기능을 별도로 시작하도록 했다. 시작 오류는 제한된 진단 증거로 남기되 사용자 설정값과 자격
정보를 수집하지 않도록 경계를 뒀다. 정상 모드와 안전 모드, 실제 Electron 시작, renderer 오류,
포트 충돌에서의 복구를 따로 검사했다. 특히 보안상 위험한 sandbox 비활성화나 GPU 비활성화를 모든
사용자에게 기본 적용하는 대신, 안전 모드와 진단 조건에 한정했다. Windows 패키지용 검증은 macOS
개발환경의 성공만으로 대체할 수 없다는 점도 배울 수 있다.

### 대기열에 글을 넣는 순간 AI를 돌려야 할까 — 자동화의 경계를 사용자에게 돌려주기

**참고사항**

연속 발행 기능을 만들 때는 글감 등록, 원고 생성, 발행 순서와 게시 시간 예약이 한꺼번에 섞이기
쉽다. ‘대기열에 추가’ 직후 백그라운드에서 AI 원고를 만들면 편할 수 있지만, 아직 다듬지 않은 주제로
비용과 결과물이 만들어지고 사용자가 무엇이 시작됐는지 놓칠 수 있다. 여러 화면이나 별도 저장소가
같은 글 상태를 소유하면 중복 항목, 순서 불일치와 수정 후 재시도 문제도 생긴다.

**결과와 검증**: 글감 등록과 AI 실행을 분리하고, 대기열은 기존 사용자 관리 문서의 상태를 기준으로
보여주기로 했다. 한 번에 한 건씩 실행하는 흐름을 먼저 확인한 뒤 단일 기기의 자동 실행을 더했다.
각 글감은 발행 대상과 카테고리, 공개/임시 저장/예약 같은 실행 계획을 소유하고, 자동 실행 설정은
시간대와 간격처럼 전체 실행 정책만 소유하게 했다. 여러 기기에서 동시에 예약을 가져가는 claim/lease는
복잡도와 사용 가능성을 비교한 뒤 도입하지 않았다. 사용자 중심 품질을 해칠 수 있었던 완전 자동 트렌드
글감 승격도 시험 후 폐기하고, 검색·선택은 돕되 대기열 추가와 발행은 사용자가 결정하도록 되돌렸다.

**글의 핵심 질문**: 자동화는 사람의 결정을 없애는 데서 시작하는가, 아니면 반복 작업을 줄이면서도
중요한 결정을 사람에게 남기는 데서 시작하는가? 등록만으로 실행되지 않는다는 점, 실패해도 글감이
유실되지 않도록 먼저 기록하는 점, 자동화는 사용자 통제와 함께 설계해야 한다는 결론을 사례로 쓴다.

### 예약 발행에서 ‘예약’은 앱이 기다리는 것과 다를 수 있다

**참고사항**

연속 발행 프로그램이 지정된 시간까지 계속 켜져 있어야 한다고 생각하기 쉽지만, 실제로는 플랫폼에
원고를 미리 올리고 미래 공개 시간을 예약해 두는 방식이 가능하다. 대기열이 예약 시각까지 보관하는
일과, 게시 플랫폼에 예약 게시를 요청하는 일은 다른 책임이다. 앱이 꺼지거나 네트워크가 끊겼을 때도
예약이 유효한지, 즉시 공개와 임시 저장을 어떻게 구분할지를 플랫폼별로 알아야 한다.

**결과와 검증**: 예약 공개 시각을 글감별 계획으로 두고, 연속 처리기는 정해진 시간대에 한 건씩
처리하도록 분리했다. 즉 자동 실행 간격을 기다리는 Queue와 게시물의 미래 공개 시점을 혼동하지 않는
모델을 택했다. 플랫폼이 실제 예약 등록을 지원하지 않거나 등록 실패가 모호한 경우를 성공으로 가장하지
않고, 대상 플랫폼이 반환한 실제 결과를 Dashboard와 사용자 알림에 반영하는 것을 검증 대상으로 삼았다.

### AI 이미지 생성 중 ‘취소’를 눌러도 외부 작업은 계속될 수 있다

**참고사항**

이미지 생성 API가 비동기 작업을 접수한 뒤 결과를 몇 번에 걸쳐 조회하는 형태라면, 사용자가 앱에서
취소를 눌러도 이미 제공자에게 접수된 작업과 비용이 실제로 중단된다는 보장은 없다. 브라우저에서
요청을 중단하거나 화면을 닫는 일, 앱 내부 작업을 취소 처리하는 일, 외부 제공자의 연산을 취소하는
일은 각각 다르다. 이 차이를 숨기면 사용자는 취소하면 과금도 즉시 멈춘다고 오해할 수 있다.

**결과와 검증**: 지원되는 요청·재시도 대기·이미지 다운로드는 취소 신호를 가능한 경계까지 전달하고,
외부에서 이미 처리 중인 작업은 취소의 한계를 짧게 안내했다. 취소 요청을 받았다는 즉시 새 작업을
허용하지 않고 실제 종료 상태를 확인한 뒤에만 다시 실행하도록 했다. 늦게 도착한 이전 결과가 새 원고를
덮어쓰지 않게 하고, 실패나 취소에도 이전에 유효했던 원고와 미리보기를 보존했다. 이 경험은 UI 버튼
문구만으로 완료됐다고 말하지 말고, 원격 시스템이 실제 보장하는 취소 범위를 먼저 확인해야 한다는
사례다.

### 사용자가 고른 AI 모델이 갑자기 쓸 수 없게 되어도 몰래 바꾸면 안 된다

**참고사항**

모델 이름, 접근 권한, 공급자 연결 상태는 바뀔 수 있다. 사용자가 특정 모델을 골랐는데 다음 실행에서
그 모델이 비활성화되거나 연결 확인이 오래되었다면, 가장 쉬운 구현은 다른 모델로 조용히 바꾸는
것이다. 하지만 모델별 비용·속도·문체·이미지 품질이 다를 수 있어, 사용자는 자신이 승인하지 않은
결과와 비용을 받을 수 있다.

**결과와 검증**: 설정한 provider/model 선택을 명시적으로 보존하고, 사용할 수 없는 이유를 보여준 뒤
사용자가 해결하거나 다른 모델을 선택하게 했다. 페이지에서만 쓰는 override는 전역 설정을 바꾸지 않고
다음 실행부터 적용되도록 했다. 새 결과가 실패하면 이전 유효 결과를 유지하고, 모델 카탈로그 변경과
사용자 선호 저장을 구분했다. 카드뉴스 작성 중에는 전역 설정으로 이동하지 않고 작업 화면 안에서
모델을 바꿀 수 있게 하되, 자격증명과 연결 확인은 별도 설정 책임으로 남겼다.

### 여러 시각 스타일을 지원하면 하드코딩된 가정이 드러난다

**참고사항**

하나의 색상 팔레트만 있는 동안에는 CSS에 직접 입력한 색과 간격이 문제처럼 보이지 않을 수 있다.
두 번째 스타일이나 고대비 테마를 추가하면 버튼·상태·포커스·모달·hover가 특정 팔레트와 구조를
가정했다는 사실이 드러난다. 반대로 모든 화면을 한 번에 공통 규칙으로 바꾸면 기존 화면의 여백과
선택 상태가 중복 적용돼 회귀 범위가 커진다.

**결과와 검증**: 색상, 타이포그래피, 모션, 밀도를 의미 기반 토큰으로 옮기되, 버튼의 중요도·키보드
순서·화면 동작은 스타일이 바꿀 수 없는 공통 계약으로 분리했다. 스타일을 등록하고 필요한 화면에서
점진적으로 확인했으며, 동일하게 보이게 할 수 없는 예외는 이유를 남겨 두었다. 실제로 시각 스타일을
늘리면서 원시 색상과 component 간 결합을 찾아냈고, 계약 테스트로 미처리 화면이 조용히 누락되지
않게 했다. 스타일 하나를 더 추가하는 일은 단순한 색상 교체가 아니라 공통 설계의 가정을 검증하는
테스트가 될 수 있다.

### UI 테스트의 실패와 제품의 실패는 같은 말이 아니다

**참고사항**

자동 브라우저 테스트가 실패하면 앱 기능이 깨졌다고 단정하기 쉽지만, 실패 지점은 앱 코드, fixture,
테스트가 클릭을 흉내 내는 방식, 실행 순서와 과부하 중 어느 쪽일 수도 있다. 반대로 “테스트가 flaky했다”는
말로 실제 회귀를 덮어서도 안 된다. 무엇을 사용자가 했고 어떤 화면 상태가 기대됐는지 시나리오 단위로
재현해야 수정 범위를 좁힐 수 있다.

**결과와 검증**: 사용자 화면의 실제 동작과 테스트 selector/capability fixture를 구분해 조사하고,
오래된 기대값이라면 현재 합의된 사용자 흐름에 맞게 테스트를 고쳤다. 예를 들어 선택 UI가 checkbox에서
radio로 바뀌었다면 다중 선택을 가정한 테스트는 제품 실패가 아니라 낡은 시나리오일 수 있다. Playwright가
pointer 이벤트를 보냈는데 브라우저 click activation이 일어나지 않는 환경에서는 UI를 억지로 바꾸기보다
테스트의 상호작용 방법을 수정했다. 이후에는 실패가 난 사용자 흐름만 요약하고, broad suite는 코드 변경과
위험도에 맞춰 실행해 같은 증거를 무의미하게 반복하지 않았다.

### 새 글쓰기 경험을 만들 때 기존 기능을 한꺼번에 갈아엎지 않기

**참고사항**

기존 글쓰기 화면을 직접 바꾸면 새로운 설계가 실패했을 때 사용자가 안정된 작업 경로까지 잃을 수 있다.
그렇다고 별도 화면을 영구히 중복 구현하면 유지보수 비용이 두 배가 된다. 실험을 어느 정도 격리할지,
이미 검증된 작성·미리보기·발행 기능을 어디까지 재사용할지의 균형이 필요하다.

**결과와 검증**: 새로운 글쓰기 흐름을 별도 베타 경험으로 시작해 사용자가 직접 확인할 수 있게 하고,
기존 발행 엔진과 문서 저장처럼 검증된 핵심은 좁은 경계를 통해 재사용했다. 한 번에 모든 원고 입력
방식을 전환하지 않고 붙여넣기, 폴더, AI 작성 순으로 공통 작업공간에 연결했다. 각 단계에서 같은
편집·미리보기·이미지 동작을 확인한 뒤 다음 입력 경로를 붙였다. 실험적 경로의 독립성과 핵심 로직의
재사용을 동시에 유지한 점이 제품 진화의 중요한 교훈이다.

### 피드백을 실행 가능한 협업 규칙으로 남기는 법

**참고사항**

사람과 AI가 반복 개발을 할 때, 매번 “더 간결하게”, “전체 테스트는 필요한 때만”처럼 대화로만
요청하면 새 작업이나 context가 바뀔 때 같은 마찰이 되풀이된다. 반면 모든 작은 요청을 장문의 규칙으로
만들면 지침이 서로 충돌하거나 읽기 어려워져 오히려 판단이 느려진다.

**결과와 검증**: 짧은 작업 요약, 변경 범위에 맞는 테스트, 전체 suite 전 승인, Git 통합 전 상태 확인,
사용자에게 남겨야 할 시각 검증처럼 반복되는 결정 기준을 저장소 협업 규칙으로 기록했다. 실제로 답변도
서술형 작업 보고보다 변경점·검증·남은 일 위주로 요약하도록 다듬었다. 제품 방향과 시각적 수용 여부는
사용자가 소유하고, 조사·구현·자동 검증은 에이전트가 맡는 경계도 명확히 했다. 협업 규칙은 AI에게
친절한 말투를 요청하는 prompt라기보다 책임·승인·검증의 작동 규칙이어야 한다.

### 재시작한 뒤 연결 상태가 다시 ‘확인 필요’가 되는 이유

**참고사항**

설정 파일과 로그인 정보가 디스크에 남아 있어도, 화면의 ‘연결됨’ 표시는 그 파일이 존재한다는 뜻과
동일하지 않다. 과거에 성공한 인증이 지금도 유효한지, 대시보드와 설정 화면이 같은 기준으로 확인하는지,
앱 재시작 후에도 그 확인 결과를 올바르게 다시 계산하는지가 모두 필요하다. 검증 상태를 영구히 성공으로
저장하면 폐기된 token이나 바뀐 비밀번호를 계속 성공으로 보일 수 있고, 매 화면 이동마다 외부 서비스에
접속하면 느리고 중복 호출이 늘어난다.

**결과와 검증**: 연결 상태는 설정 화면과 Dashboard가 같은 기준을 사용하도록 하고, 저장된 자격 정보는
재시작 뒤 현재 상태를 다시 확인했다. 동일 시점에 중복 확인이 들어오면 진행 중 요청을 공유하고, 최근
검증은 짧은 시간 재사용했다. 설정이 바뀌면 이전 확인 결과를 재사용하지 않고, 대시보드가 외부 인증
확인 때문에 전체 첫 화면을 막지 않도록 했다. ‘값이 설정됨’, ‘마지막으로 성공함’, ‘현재 연결 확인됨’을
별도 상태로 다루는 일이 핵심이다.

### 발행 실패 때 사용자가 쓴 내용을 지우지 않는 것이 기능이다

**참고사항**

글 발행 버튼은 외부 로그인이나 권한 오류를 만날 수 있다. 제출 버튼을 누른 직후 폼을 초기화하면
비동기 발행이 실패했을 때 사용자는 주제·본문·키워드·발행 옵션을 다시 입력해야 한다. 그렇다고 성공한
요청이 끝난 뒤 사용자가 이미 새 글을 작성 중인데 화면을 무조건 비워도 안 된다. 저장·실행·외부 게시가
서로 다른 시점에 끝날 수 있기 때문에 “언제 입력 내용을 정리해도 되는가”를 명시해야 한다.

**결과와 검증**: 선택된 플랫폼에 대한 인증과 권한을 먼저 확인하고, 실패하면 원고를 대기열이나 외부로
보내기 전에 입력 상태를 보존했다. 실행이 시작된 뒤 실패한 항목도 다시 시도할 수 있게 남겼다. 성공한
경우에도 제출 당시 내용과 현재 입력이 여전히 같은지 비교하고, 사용자가 실행 중 새로 작성한 내용은
초기화하지 않았다. 테스트에서는 만료된 로그인, WordPress 설정 오류, 실행 중 입력 수정과 재시도를 각각
재현했다. 입력 보존은 폼의 편의 기능이 아니라 실패 복구와 중복 발행 예방의 일부다.

### RSS를 정기적으로 읽되, 바뀌지 않은 데이터를 계속 쓰지 않기

**참고사항**

여러 블로그나 공개 RSS를 모아 콘텐츠 후보로 보여주면 주기적인 수집이 필요하다. 하지만 매번 전체
목록을 스프레드시트에 다시 쓰면 사용자가 고친 제목·상태·발행 계획을 덮어쓰고 API quota도 낭비할 수
있다. 한 feed가 잠깐 실패했다고 다른 정상 source의 새 글까지 가리는 문제, 앱 재시작이나 설정 변경 때
수집 timer가 중복되는 문제도 있다.

**결과와 검증**: 수집 결과는 기존 항목과 식별값을 비교해 새 항목만 추가하고, 같은 feed가 변하지
않았으면 저장소에 쓰지 않았다. Naver와 WordPress 같은 source는 독립적으로 읽어 한 source의 장애가
다른 source의 결과를 없애지 않게 했으며, 실패하면 마지막 정상 자료를 보존하고 다음 실행에서 다시
시도했다. 수집은 앱 실행 중에만 수행하고 사용자에게 routine polling 알림을 띄우지 않기로 했다. RSS
등록은 콘텐츠를 선택지로 제공할 뿐 카드뉴스 생성이나 발행을 자동으로 시작하지 않는다.

### 다운로드 URL이 아니라 실제 이미지 파일을 외부 서비스가 가져갈 수 있는지 확인하기

**참고사항**

외부 게시 API가 로컬 파일이 아니라 공개 이미지 URL을 요구할 수 있다. Google Drive에서 브라우저로
열리는 공유 링크도 외부 서비스가 이미지 파일 바이트를 직접 다운로드할 수 있다는 보장은 없다. 로그인
HTML, 미리보기 페이지, redirect가 섞일 수 있기 때문이다. 파일을 공개하는 작업은 접근성과 개인정보
노출을 맞바꾸므로, 단순히 HTTP 200만 확인해서도 부족하다.

**결과와 검증**: 임시 이미지 한 장으로 익명 요청을 해 실제 응답이 이미지 MIME type과 유효한 파일
signature를 가진 바이트인지 검사했다. 첫 실패는 OAuth가 아니라 Google Cloud API 활성화 문제였고,
설정한 뒤 direct download 요청이 성공했다. 테스트 파일은 확인 후 정리했다. 이 결과가 곧 Buffer 등
모든 소비자의 호환을 증명한다고 확대 해석하지 않고, redirect 처리·예약 게시 시점의 URL 유효성·삭제
시점은 별도 확인 항목으로 남겼다. 공개 링크는 편리한 전달 수단인 동시에 수명과 정리 정책을 가진
임시 접근 권한이라는 점을 설명할 수 있다.

### 자동 업데이트는 파일을 다운로드하는 것으로 끝나지 않았다

**참고사항**

Electron 데스크톱 앱이 업데이트 패키지를 내려받고 압축을 풀었다고 해서 실제 앱 파일이 교체되는
것은 아니다. Windows에서는 앱이 실행 중일 때 실행 파일을 바꾸기 위해 보조 프로세스를 실행하고,
그 보조 프로세스가 준비됐다는 확인을 받은 뒤에야 앱을 종료해야 한다. Node가 PowerShell을 특정
분리 모드로 실행하면 부모 앱이 종료되기 전에 helper가 스크립트를 실행하지 못하고 정상 종료 코드만
반환하는 문제도 실제 패키지에서 재현됐다.

**결과와 검증**: 제품 업데이트를 바로 고치기 전에 최소 Electron 앱과 무해한 helper를 만든 격리
실험으로 기존 실행 방식과 두 단계 실행 방식을 비교했다. Windows CI의 패키징된 unsigned 앱에서 기존
방식은 helper 준비 marker를 만들지 못했고, 비분리 bootstrap이 helper를 독립 실행하는 대안은 준비와
부모 종료 후 지속 동작을 확인했다. 이후 updater는 helper 준비/완료/실패를 각각 증명하고, 준비 전에는
현재 앱을 종료하지 않도록 보강했다. macOS에서 Windows 프로세스 실행 경계를 테스트한 척하지 않고,
실제 OS와 패키지 조건에서 재현 가능한 작은 PoC를 먼저 만든 것이 핵심이다.

### 새 모델 ID가 나와도 연결 확인이 낡은 목록에 묶이면 안 된다

**참고사항**

AI 공급자는 같은 모델에 날짜가 붙은 ID를 추가하거나 endpoint 형식을 바꿀 수 있다. 모델 목록을 한 번
하드코딩한 뒤 연결 확인, UI 선택, 실행 코드가 각각 다른 이름 규칙을 가정하면 모델 선택은 보이는데
연결 확인만 실패하거나 반대로 연결 확인은 성공해도 실행 endpoint가 맞지 않는 일이 생긴다.

**결과와 검증**: 모델의 사용자 표시 이름, 공급자가 요구하는 정확한 ID, 호출 transport/endpoint를
분리해 살펴보고, 날짜형 ID처럼 유효한 변형을 임의로 잘라내지 않도록 연결 계약을 갱신했다. 최신 모델을
추가할 때 UI 카탈로그·connection check·실제 요청 경로가 같은 기준을 쓰는지 함께 검사했다. 공급자의
모델 가용성과 명명 규칙은 바뀔 수 있으므로 정기적으로 공식 문서를 확인하고, 특정 모델 선택이 거부됐을
때 다른 모델로 몰래 바꾸기보다 원인을 사용자에게 돌려주는 원칙도 함께 적용한다.

### 생성형 카드 이미지는 한 장씩 예쁜 것과 한 세트로 일관된 것이 다르다

**참고사항**

카드뉴스처럼 여러 장을 생성하면 각 이미지를 따로 보면 괜찮아도 한 세트 안에서 글꼴·색감·구도·정보량이
제각각일 수 있다. 매번 같은 고정 프롬프트를 쓰면 세트 간 결과가 반복되고, 반대로 매 장에 서로 다른
스타일 지시를 넣으면 세트의 통일성이 깨진다. AI가 한글을 이미지 안에 그리게 할지, 후처리 렌더러가
텍스트를 정확히 합성하게 할지도 품질·속도·언어별 표시 사이의 선택이다.

**결과와 검증**: 한 세트 안에서는 공통 art direction과 각 슬라이드 역할을 공유하고, 새 세트를 만들
때는 variation cue를 바꿔 결과를 달리하는 접근을 사용했다. 처음부터 색상·폰트·템플릿 편집기를 크게
만들기보다 카드 수, 비율, 스타일, 이미지 안 한글 사용처럼 사용자가 결정해야 할 소수 옵션만 보였다.
이미지 모델이 한글을 어떻게 처리하는지는 모델과 시점에 따라 다르므로 모든 결과에 정확한 글자를
보장한다고 약속하지 않고, 별도 렌더링은 제품 조건과 검증 결과에 따라 후속 선택으로 두었다. 생성
실패 시 마지막 성공 결과를 보존하고, 사용자가 결과를 내려받아 확인할 수 있게 했다.

### Google Picker는 계정 권한을 대신하는 마법의 창이 아니었다

**참고사항**

`drive.file` 권한만으로는 사용자가 예전에 직접 만든 임의의 파일이 앱에 자동으로 보이지 않을 수 있다. 반면 파일 선택 UI에서 사용자가 특정 파일을 앱에 명시적으로 선택하면 그 파일을 앱이 다루는 경로가 열린다. 그래서 “내 계정으로 로그인했으니 내 Drive 파일은 전부 읽을 수 있다”와 “파일 선택창에서 고른 파일만 앱에 공유한다”는 서로 다른 권한 모델이다. OAuth 로그인과 파일 선택은 밀접하지만 같은 동작은 아니다.

**결과와 검증**: 별도 웹 POC에서 `drive.file`만 요청해 앱이 만든 파일의 읽기·쓰기와 계정 소유자가 만든 파일의 기본 접근 차이를 확인하고, 파일 선택 이후 선택한 파일을 읽고 수정하는 흐름을 검증했다. 제품에서는 신규 파일 생성과 기존 파일 선택을 한 연결 흐름 안에 두고, 계정 인증이 필요한 경우 사용자가 시작한 동작에서 인증을 이어가도록 했다. 기존 URL 연결 사용자는 자동 전환된 것으로 간주하지 않고 기존 파일을 한 번 다시 선택하게 하되, 취소나 실패 때 기존 연결 정보를 지우지 않고, 성공 뒤에는 반복 안내하지 않도록 했다. 핵심은 권한을 넓히는 대신 사용자가 선택한 리소스를 좁게 허용하고, 파일 내용은 그대로 보존하면서 연결 자격만 바꾸는 것이었다.

### 테이블의 RLS를 켰다고 비밀값이 안전해지는 것은 아니었다

**참고사항**

Row Level Security(RLS)는 데이터베이스 테이블을 직접 조회할 때 적용되는 행 접근 규칙이다. 권한이 높은 서버 함수가 호출자를 대신해 동작한다면, 그 함수가 어떤 입력을 받으며 무엇을 반환하는지가 별도의 보안 경계가 된다. 따라서 “모든 테이블에서 RLS가 켜져 있다”만으로 API 전체가 안전하다고 결론 내릴 수 없다. 함수 실행 권한, 호출자 확인, 반환 데이터의 최소화, 허용할 항목의 명시적 제한까지 함께 살펴야 한다.

**결과와 검증**: Supabase 스키마·함수 권한 검토에서 테이블 보호와 RPC 함수의 반환 범위는 별도로 감사해야 함을 확인했다. 특히 빈 목록이나 알 수 없는 요청을 “제한 없음”으로 해석하지 말고 거부하는 fail-closed 계약, 필요한 호출자만 함수에 접근하는 grant, 꼭 필요한 값만 반환하는 경로를 단계적으로 정리했다. 공개 글에서는 실제 테이블·함수명이나 운영 환경의 세부 발견사항을 공개하지 않고, “테이블 정책과 서버 함수 권한을 한 쌍으로 점검하는 보안 리뷰”라는 일반 원칙으로 설명할 수 있다.

### 앱에 포함되는 OAuth 설정과 서버에만 둬야 하는 공유 자격은 다르다

**참고사항**

데스크톱 앱의 OAuth Client ID는 사용자를 인증할 앱을 식별하기 위한 값이고, 설치된 앱에 비밀처럼 숨겨둘 수 있는 서버 자격과는 성격이 다르다. 반대로 모든 사용자가 함께 쓰는 외부 API 키는 추출되면 공유 quota와 비용에 영향을 줄 수 있다. 두 값을 모두 막연히 “secret”이라고 부르면 어느 쪽을 어디에 저장하고 어떤 경계에서 쓸지 잘못 결정하기 쉽다.

**결과와 검증**: credential을 소유자와 사용 목적에 따라 나눠, 사용자 개인 OAuth는 장치에서 사용자 승인과 제한 scope를 사용하고, 공유 자격이 필요한 기능은 좁은 서버 capability를 통해 실행하도록 점진적으로 옮겼다. 서버 함수는 사용자가 임의의 credential을 읽는 통로가 아니라, 허용된 기능만 실행하는 경계여야 한다. 기존 사용자를 한 번에 끊지 않도록 호출자를 먼저 이전하고 호환 기간을 둔 뒤 사용하지 않는 경로를 정리하며, 운영 credential 교체는 개발 검증과 별도 승인·절차로 다루는 것도 중요한 결과다.

### Buffer에 발행 요청을 보냈다고 발행 여부를 아는 것은 아니었다

**참고사항**

SNS 게시처럼 외부 부작용이 있는 요청은 서버가 요청을 처리한 직후 응답만 네트워크에서 사라질 수 있다. 이때 클라이언트가 무조건 재시도하면 같은 게시물이 이미 예약되거나 게시됐는데 중복 시도를 할 위험이 있다. timeout은 “실패했다”가 아니라 “결과를 아직 모른다”일 수 있다. 이 구분은 결제·예약·파일 생성 등 다른 비멱등 작업에도 그대로 적용된다.

**결과와 검증**: 발행 응답이 모호하면 같은 내용을 즉시 다시 보내는 대신 최근 게시 결과를 확인해 이미 처리된 채널은 완료로 복구하고, 확인되지 않은 채널만 재시도하도록 보완했다. Buffer가 중복이라고 명시적으로 응답한 경우도 단순 실패로 기록하지 않도록 했다. 여러 채널 가운데 일부만 성공한 상황을 별도로 다루어 성공한 채널에 같은 요청을 반복하지 않게 했다. 대외 API가 idempotency key를 제공하지 않더라도, 요청 전후의 상태 대조와 채널별 진행 기록으로 중복 가능성을 낮출 수 있다는 실전 사례다.

### 외부 게시 서비스는 이미지 파일 대신 공개 URL을 요구할 수 있다

**참고사항**

사용자 PC에 있는 이미지를 외부 게시 서비스에 넘긴다고 해서 그 서비스가 로컬 파일에 접근할 수 있는 것은 아니다. Buffer 연동에서는 이미지의 공개 HTTPS URL이 필요한 경로를 확인했다. Drive의 공유·미리보기 페이지 URL은 브라우저에서 열리는 것과 외부 서버가 이미지 바이트를 직접 가져가는 것이 같지 않다. 다운로드 권한, redirect, 응답 MIME과 실제 파일 형식, 예약 시점까지 URL이 살아 있는지를 나눠 검증해야 한다.

**결과와 검증**: 임시 파일로 외부에서 받은 응답이 이미지 바이트인지 먼저 확인하고, Drive 링크만으로는 충분하지 않은 경우를 찾아 실제 미디어 전달 경로를 시험했다. 첫 실패를 OAuth 문제로 오인하지 않고 Google Cloud API 활성화 상태와 HTTP 응답을 분리해 진단했다. Buffer 테스트에서는 작은 합성 이미지가 거부되고 실제 규격의 이미지가 받아들여지는 차이도 확인해, “API가 응답했다”와 “실제 사용자의 미디어 조건을 통과했다”를 구별했다. 공개 URL은 편의성뿐 아니라 접근 범위, 보존 기간, 게시 후 정리 시점을 포함해 설계해야 한다. 외부 서비스의 최신 이미지 제약은 글을 발행하기 전에 공식 문서로 재확인한다.

### 비동기 이미지 생성에서는 제출 재시도보다 작업 추적이 먼저였다

**참고사항**

보통 API 호출은 결과를 기다렸다가 timeout이면 다시 시도하는 방식으로 생각하기 쉽다. 하지만 유료 생성 작업은 서버가 작업을 접수한 뒤 응답이 유실될 수 있고, 무턱대고 다시 제출하면 같은 작업에 중복 비용이 발생할 수 있다. 비동기 API는 제출, 작업 ID 획득, 상태 조회, 결과 다운로드가 서로 다른 단계이며 각 단계의 재시도 안전성이 다르다.

**결과와 검증**: KIE.ai 이미지 경로는 제출을 한 번만 시도하고, 작업 ID를 받은 뒤에는 상태 조회와 결과 다운로드를 재시도하도록 분리했다. 응답을 잃어 접수 여부를 모르는 경우 새 유료 작업을 자동 생성하지 않고 결과를 미확정으로 다뤘다. 기존 호출자는 완료 이미지 파일을 받는 계약을 유지해 공급자별 비동기 절차가 나머지 글쓰기 흐름으로 새지 않게 했다. 최소한의 작업 상태는 재시작 뒤 식별할 수 있게 기록하되 prompt나 자격값은 기록하지 않았다. 나중에 취소 기능을 더할 때도 앱에서 대기를 중단하는 것과 공급자 쪽 계산을 실제로 취소하는 것을 구분해야 했다.

### 로컬·개발·운영 데이터베이스를 같은 변경 이력으로 재현하기

**참고사항**

원격 개발 DB를 손으로 먼저 수정하면 로컬 개발자가 그 상태를 재현하지 못하거나 새 환경에서 migration 순서가 깨질 수 있다. 데이터베이스 변경은 SQL 하나의 성공 여부만 볼 것이 아니라 빈 환경에서 처음부터 다시 만들 수 있는지, 역할별 권한과 함수 실행 계약이 일치하는지, 개발 환경에서 검증한 변경만 운영으로 승격되는지를 확인해야 한다.

**결과와 검증**: 로컬 Supabase를 migration 기반으로 재현하고, 스키마·RLS·함수 권한 계약을 자동 확인한 뒤 Development 환경과 비교하는 개발 루틴을 마련했다. 원격 환경은 로컬 변경을 대체하는 별도 진실의 원천이 아니라 검증·승격 대상이 되도록 정리했다. 서비스 데이터나 운영 자격을 로컬에 복제하지 않고 테스트용 데이터로 계약을 검증하며, 운영 반영은 개발 배포와 분리해 승인받는 원칙을 설명할 수 있다.

### 새 외부 공급자를 붙일 때 API 응답을 그대로 제품 계약으로 삼지 않기

**참고사항**

같은 “이미지 생성” 기능이라도 동기 응답, 비동기 작업 ID, 공급자별 상태 이름과 결과 URL이 다를 수 있다. 공급자 API 응답을 화면과 모든 호출자에게 직접 퍼뜨리면 다음 공급자를 추가할 때 제품 코드 곳곳에 조건문이 생긴다. 반대로 잘못 일반화하면 특정 모델의 요청 형식을 추측해 실패를 숨길 수도 있다.

**결과와 검증**: 공통 작업 흐름은 제출·대기·실패·결과 적용의 책임을 맡고, 공급자별 adapter는 신뢰할 수 있는 endpoint와 요청/응답 형식을 해석하도록 경계를 잡았다. 모델 카탈로그만 보고 미지원 요청 형식을 만들어내지 않고, 실제 API 계약을 확인한 모델만 허용했다. 성공적인 KIE 이미지 경로는 기존 호출자에게 로컬 파일 결과를 돌려주면서 비동기 세부사항을 경계 안에 둔 사례다. 다만 공통 추상화가 모든 공급자를 똑같게 만든다는 주장이 아니라, 달라지는 곳을 고립시켜 검증 가능하게 한다는 점을 강조한다.

## 개발과 배포 환경

### GHCR에 Docker image를 보관하고 동일한 artifact를 환경별로 승격하는 방법

**참고사항**

Container registry는 소스 저장소나 실행 서버가 아니라, CI가 빌드한 Docker image를 보관하고
배포 대상이 가져갈 수 있게 하는 저장소다. GitHub에 소스와 CI가 있는 프로젝트에서는 GHCR
(GitHub Container Registry)을 사용해 테스트를 통과한 image를 Git commit, version tag와 digest에
연결할 수 있다. Development와 Production 서버가 각자 소스에서 image를 다시 빌드하지 않고 같은
digest를 내려받아 실행하면, 검증한 실행물과 배포한 실행물이 동일하다는 사실을 확인하기 쉽다.

글에서는 `source repository -> CI build/test -> image registry -> deployment target`의 역할을
구분한다. Tag는 사람이 읽기 쉽고 버전 운영에 편하지만 다른 image를 가리키도록 움직일 수 있다.
Digest는 image content에 의해 결정되는 immutable identity이므로 승격과 rollback의 정확한 기준이
된다. CI는 commit SHA와 version tag를 함께 기록하되 실제 배포 manifest에는 digest를 고정하고,
SBOM·취약점 검사·서명과 provenance를 연결하면 공급망 신뢰도를 높일 수 있다.

Docker Hub는 Docker 생태계 전반의 공개 배포와 발견에 강하고, GHCR은 GitHub repository, Actions,
Packages와 조직 권한을 함께 관리하기 편하다. Registry 선택 시 공개·비공개 범위, pull 권한,
보존 정책, 비용, multi-architecture image, rate limit과 서버의 인증 방법을 비교한다. Registry는
배포 승인, health check와 rollback을 대신하지 않으므로 동일 artifact 원칙과 운영 배포 절차를
함께 설계해야 한다.

### Local에서 Development를 거쳐 Production까지 DB 변경을 안전하게 승격하는 방법

**참고사항**

초기에는 필요한 SQL을 각 환경에 직접 실행해도 빠르게 보이지만, 시간이 지나면 어느 DB에 어떤
변경이 적용됐는지 재현하기 어렵고 운영 데이터에 검증되지 않은 변경을 적용할 위험이 커진다.
Local, 원격 Development와 Production의 역할을 분리하고 순서가 있는 canonical migration을 모든
환경의 단일 변경 이력으로 삼는 이유를 설명한다.

Feature branch에서는 빈 Local DB를 reset하고 migration과 비식별 seed가 처음부터 순서대로
적용되는지 확인한다. 통합 branch에서는 같은 migration과 server function을 Development에 배포해
원격 migration 이력, 함수 상태와 공개 smoke 결과를 검증한다. Production은 새로운 코드를 시험하는
장소가 아니라 Development에서 검증한 변경 묶음을 승인해 승격하는 대상이어야 한다.

이때 artifact와 fingerprint를 이용하면 `검증한 바로 그 변경인가`를 기계적으로 비교할 수 있다.
Artifact는 DB 복사본이 아니라 다음과 같은 배포 입력을 정규화한 JSON 명세다.

- 모든 migration의 version, 경로와 파일 내용 SHA-256
- 모든 server function과 shared module의 경로와 파일 내용 SHA-256
- 함수 이름과 인증 정책
- 환경별 manifest의 파일 내용 SHA-256
- 정확한 Git commit SHA

정렬과 직렬화 규칙을 고정한 artifact 전체의 SHA-256을 대표 fingerprint로 사용한다. SQL 한 글자,
함수 코드 한 줄, 인증 정책, manifest 또는 commit이 달라지면 fingerprint도 달라진다. Development
검증 결과에 fingerprint를 남기고 Release 후보에서 다시 계산한 값이 다르면 승격을 차단한다.
Fingerprint는 두 변경 묶음이 동일하다는 증거일 뿐 내용이 올바르다는 증거는 아니다. 올바름은
Local reset, 자동 테스트, Development smoke와 사용자 검증이 담당한다.

Production 적용 전에는 read-only schema audit, backup/PITR, 대상 project 식별자, 영향 범위,
중단 조건과 승인자를 확인한다. 일반적으로 schema migration을 먼저 적용하고 이에 의존하는 server
function을 배포하며, 완료 후 read-only smoke와 evidence를 남긴다. 장애가 발생하면 이미 적용된
migration 파일을 수정하거나 DB를 무리하게 과거로 되돌리기보다 새 migration으로 forward fix하는
편이 이력과 복구 가능성을 지키기 쉽다.

마지막으로 additive migration과 호환성을 구분한다. enum 또는 CHECK 범위를 넓히는 변경처럼 기존
클라이언트가 계속 동작하는 변경은 단계적 배포가 쉽다. 반면 기존 credential row나 column을
삭제하는 변경은 migration 문법이 단순해도 구버전 앱을 즉시 깨뜨릴 수 있다. 최소 지원 버전,
구버전 종료 정책, data backfill, rollback·복구 조건을 migration 설계와 함께 결정해야 한다.

## 디자인 시스템과 AI 협업

### 예쁜 화면보다 먼저 판단 체계를 만든 이유: Design Principle에서 Component Guide까지

**참고사항**

디자인 고도화를 색상, 서체와 둥근 모서리를 바꾸는 작업으로 시작하면 개별 화면은 그럴듯해져도
제품 전체에는 설명하기 어려운 예외가 쌓이기 쉽다. 같은 역할의 버튼이 화면마다 다르게 강조되고,
선택 상태와 keyboard focus가 비슷하게 보이며, 어떤 영역은 이유 없이 배경색이 채워지는 식이다.
사람과 AI가 함께 UI를 반복해서 개선하는 환경에서는 취향을 전달하는 style guide만으로 부족하다.
새로운 문제를 만날 때 같은 판단을 다시 내릴 수 있는 계층적인 기준이 필요하다.

글에서는 디자인 관련 문서의 역할을 다음처럼 구분한다.

1. **Product Experience Principles**는 제품이 지향할 경험과 판단 이유를 정의한다. 사용자의 목적을
   화면의 주인공으로 삼고, 시작은 단순하게 만들며, 시스템 상태와 작업의 연속성을 보존하고, 같은
   의미를 같은 방식으로 표현하는 것처럼 style이 바뀌어도 유지될 기준이다.
2. **Operational Guidelines**는 원칙을 반복 가능한 화면 결정으로 번역한다. 완료 행동의 위치와
   위계, secondary·danger action의 분리, 예외를 허용하는 조건처럼 실제 review에서 바로 사용할 수
   있는 규칙을 다룬다.
3. **Component and Pattern Guide**는 구현 과정에서 검증된 세부 계약을 축적한다. selected, hover와
   focus-visible의 차이, disabled와 hidden의 선택 기준, inline 안내와 tooltip의 역할, progressive
   disclosure의 summary, provider 종속 control, 복구 가능한 초기화 등이 여기에 속한다.
4. **Semantic Token 및 Style Contract**는 style이 변경할 수 있는 것과 소유하면 안 되는 것을
   구분한다. 색상, typography, radius, elevation과 density는 style pack이 바꿀 수 있지만 기능,
   DOM, action priority, 상태 전이, ARIA와 keyboard 순서는 공통 계약으로 유지한다.
5. **Style Pack**은 같은 계약 안에서 하나의 완결된 시각적 성격을 제공한다. 성격이 다른 두 번째
   style을 실제 화면에 연결하면 첫 style의 공통 규칙처럼 숨어 있던 raw color, spacing과 component
   결합을 발견할 수 있다.
6. **Development Record와 Validation Gate**는 어떤 문제를 관찰했고 어떤 대안을 검토했으며 왜 현재
   기준을 선택했는지 보존한다. 원칙 초안, compatibility 기반, 첫 정식 style, 두 번째 style 같은
   단계에서 자동 검증과 사용자 확인을 거쳐야 선언이 실제 제품 계약으로 발전한다.

구체적인 사례를 통해 `일관성`과 `획일성`의 차이를 설명한다. 모든 component를 같은 모양으로 만드는
것이 아니라 같은 의미에 같은 판단 규칙을 적용하는 것이 일관성이다. 예를 들어 인접한 선택으로
활성화할 수 있는 예약 field는 존재와 의존 관계를 보여주기 위해 disabled로 남길 수 있지만, 현재
작업과 완전히 무관해 복잡성만 늘리는 field는 숨길 수 있다. 항상 필요한 짧은 정보는 inline hint,
필요할 때만 확인할 긴 설명은 tooltip, control과 상태만으로 충분히 이해되는 내용은 시각적으로
생략한다. 특정 provider에서만 유효한 옵션은 그 provider가 선택된 동안만 활성화하되 사용자의
선호값은 지우지 않는다.

작은 불일치를 고치는 과정도 기준을 발전시키는 자료가 된다. Select와 disclosure 화살표의 우측
여백을 공통 trailing inset으로 맞추고, tooltip이 container에 잘리는 문제를 field별 위치
hard-coding이 아니라 가용 공간을 측정하는 collision-aware placement로 해결할 수 있다. 반대로 native
date/time picker 내부 UI처럼 운영체제와 브라우저가 소유하는 영역은 focus 접근성을 해치지 않는지
확인한 뒤 합리적인 예외로 기록한다. 시각 통일만을 위해 복잡한 custom widget을 다시 만드는 비용도
함께 비교한다.

AI와의 역할 분담도 다룬다. 사용자는 제품 방향, 실제 사용 중 느끼는 미묘한 위계와 예외의 타당성을
판단하고, coding agent는 관련 구조를 조사해 일회성 CSS 대신 공통 규칙을 구현하며 자동 검증과 문서를
갱신한다. `발견 -> 원인 조사 -> 기준 도출 -> 제한된 적용 -> 사용자 확인 -> canonical guide 승격`의
순환을 사용하면 작은 UI feedback이 제품 전체에서 재사용할 수 있는 설계 자산으로 남는다. 디자인
시스템의 완성도를 component 개수보다 새로운 화면에서도 일관된 결정을 재현할 수 있는지로 평가하는
관점을 제안한다.

### Codex 바이브 코딩에서 품질을 유지하며 불필요한 토큰과 사용량을 줄이는 방법

**참고사항**

Coding agent를 경제적으로 오래 사용하는 방법을 단순히 prompt 글자 수를 줄이는 요령으로 설명하면
핵심을 놓치기 쉽다. 짧지만 모호한 요청은 광범위한 탐색, 반복 질문, 잘못된 구현과 재작업을 만들 수
있다. 반대로 목표, 범위와 완료 조건을 조금 길게 적은 요청은 전체 작업량을 줄일 수 있다. 핵심은
모델에게 덜 생각하라고 요구하는 것이 아니라 이미 끝난 조사와 결정을 다시 생각하지 않게 하고,
현재 변경의 위험에 필요하지 않은 문맥·도구·검증을 소비하지 않게 만드는 것이다.

먼저 큰 프로젝트를 목표와 검증 경계가 분명한 stage로 나눈다. 각 stage에는 `사용자 필요`, `목표`,
`포함 범위`, `명시적 비범위`, `보존할 동작`, `목표 산출물`, `완료 조건`, `검증 수준`을 기록한다.
이렇게 하면 agent가 선의로 인접 기능까지 확장하거나 완료 기준을 추측하는 일을 줄일 수 있다. 기능
branch의 development record에는 중요한 결정, 실패한 접근, 교정 내용과 마지막 검증 결과를 남기고,
장기간 유효한 구조만 canonical architecture 문서로 승격한다. 프로젝트 전체에서 반복할 규칙은
`AGENTS.md` 같은 지침 파일에 두되, 너무 길거나 서로 충돌하는 지침은 오히려 매 작업의 input context와
판단 비용을 키울 수 있으므로 주기적으로 감사한다.

Thread를 오래 유지하면 요구사항과 결정뿐 아니라 탐색 출력, 긴 test log, 이미 해결된 오류와 오래된
대안도 함께 쌓인다. Stage나 review milestone이 끝났을 때 새 thread로 이동하고 전체 대화를 복사하는
대신 다음 정보만 인계한다.

- 현재 repository, branch와 working-tree 상태
- 완료된 범위와 아직 남은 범위
- 사용자가 확정한 중요한 결정과 명시적 비범위
- 관련 canonical 문서와 development record 경로
- 최근 focused test, browser smoke와 full regression 결과
- known issue, 다음 목표와 첫 착수 순서

새 thread의 agent는 이 인계문을 그대로 믿기보다 Git과 문서를 짧게 확인한 뒤 작업을 계속한다. 이
방식은 대화 기억을 버리는 것이 아니라 가치 있는 문맥을 저장소의 검증 가능한 상태로 압축하는
것이다. API 기반 agent workflow에서는 공식 compaction 기능을 검토할 수 있지만, 사람이 사용하는
Codex에서도 milestone별 요약과 새 thread 분리는 같은 목적의 실용적인 운영 방법이 된다.

탐색과 도구 출력도 필요한 부분만 남긴다. 먼저 file list와 `rg` 같은 targeted search로 후보를 좁힌
뒤 관련 구간을 읽고, 전체 파일·전체 로그를 매번 대화에 싣지 않는다. 명령 결과가 길다면 실패 이름,
원인과 다음 행동을 요약하고 원문은 repository 또는 test artifact에서 다시 확인할 수 있게 한다.
Agent에게도 진행 중에는 핵심 상태만, 완료 시에는 변경점·검증 결과·수동 확인 항목만 보고하도록
요청하면 구현 품질과 무관한 output token을 줄일 수 있다.

검증은 변경 위험에 맞춰 단계적으로 넓힌다. 작은 UI나 copy 수정마다 full suite를 반복하지 않고
구현 중에는 관련 focused contract를, 하나의 reviewable slice가 완성되면 browser smoke를, 사용자
확인과 merge 준비가 끝난 뒤 full regression을 수행한다. 테스트를 생략하는 것이 아니라 같은
증거를 변화 없이 반복 생성하지 않는 것이다. 실패가 나왔을 때만 관련 범위를 다시 좁혀 원인을
찾고, 수정 후 필요한 수준까지 재검증한다.

모델과 reasoning effort도 작업 난이도에 맞춘다. 단순한 위치 탐색, 반복 변환과 읽기 중심 요약은
빠르고 경제적인 모델 또는 낮은 reasoning으로 처리할 수 있고, 모호한 다단계 구현, architecture,
보안과 어려운 회귀 분석에는 더 강한 모델과 높은 reasoning을 사용한다. 높은 reasoning이 항상 더
좋다는 전제보다 실제 작업에서 품질 차이를 평가해 기본값을 정한다. 모델 이름, 제공 범위와 사용량
정책은 바뀔 수 있으므로 글 작성 시점의 공식 OpenAI 문서를 다시 확인한다.

하위 agent의 병렬 실행도 시간과 token을 구분해 판단한다. 독립적인 code mapping, 문서 조사, 보안과
test gap 검토처럼 결과를 요약해 합칠 수 있는 작업은 병렬화의 이점이 있다. 그러나 각 agent가 별도
context와 도구를 사용하므로 단일 agent보다 총 token 사용량이 늘 수 있고, 같은 파일을 여러 agent가
동시에 편집하면 충돌과 조정 비용까지 생긴다. 작업이 실제로 독립적이고 병렬 결과가 시간 또는 품질을
충분히 개선할 때만 사용하고, 범위가 작은 순차 수정에는 한 agent를 유지한다.

마지막으로 `토큰을 일정 비율 줄이면 사용 시간이 같은 비율로 늘어난다`거나 `prompt가 짧을수록 항상
저렴하다`고 단정하지 않는다. Codex와 구독형 제품의 실제 사용 한도는 선택한 모델, reasoning 수준,
기능, tool call, 병렬 agent와 시점별 정책의 영향을 받을 수 있다. 글의 초점은 보장할 수 없는 절감률이
아니라 `재탐색`, `재작업`, `불필요한 전체 검증`, `과도한 출력`, `중복 context`를 줄이면서 비슷한
품질의 근거와 검증을 유지하는 작업 설계에 둔다.
