# Release Publish Form Resilience Development

## Branch

- Branch: `codex/release-publish-form-resilience`
- Base/parent: `release/v0.4.0`
- Start date: 2026-09-02
- Status: Completed and accepted

## User Need

`블로그 Beta > 빠른 글 작성 > 바로 생성`에서 바로 포스팅을 시도할 때 네이버 로그인 만료나 워드프레스 연결 오류가 발생해도 사용자가 작성한 주제, 키워드, 제목, 참고사항과 발행 설정을 잃지 않아야 한다. 연결 실패는 작성 내용에 파괴적인 영향을 주지 않아야 한다.

## Goal

- 선택한 발행 대상의 연결 상태를 실제 발행 전에 확인한다.
- 네이버 또는 워드프레스 연결 검증이 실패하면 입력 폼을 그대로 유지한다.
- 실패 안내는 대상별로 명확하고 간결하게 제공한다.
- 워드프레스가 설정되지 않은 경우 사용할 수 없는 발행 대상을 선택하지 못하게 한다.
- 비동기 발행 실패가 발생해도 대기열에 저장된 글감을 보존하고 사용자가 다시 실행할 수 있게 한다.
- 성공한 제출을 정리할 때도 사용자가 그 사이 새로 작성한 내용을 지우지 않는다.

## Scope

- 빠른 글 작성의 `바로 포스팅` 흐름
- 네이버 세션 사전 확인
- 워드프레스 설정 및 연결 사전 확인
- 대상 선택 가능 상태와 안내 문구
- 제출 폼 보존 및 성공 시 조건부 초기화
- 관련 서비스, UI 계약 및 브라우저 회귀 테스트

## Non-goals

- 네이버 브라우저 세션을 OAuth2 refresh-token 방식으로 교체
- 네이버가 폐기한 로그인 쿠키의 자동 복구
- 워드프레스 자격 증명 또는 네이버 로그인 정보를 UI가 자동 수정
- 발행 엔진 전반의 재설계

## Proposed Design

1. 현재 대상별 설정·연결 확인 API와 발행 런타임 경계를 조사한다.
2. 바로 포스팅 전에 선택된 대상만 검증하는 명시적 preflight 계약을 둔다.
3. preflight 실패 전에는 대기열 저장이나 폼 초기화를 하지 않는다.
4. 실행이 시작된 뒤 실패하더라도 대기열 항목을 `발행 준비 완료`로 보존한다.
5. 바로 포스팅 폼은 실행의 성공이 확인되기 전까지 유지한다. 성공 시에도 제출 스냅샷과 현재 폼이 같을 때만 초기화한다.
6. 워드프레스 미설정 상태는 대상 선택 불가와 이유 안내로 표현한다.

## Decisions

- 사용자 원칙: 인증이나 발행 실패는 사용자가 작성한 내용에 대해 절대 파괴적인 결과를 만들지 않는다.
- 네이버 실패 문구는 `네이버 로그인 후 다시 시도해 주세요.`처럼 간결하게 쓴다.
- 워드프레스도 네이버와 동일하게 사전 연결 검증과 입력 보존 원칙을 적용한다.
- 네이버 인증은 현재 브라우저 저장 상태 기반이며 OAuth2 refresh-token 전환은 이번 범위에 포함하지 않는다.

## Progress

- 현재 흐름이 대기열 저장 직후 폼을 먼저 초기화하고, 이후 비동기 실행을 시작한다는 원인을 확인했다.
- 네이버 인증은 `naver_auth.json` 브라우저 저장 상태를 사용하고, 글쓰기 화면이 로그인 페이지로 전환되는지 검사한다는 점을 확인했다.
- 유효한 확인 및 발행 뒤에는 최신 브라우저 저장 상태를 다시 기록하지만, 네이버가 만료한 세션을 자동 갱신하는 refresh token은 없음을 확인했다.
- 바로 포스팅 전에 선택된 네이버 세션을 강제로 다시 확인하고, 선택된 WordPress의 REST 인증과 글쓰기 권한을 확인하도록 연결했다.
- 어느 연결 검사든 실패하면 대기열 저장 요청을 보내지 않고 현재 입력값과 입력 모드를 유지하도록 했다.
- 설정되지 않은 네이버 또는 WordPress 대상은 Blog Beta에서도 선택 해제 및 비활성화되도록 기존 플랫폼 준비 상태 동기화에 포함했다.
- 바로 포스팅으로 대기열에 저장한 항목은 실행 완료 전까지 폼을 유지한다. 완료 시 제출 당시 스냅샷과 현재 폼이 같을 때만 초기화해 실행 중 새로 입력한 내용을 보호한다.
- WordPress 인증 검사가 단순 로그인뿐 아니라 실제 글쓰기 권한까지 실패로 구분하도록 응답 계약을 명확히 했다.
- 사용자 테스트에서 초기 Dashboard 연결 상태 확인이 오래 걸리고, 잘못된 네이버·WordPress 설정을 저장해도 이전 정상 상태가 남는 문제를 확인했다.
- 초기 Dashboard는 네이버 숨은 브라우저 검사를 직접 실행하지 않고 현재 프로세스에서 이미 확인된 상태만 읽도록 변경했다. 설정값이 바뀌면 이전 확인 결과와 서명이 달라져 `확인 필요`가 된다.
- WordPress 접속 확인 결과는 원문 비밀번호를 저장하지 않는 설정 서명에 연결했다. 같은 설정을 저장했을 때 성공·실패 결과를 Dashboard에 반영하고, 다른 설정이면 기존 결과를 재사용하지 않는다.
- `설정됨`과 `연결 확인됨`을 구분하고, 설정 저장 직후 Dashboard의 5초 조회 제한을 우회해 새 상태를 즉시 반영한다.
- 사용자 재검증에서 WordPress 접속 확인이 연결 성공과 글쓰기 권한을 같은 기준으로 판단해 기존 정상 설정까지 실패시키는 회귀와, 설정의 네이버 확인 직후 Dashboard가 5초 조회 제한으로 이전 상태를 표시하는 불일치를 확인했다.
- 설정의 `접속 확인`은 인증 연결 자체를 확인하고, Blog Beta 발행 preflight는 임시 저장·공개 발행에 필요한 권한까지 확인하도록 역할을 분리했다. WordPress가 capability를 생략해도 표준 역할 정보로 권한을 보완한다.
- 네이버와 WordPress의 설정 확인 성공·실패 직후 Dashboard 조회 제한을 초기화하고 같은 서버 상태를 다시 읽도록 동기화했다.
- 실제 UI 재확인에서 설정의 네이버 확인과 기존 Dashboard 조회가 겹치면 강제 갱신 요청까지 무시되는 경쟁 조건을 확인했다. 진행 중 받은 강제 갱신은 pending으로 합치고 현재 조회 종료 직후 반드시 한 번 더 실행하도록 수정했다.

## Verification Plan

- 네이버 미로그인/만료 상태에서 바로 포스팅을 시도해 입력값과 입력 모드가 유지되는지 확인
- 워드프레스 미설정 상태에서 대상 선택이 제한되는지 확인
- 워드프레스 연결 오류 시 입력값이 유지되고 대상별 안내가 표시되는지 확인
- 정상 연결 상태에서 바로 포스팅이 기존처럼 시작되는지 확인
- 실패한 실행 항목이 대기열에서 다시 실행 가능한 상태로 남는지 확인
- 성공 직전 사용자가 폼을 수정한 경우 새 입력이 초기화되지 않는지 확인

## Manual Checks Still Required

- 사용자가 실제 앱에서 네이버와 WordPress 설정을 정상·오류 값으로 바꾸고 접속 확인 및 Dashboard 상태 동기화를 확인했다.
- 초기 불일치와 WordPress 권한 판정 회귀, Dashboard 강제 갱신 경쟁 조건을 수정한 뒤 최종 UI 동작을 승인했다.
- 실제 발행 서비스의 외부 상태 변화는 계속 발생할 수 있으므로 발행 직전 preflight와 입력 보존 원칙을 유지한다.

## Risks / Follow-up

- 외부 서비스 연결은 사전 검증 직후에도 만료될 수 있으므로 실행 단계의 기존 검증과 실패 보존을 함께 유지해야 한다.
- 실제 네이버·워드프레스 발행은 외부 부작용이 있으므로 자동 테스트는 mock/fixture 중심으로 진행하고 최종 연결·UI 확인은 사용자가 수행한다.
