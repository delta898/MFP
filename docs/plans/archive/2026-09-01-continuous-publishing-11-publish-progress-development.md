# 연속 발행 Stage 11: 발행 진행·결과 표시

## 사용자 필요

Blog Beta의 `바로 포스팅`이나 글감 관리의 즉시 실행을 시작한 뒤, 사용자가 현재 무엇을 처리하고 있는지와 최종 성공·실패를 같은 화면에서 이해할 수 있어야 한다.

## 목표

- 기존 연속 발행 runner의 상태를 사용자 친화적인 진행·결과 표현으로 연결한다.
- 빠른 글 작성과 글감 관리에서 시작한 실행이 같은 상태 표현을 사용하게 한다.
- 진행 중 중복 실행을 막고, 실패 시 글감이 대기열에 남는 기존 안전 동작을 명확히 보여준다.
- 기존 블로그의 발행 로그 경험을 참고하되 Blog Beta에 필요한 최소 UI만 제공한다.

## 명시적 비목표

- 이번 단계에서 미리 보기를 추가하지 않는다.
- 내부 runner 상태명, Sheet 행 번호, API 경로 같은 개발자 정보를 노출하지 않는다.
- 로그 전체를 상시 표시하는 복잡한 콘솔 UI를 만들지 않는다.
- 발행 엔진, 플랫폼별 발행 정책 또는 환경별 안전 정책을 변경하지 않는다.

## 설계 쟁점

- 진행 상태를 어느 화면에 얼마나 오래 보여줄지
- 단계별 진행과 단순 상태 중 어느 수준이 사용자에게 필요한지
- 성공 후 결과 링크, 실패 이유, 재시도 동작의 최소 범위
- 실행 중 사용자가 다른 탭으로 이동한 경우 상태를 어떻게 유지할지

## 구현 단계

1. 기존 runner 상태·polling·legacy 발행 로그 경계 조사
2. 사용자와 최소 진행·결과 UI 합의
3. 공통 상태 표시 구현
4. focused contract 및 browser smoke 검증
5. 사용자 수동 확인 후 기록 최종화

## 진행 기록

- 2026-09-01: Stage 10을 부모 브랜치에 병합한 뒤 Stage 11 브랜치와 개발 기록을 생성했다.

- 2026-09-01: 실행 중에는 빠른 글 작성과 글감 관리의 직접 실행 동작을 함께 비활성화하고, polling 완료 후 Queue를 갱신하도록 기존 흐름을 유지했다.
- 2026-09-01: 진행·완료 상태를 별도 toast로 중복 안내하지 않고 상태 영역 하나로 통합했다.
- 2026-09-01: 바로 생성과 글감 관리의 실행 위치에 공통 상태 바로가기를 추가했다. 자동 이동과 포커스 변경은 도입하지 않았다.
- 2026-09-01: 바로 생성에 빠졌던 `보이지 않게 실행` 선택을 복구하고, 원고 폴더·붙여넣기의 같은 선택과 동기화했다. 실행 옵션은 포스팅 대상과 시각적으로 분리했다.
- 2026-09-01: 첫 browser smoke에서 숨겨진 `상태 보기`까지 버튼 목록에 포함하던 테스트 선택자를 발견해 실제 표시 버튼만 검사하도록 바로잡았다. 두 번째 실행에서는 복수의 선택 행 실행 요청 중 첫 요청을 고르던 검사를 최신 요청 기준으로 수정했다.
- 2026-09-01: 사용자 시각 확인에서 바로 생성 실행 옵션이 기존 필드의 세로 flex 규칙을 상속해 두 줄로 깨지는 문제를 확인했다. 실행 옵션 컨테이너의 가로 정렬과 테두리를 명시하고, 좁은 화면에서만 의도적으로 세로 배치하도록 수정했다.
