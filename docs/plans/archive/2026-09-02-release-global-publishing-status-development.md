## User need and goal

사용자는 어느 메뉴를 보고 있든 Blog Beta의 연속 발행이 실행 중인지, 다음 처리가 예정되어 있는지, 확인할 문제가 있는지를 짧게 인식할 수 있어야 한다. 현재 대시보드 메뉴의 항상 같은 숫자 배지는 의미 있는 변화를 전달하지 못하므로 제거하고, 시간과 활동을 다루는 시계 Widget을 전역 상태의 주 표시 영역으로 활용한다.

## Scope

- 대시보드 메뉴의 의미 없는 고정 추천 개수 배지를 제거한다.
- Blog Beta 연속 발행의 전역 요약 상태를 `확인 필요 > 발행 중 > 다음 처리` 우선순위로 계산한다.
- 시계 Widget에는 가장 중요한 상태 한 건만 간결하게 표시한다.
- 발행 중 또는 확인 필요일 때만 Blog Beta 사이드바에 작은 상태 신호를 표시한다.
- 전역 상태를 누르면 Blog Beta의 글감 관리로 이동한다.
- 실행 완료 후 다음 예약이 있으면 전역 표시가 다음 처리 상태로 전환되도록 갱신한다.

## Non-goals

- 여러 알림을 나열하는 알림 센터나 이력 화면은 만들지 않는다.
- 예약이 있다는 이유만으로 사이드바에 항상 숫자나 점을 표시하지 않는다.
- 글감별 상세 제목, 대기열 전체 개수와 이후 일정을 전역 UI에 노출하지 않는다.
- 쇼핑, SNS, 업데이트와 계정 상태를 이번 단계에서 연결하지 않는다.
- 자동 타이머나 발행 실행 규칙을 변경하지 않는다.

## Proposed design

- 서버 또는 기존 상태 계약에서 전역 표시가 필요한 최소 요약만 제공하고 UI가 여러 상세 응답을 임의 조합하지 않게 한다.
- 시계 Widget은 하나의 상태 chip을 표시한다: `발행 확인 필요`, `발행 중 · 짧은 제목`, `다음 처리 오늘 07:09` 중 하나다.
- 연속 발행이 꺼졌거나 준비 글감과 실행·주의 상태가 없으면 chip을 숨긴다.
- 사이드바는 발행 중에 파란 진행 신호, 확인 필요에 주의 신호만 사용한다.
- 화면이 보일 때와 상태 변화 직후에는 빠르게 갱신하고, 예약 대기 중에는 낮은 빈도로 확인한다.

## Implementation stages

1. 대시보드 배지와 시계·사이드바·runner 상태의 현재 데이터 흐름을 조사한다.
2. 전역 연속 발행 요약 계약과 우선순위 계산을 추가한다.
3. 시계 Widget의 단일 상태 chip과 이동 동작을 연결한다.
4. 사이드바의 최소 실행·주의 신호를 연결한다.
5. 계약, 브라우저 회귀와 사용자 수동 확인 항목을 정리한다.

## Decisions and tradeoffs

- 시계 Widget을 주 정보 영역으로 사용하고 사이드바에는 상세 정보를 중복하지 않는다.
- 한 번에 가장 중요한 상태 하나만 보여 작은 글로벌 영역의 인지 부담을 제한한다.
- 예약 상태는 정상적인 대기 상태이므로 사이드바 신호로 사용하지 않는다.
- `다음 발행` 대신 실제 동작과 맞는 `다음 처리` 표현을 사용한다. 임시 저장이나 플랫폼 예약도 처리 대상이 될 수 있기 때문이다.

## Remaining risks and manual checks

- 장시간 열린 앱에서 예약 상태가 실제 서버 시간 변화와 함께 자연스럽게 갱신되는지는 수동 확인이 필요하다.
- 긴 제목, 작은 창과 각 메뉴 화면에서 Widget 및 사이드바 신호가 레이아웃을 밀지 않는지 사용자 UI 검토가 필요하다.
- 완료·실패 상태의 유지 및 해제 기준이 기존 runner 상태 계약과 일치해야 한다.
