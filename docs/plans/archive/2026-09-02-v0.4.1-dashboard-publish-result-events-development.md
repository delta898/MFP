## Branch

- Branch: `codex/feature/v0.4.1-dashboard-publish-result-events`
- Base/parent branch: `codex/feature/v0.4.1-dashboard-upgrade`
- Start date: 2026-09-02
- Status: 완료

## 사용자 필요와 목표

Dashboard에서 사용자의 실제 작업 성향을 보여줄 수 있도록 네이버와 WordPress의 성공한 발행 결과를 플랫폼 단위로 기록한다. 임시 저장이나 예약 등록도 포함하는 `처리 완료`와 BlogGenius가 실제 공개까지 완료한 `공개 발행`을 구분해 후속 기간 통계의 신뢰할 수 있는 근거를 만든다.

## 범위

- 기존 발행 경로와 결과 저장 경계 조사
- 네이버·WordPress 플랫폼별 성공 결과 이벤트의 최소 계약
- 공개 발행, 예약 등록, 임시 저장 결과의 명시적 구분
- 중복 재시도에서 같은 플랫폼 결과를 이중 집계하지 않는 식별 규칙
- 현재 저장 구조에 맞는 이벤트 기록소와 조회 경계
- focused unit/contract test와 canonical 문서 현행화

## 명시적 비범위

- Dashboard 통계 카드와 최근 결과 UI
- 오늘·이번 주·최근 30일 집계 표현
- 네이버·WordPress에서 사용자가 나중에 직접 공개한 결과의 추정
- 조회수, 방문자, 검색 순위 등 외부 분석 데이터
- release, version, push 또는 배포

## 제안 설계

- 통계는 글감 행 수가 아니라 성공한 플랫폼 결과 수를 기준으로 한다.
- 하나의 작업이 네이버와 WordPress에서 각각 성공하면 결과 이벤트도 2건이다.
- 결과 이벤트는 사실 기록이며, 기간별 통계는 이 사실에서 파생한다.
- 발행 요청의 의도와 실제 성공 결과를 함께 기록해 `처리 완료`와 `공개 발행`을 결정론적으로 구분한다.
- 재시도 및 부분 성공 흐름에서는 기존 operation/platform 식별자를 우선 재사용해 중복 기록을 방지한다.
- 실패 결과는 성공 통계에 포함하지 않으며, 기존 사용자 입력과 마지막 유효 상태 보존 원칙을 바꾸지 않는다.

## 사용자와 결정한 사항

- `처리 완료`와 `공개 발행`은 반드시 함께 제공한다.
- 임시 저장 중심 사용자에게 공개 발행 0건만 보여주지 않고 실제 처리 활동을 함께 보여준다.
- 두 지표는 글감 행이 아니라 성공한 플랫폼 결과를 센다.
- 네이버와 WordPress가 모두 성공하면 2건이다.
- `처리 완료`에는 공개 발행, 예약 등록, 임시 저장 성공이 포함된다.
- `공개 발행`에는 BlogGenius가 실제 공개 발행까지 성공한 결과만 포함한다.

## 구현 단계

1. 기존 publish coordinator, operation ledger, 플랫폼 adapter와 저장소 경계 조사
2. 이벤트 스키마와 중복 방지 키 결정
3. 성공 결과 기록 및 조회 경계 구현
4. 부분 성공·재시도·발행 옵션별 focused test
5. canonical architecture/decision 문서와 parent 기록 현행화

## 진행 및 변경 기록

- 2026-09-02: Dashboard parent에서 플랫폼 발행 결과 이벤트 계약 sub-feature를 시작했다.
- 2026-09-02: 기존 publish coordinator와 owner activity lifecycle을 조사했다. 공개·임시 저장 성공은 이미 공통 기록 경계를 사용하지만 예약 성공은 기록되지 않는 것을 확인했다.
- 2026-09-02: 별도 통계 저장소를 만들지 않고 lifecycle에 `scheduled` stage를 추가했다. 성공한 네이버·WordPress 결과만 플랫폼별 사실로 만들며 operation/domain/platform/stage 조합을 안정적 evidence id로 사용한다.
- 2026-09-02: 다음 통계 단계가 기존 draft/publish 사실과 새 schedule 사실을 같은 규칙으로 읽도록 저장 이벤트 검증·정규화 계약을 추가했다. 처리 완료·공개 발행 여부는 저장된 임의 boolean이 아니라 검증된 stage에서 파생한다.

## 최종 결과 및 검증

- 성공한 플랫폼별 발행 결과를 `drafted`, `scheduled`, `published` lifecycle 사실로 기록한다.
- 실패한 플랫폼과 지원하지 않는 플랫폼은 성공 사실에서 제외한다.
- 기존 operation/domain/platform/stage 조합으로 재시도 시 같은 사실이 중복 저장되지 않는다.
- 기존 draft/publish 이벤트도 새 통계 계약에서 읽을 수 있도록 정규화한다.
- focused memory/publishing test 26개 통과.
- parent merge 전 전체 단위 테스트 1,270개 통과.
- UI 변경이 없어 별도 사용자 화면 확인은 필요하지 않다.
- 과거 Sheet 상태를 역으로 이벤트화하는 backfill은 수행하지 않는다.
