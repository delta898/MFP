# v0.4.3 Persistent License Storage Development Record

## Branch
- Branch: `codex/fix/v0.4.3-persistent-license-storage`
- Base/parent branch: `release/v0.4.3`
- Start date: 2026-09-06
- Status: complete; automated verification passed and parent merge approved

## User Need
An extracted or newly installed BlogGenius version must retain the user's license without copying configuration from the previous application folder. The current portable-first layout stores `license.key` beside the application, so a new version folder can lose the license context and fail to show the existing plan.

## Goal
Store the license key in Electron's persistent per-user data directory while preserving environment-specific key separation and safely adopting an existing legacy key on first launch.

## Scope
- Resolve a persistent per-user license path when Electron supplies its `userData` directory.
- Continue to separate local, development, and production license filenames.
- Read the persistent key first.
- Fall back to the existing application/config key and migrate it to persistent storage when possible.
- Write newly issued, registered, or recovered keys to persistent storage.
- Add focused path, migration, and license-loading tests.
- Update maintained license documentation.

## Explicit Non-goals
- Do not move `config.json`, OAuth files, logs, workspaces, or generated content in this stage.
- Do not add or redesign the email recovery UI.
- Do not change licensing plans, quotas, server RPC policy, or device identity rules.
- Do not remove legacy key files automatically.

## Proposed Design
Treat the Electron `userData` directory as the durable owner of the active license key. Keep the package-local key as a legacy import source only. Resolution and migration will live behind a small shared path/storage boundary so callers continue to use the existing license API rather than knowing platform paths.

When no Electron user-data path is available, such as ordinary CLI development, preserve the current runtime-root behavior. This avoids unexpectedly sharing development credentials with the packaged production app.

## Affected Boundaries
- Electron bootstrap environment
- configuration path resolution
- license key loading and persistence
- release packaging/update behavior
- license operations and development documentation

## Decisions and Tradeoffs
- Move only the license key because it is the minimum durable identity required to restore plan visibility across application versions.
- Prefer migration-by-copy and retain the legacy file. Automatic deletion would make rollback harder and is unnecessary.
- Keep environment-specific filenames to prevent local/development credentials from replacing production credentials.
- Email recovery remains necessary when neither persistent nor legacy storage contains a key.

## Implementation Stages
1. Extract deterministic persistent and legacy license path resolution.
2. Load persistent-first and migrate a valid legacy key.
3. Persist all newly obtained keys to the durable path.
4. Add focused automated coverage and update documentation.

## Verification Plan
- Unit-test production Electron user-data resolution on macOS/Windows-neutral paths.
- Unit-test persistent precedence, legacy fallback, migration success, and safe migration failure.
- Run focused configuration and license tests.
- Run the relevant packaged/runtime contract tests.
- Leave final packaged upgrade verification to the user after implementation.

## Current Risks
- Existing installations may contain keys in several legacy candidate paths.
- A read-only or unavailable user-data directory must not prevent the current process from using a valid legacy key.
- Development and production keys must remain isolated.

## Final Result
Electron runs now keep environment-specific license keys under the app-specific persistent user-data directory. Installing or extracting a later BlogGenius version therefore reuses the same key and restores plan information without copying `config.json`. An existing key in the currently launched legacy application folder is adopted once and retained for rollback. If neither location has a key, the existing test issuance or email recovery policy still applies; this change does not infer or expose a license from HWID alone.
