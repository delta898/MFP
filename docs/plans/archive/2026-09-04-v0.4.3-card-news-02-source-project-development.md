# v0.4.3 Card News Stage 02 Source and Project Development Record

## Branch
- Branch: `codex/feat/v0.4.3-card-news-02-source-project`
- Base/parent branch: `codex/feat/v0.4.3-card-news-main`
- Start date: 2026-09-04
- Status: completed and merged to parent

## User Need
Users need a reliable starting point for card news: select a currently public article from a configured blog feed, enter a normal public URL, or paste a manuscript. Their selection and later generated work must belong to a durable project instead of disappearing when retrieval or generation fails.

## Goal
Build the provider-neutral source and project foundation behind the future Card News screen. Normalize the three source paths into one snapshot, preserve provenance, and define durable project state that can later accept outlines, generated cards, exports, and delivery results.

## Scope
- Discover articles through configured Naver and WordPress feeds by reusing the existing feed boundaries.
- Resolve a selected feed item or direct public URL into a bounded article snapshot.
- Accept pasted manuscript text without a network dependency.
- Create and update durable card-news project records.
- Preserve the last valid source snapshot and generated state when a refresh fails.
- Add focused unit tests with fixtures and injected dependencies.

## Explicit Non-goals
- No user-facing Card News screen in this stage.
- No image-model calls or card rendering.
- No Drive upload, Buffer publishing, or production mutation.
- No authenticated or anti-bot page scraping.
- No deterministic text renderer.

## Proposed Design
- Keep source discovery, public-document retrieval, and project persistence as separate capabilities.
- Represent configured feeds and direct URLs with the shared source contract from stage 01.
- Store fetched title, body, excerpt, canonical URL, attribution, and retrieval time as a source snapshot while retaining feed identity separately.
- Use dependency injection for feed discovery, document retrieval, clock, identifiers, and persistence so tests remain local and deterministic.
- Treat project updates as immutable state transitions and retain the previous valid snapshot on dependency failure.

## Affected Boundaries
- `src/card-news/` for domain contracts, source orchestration, and project state.
- Existing RSS and hardened public-document retrieval modules only through reusable public interfaces; avoid provider-specific branches inside the card-news project model.
- A local repository boundary chosen after auditing existing workspace persistence conventions.

## Decisions and Tradeoffs
- RSS discovers what is publicly published, but the article URL supplies the current full body.
- Manuscripts are first-class sources rather than simulated URLs.
- Project durability is required before UI and image generation so later failures cannot erase user work.
- Existing hardened URL safety rules must be reused or extracted; a weaker card-news-only fetcher is not acceptable.

## Implementation Stages
1. Audit current feed, public-document, and local persistence interfaces.
2. Add source orchestration and normalized snapshots with focused tests.
3. Add durable project state/repository and failure-preservation tests.
4. Update parent documentation and report the next UI-facing slice.

## Remaining Risks
- Existing article extraction may be too coupled to writing-style analysis and need a small shared infrastructure extraction.
- Feed summaries may omit content, requiring a visible retrieval failure state rather than silently producing weak projects.
- Local project storage must follow the packaged application workspace conventions on macOS and Windows.
- The user-facing Card News screen still needs source selection, preview, and project reload controls before manual UI validation is meaningful.

## Final Result
Stage 02 added the local source and durable project foundation for Card News. Configured blog feeds, direct public URLs, and pasted manuscripts now normalize into durable source snapshots; project refreshes preserve the last valid source, cards, and assets when retrieval fails; and local JSON persistence stores card-news projects atomically under the application workspace.
