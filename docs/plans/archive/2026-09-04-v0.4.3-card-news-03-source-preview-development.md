# v0.4.3 Card News Stage 03 Source Preview Development Record

## Branch
- Branch: `codex/feat/v0.4.3-card-news-03-source-preview`

- Start date: 2026-09-04
- Status: in progress

## User Need
Users need to start a card-news project from a source they can understand before any image generation cost or long-running AI work begins. The first UI slice should make the source choice clear, preview the captured content, and preserve the project for the next stage.

## Goal
Expose the stage 02 source foundation through a small Card News surface and local API boundary. Users should be able to choose a configured blog article, enter a public URL, or paste a manuscript and confirm the resolved source without being asked to create or manage a project.

## Scope
- Add a Card News top-level navigation entry and view shell.
- Add a local Card News API for configured source discovery and source confirmation; retain internal project create/list operations as generation-stage groundwork without exposing them as a user step.
- Resolve a selected blog row immediately; keep an explicit confirmation action only for URL and direct-input modes before later generation.
- Show friendly empty and failure states without clearing the user's current input.
- Add focused service, route, and UI structure tests.

## Explicit Non-goals
- No card outline generation or image generation.
- No local image export, Google Drive archive, Buffer publishing, or SNS account integration.
- No authenticated page scraping or anti-bot bypass.
- No production or remote database mutation.
- No release version bump.

## Proposed Design
- Build a `card-news.service` under `src/ui-api/services/` that wires the stage 02 source/project modules to existing config, RSS, and workspace conventions.
- Add controller and route modules under the existing UI API boundary.
- Add `view-card-news` as a compact workflow: content type selector, content input area, and selected-content panel.
- Use simple UI copy that reflects the user's mental model: "내 블로그 글", "URL", and "원고".
- Preserve source input and any last valid preview if a refresh fails.

## Affected Boundaries
- `src/ui-api/services/`, `controllers/`, and `routes/` for the local API boundary.
- `ui/index.html`, `ui/app.js`, `ui/partials/views/`, `ui/scripts/features/`, and `ui/styles/features/` for the first visible surface.
- `scripts/` UI contract tests for navigation, shell composition, and API routing.
- Parent and stage development records.

## Decisions and Tradeoffs
- This stage intentionally stops before AI generation so the user can validate whether the source workflow feels right.
- The configured blog path is RSS-first because public RSS reflects only publicly published posts.
- Direct URL input remains public-only; failed extraction should be visible and recoverable.
- Blog rows resolve immediately because this is a read-only network lookup with no AI cost. URL and direct-input modes retain an explicit `내용 확인` action so typing does not trigger premature requests.
- The existing hardened HTTPS page extractor is reused through a Card News adapter. Its security limits remain shared while Card News presents feature-specific error wording.
- Recent projects expose only a compact summary in the UI API; the full source snapshot remains in the local workspace store for the later generation stage.
- The durable `project` remains an internal recovery and automation concept. User-facing copy uses `작업`, and the visible workflow is `원문 선택 → 원문 확인 → 카드 설정 → 만들기 → 결과`.
- `미리보기` is reserved for generated Card News results. Source retrieval uses `원문 확인` and the result panel is named `선택한 원문` to avoid implying that cards already exist.
- A separate Settings > Card News page is deferred. The generation stage will expose only essential settings in the workflow and preserve the most recently used values locally; automation will later own an explicit preset rather than borrowing transient manual UI state.
- Source confirmation does not create a user-visible work item. The internal project record will be created automatically when the user actually starts Card News generation, so recovery architecture does not add a product step.
- Blog-row lookups are cached for the current session, and overlapping requests use last-request-wins behavior so rapid selection cannot replace the newest choice with an older response.
- A generated-history surface remains optional future work. If introduced, it should list source identity and generated Card News result links rather than expose empty source-selection drafts.
- When both Naver and WordPress are configured, their articles are separated into compact platform tabs with counts; a single configured platform skips the redundant tab control. The last selected platform is remembered locally.
- Source refresh uses the established circular refresh-icon pattern and keeps the active platform while both feeds refresh. A failure is presented within the affected platform instead of hiding healthy results from the other source.
