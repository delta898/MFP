## 사용자 필요

Stage 6에서 저장한 연속 발행 정책이 실제로 한 건씩 동작해야 한다. Production에서만 시험할 수
있는 구조는 개발 효율이 지나치게 낮으므로 Local과 Development에서도 환경에 맞는 안전한 검증
경로가 필요하다.

## 목표

- 저장한 허용 시간대와 최소 간격에 따라 가장 오래된 준비 글감 한 건을 실행한다.
- 한 앱 프로세스에서는 실행이 겹치지 않게 한다.
- Local에서는 외부 플랫폼을 변경하지 않는 시뮬레이션만 수행한다.
- Development에서는 `임시 저장` 계획만 자동 실행하고 공개·예약 발행은 차단한다.
- Development에서 기다리지 않고 확인할 수 있도록 `30초 후 1회 자동 실행 테스트`를 제공한다.
- Production은 글감별 발행 계획을 그대로 따르되 기존 환경 권한을 우회하지 않는다.

## 명시적 비목표

- Supabase claim·lease 또는 여러 기기간 중복 실행 조정은 구현하지 않는다.
- 사용자가 여러 기기에서 동시에 자동 실행을 켠 상황을 시스템이 조정하지 않는다.
- 무제한 자동 재시도, Trends/RSS 자동 승격과 기존 자동 포스팅 대체는 포함하지 않는다.
- 자동화 검증에서 실제 AI 호출, 원격 발행 또는 원격 데이터 변경을 수행하지 않는다.

## 승인된 결정

1. 일반 자동 실행 최소 간격은 10분을 유지한다.
2. 단일 활성 기기 사용을 제품 원칙으로 두며 다중 기기 충돌은 사용자 책임으로 명시한다.
3. Local은 Queue 선두를 확인하되 상태 변경, AI 생성과 플랫폼 작업을 하지 않는다.
4. Development 자동 실행은 `draft`만 허용한다. `publish`와 `schedule`은 실행하지 않고 사용자 확인이 필요한 이유를 표시한다.
5. 30초 시험 실행은 설정을 바꾸지 않는 일회성 동작이며 Development의 동일한 `draft` 전용 제한을 따른다.
6. 앱 재시작 시 지난 실행을 따라잡지 않고 현재 시각에서 다음 허용 시각을 다시 계산한다.

## 설계

- 환경 manifest에 수동 발행, 전체 자동 발행과 구분되는 `자동 임시 저장` capability를 둔다.
- in-process scheduler가 로컬 설정을 읽고 timer를 예약하며 기존 FIFO 단건 runner를 자동 실행 모드로 호출한다.
- 기존 runner promise를 공통 배타 경계로 사용해 수동 실행과 자동 실행이 겹치지 않게 한다.
- scheduler 상태와 다음 실행 시각은 API로 노출하고 설정 화면에서 환경별 실제 동작을 설명한다.
- 테스트는 가짜 clock/timer와 실행기 fixture로 시간대, FIFO 위임, 환경 차단과 중복 실행을 검증한다.
