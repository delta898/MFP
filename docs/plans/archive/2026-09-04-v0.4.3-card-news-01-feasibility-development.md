# v0.4.3 Card News Stage 01 Feasibility Development Record

## Branch
- Branch: `codex/feat/v0.4.3-card-news-01-feasibility`
- Base/parent branch: `codex/feat/v0.4.3-card-news-main`
- Start date: 2026-09-04
- Status: completed; merged-candidate verification finished and external transport PoC deferred

## User Need
Before building the card-news UI and generation pipeline, verify the existing BlogGenius boundaries and the external constraints that determine whether source retrieval, local export, Google Drive archival, and optional Buffer multi-image publishing can be implemented without brittle coupling.

## Goal
Produce tested internal contracts and an evidence-backed recommendation for the first implementation slice. Keep the work non-publishing and non-destructive unless the user later approves a bounded remote PoC.

## Scope
- Audit configured-blog and RSS retrieval paths.
- Audit public URL extraction and define the supported failure boundary.
- Audit current Google OAuth scopes and Drive file capabilities.
- Audit the current Buffer request model and define an ordered multi-asset contract.
- Confirm that complete-card AI output can remain independent from a future deterministic rendering capability.
- Define a channel capability matrix for card count, asset requirements, and distribution transformations.
- Add focused automated contract tests where behavior can be proven locally.
- Record which remaining questions require a real external compatibility test.

## Explicit Non-goals
- No user-facing card-news UI in this stage.
- No production schema or hosted service changes.
- No real SNS publication.
- No public sharing of user Drive files without explicit approval for a bounded test.
- No final commitment to Google Drive, WordPress, or application-owned storage as the publishing transport.

## Proposed Design

### Feasibility Outputs
The stage should finish with:
- source snapshot contract
- ordered card asset contract
- storage versus publishing-transport capability boundary
- platform capability matrix with safe validation defaults
- initial AI rendering recommendation and the boundary for a future deterministic renderer
- a list of externally testable hypotheses and cleanup requirements

### External PoC Gate
Any later live test must specify:
- exact development account and channel
- temporary files created
- whether files become publicly readable
- whether a post is created or only a Buffer draft/request validation is used
- cleanup and recovery procedure

## Decisions and Tradeoffs
- RSS is authoritative for the currently public article list, while the selected canonical URL is used to retrieve full current text.
- Public URL extraction intentionally excludes authenticated or protected pages.
- Local export is independent from automatic distribution and therefore requires no public URL.
- Complete-card AI generation is the initial default. Semantic copy remains separate for card-level revision and regeneration; deterministic text composition is deferred.
- Google Drive is expected to be suitable for user-owned archival; its public-link suitability for Buffer remains unproven.
- Direct Meta integration does not remove public media URL requirements and is outside this stage.

## Manual Checks Still Required
None yet. Any proposed external compatibility check will be handed to the user for approval before execution.

## Remaining Risks
- External API behavior may differ from static documentation.
- Google Workspace policies may prevent public Drive sharing for some users.
- A URL accepted by Buffer may still be rejected later by an individual SNS platform.
- Packaged application fonts and native image dependencies may differ by OS.
- The existing Google OAuth default includes `drive.file`, which is suitable for files created by BlogGenius, but Drive public-link compatibility with Buffer remains an external hypothesis.

## Final Result
Local feasibility is established for configured RSS sources, bounded public URL retrieval, manuscript input, complete-card AI generation, ordered local assets, Google Drive archival permission, and provider-neutral delivery validation. The next reviewable stage can build the source and project foundation without depending on Buffer, a public asset host, or a deterministic font renderer. Drive public-link compatibility remains an explicit pre-publishing PoC rather than an assumption in the core design.
