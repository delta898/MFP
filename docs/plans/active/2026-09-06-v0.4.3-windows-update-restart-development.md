# v0.4.3 Windows Update Restart Development Record

## Branch
- Branch: `codex/fix/v0.4.3-windows-update-restart`
- Base/parent branch: `release/v0.4.3`
- Start date: 2026-09-06
- Status: in progress

## User Need
On Windows, self-update downloads, verifies, and extracts the release successfully. After the restart message, BlogGenius closes but does not reopen. The expected helper log is also absent, even though the main log claims that the helper is ready.

## Goal
Make Windows deferred update restart fail-safe: confirm that the external helper actually starts before terminating BlogGenius, preserve useful startup diagnostics, then let the helper replace files and relaunch the updated executable.

## Scope
- Separate Windows helper script preparation from process launch.
- Launch the helper only when restart is requested.
- Confirm child-process spawn before exiting the current app.
- Preserve bootstrap errors instead of discarding helper stdout/stderr.
- Keep existing file preservation, replacement, and relaunch behavior.
- Add focused updater tests for success and failure paths.

## Explicit Non-goals
- Do not replace the ZIP-based updater or introduce an installer framework.
- Do not change release discovery, download, or SHA-256 verification.
- Do not change macOS or Linux restart behavior beyond shared seams needed for testing.
- Do not publish a new dev build in this branch.

## Proposed Design
`prepareWindowsDeferredApply` writes the PowerShell script and stores all invocation metadata without launching it. `restart` launches the helper, waits for the Node child-process `spawn` event, and only then invokes the process-exit callback. Startup errors reject the restart and keep BlogGenius alive. Helper stdout/stderr are redirected to a bootstrap log beside `apply-update.log`, covering failures that occur before the script's own logger starts.

PowerShell selection prefers the standard Windows PowerShell executable and may fall back to `pwsh` when appropriate. The generated helper continues to wait for the current PID, replace only non-preserved application files, and relaunch the exact executable path.

## Affected Boundaries
- `src/updater.js`
- updater unit tests
- update restart API error propagation
- Windows packaged runtime only

## Decisions and Tradeoffs
- The app must not exit on an unconfirmed helper launch; a failed restart is recoverable while the current process remains alive.
- Preparation logs must distinguish script creation from successful helper launch.
- Early diagnostics use a separate bootstrap log because `apply-update.log` cannot capture failures before PowerShell enters the script.

## Implementation Stages
1. Extract helper invocation metadata and deferred launcher.
2. Make restart asynchronous and exit only after confirmed spawn.
3. Propagate launch failure through the restart endpoint.
4. Add focused tests for helper preparation, successful launch, and failed launch.

## Verification Plan
- Unit-test that preparation performs no child-process launch.
- Unit-test that successful spawn triggers exit only afterward.
- Unit-test that spawn failure does not trigger exit and yields a diagnostic error.
- Run updater and system controller focused tests.
- Run the relevant UI/browser smoke if restart endpoint behavior changes the client contract.

## Progress
- 2026-09-06: user reproduced the issue on Windows: the app closed, did not relaunch, and produced no `apply-update.log`.
- 2026-09-06: diagnosis identified that the old code logged helper readiness without observing the child `spawn` or `error` event and discarded all startup diagnostics.
- 2026-09-06: moved helper launch from update preparation to the restart request and added an explicit PowerShell readiness marker.
- 2026-09-06: added standard Windows PowerShell path discovery with command-name and `pwsh.exe` fallbacks, plus `apply-update-bootstrap.log` for failures before the helper script logger starts.
- 2026-09-06: changed the restart endpoint to wait for helper readiness before returning success. Launch failure now returns an API error and keeps the current BlogGenius process alive.
- 2026-09-06: added focused success/failure tests with injected Windows process boundaries.
