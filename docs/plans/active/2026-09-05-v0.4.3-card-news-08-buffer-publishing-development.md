# v0.4.3 Card News Stage 08 Buffer Publishing Development Record

## Branch

- Branch: `codex/feat/v0.4.3-card-news-08-buffer-publishing`
- Base/parent: `codex/feat/v0.4.3-card-news-main`
- Start date: 2026-09-05
- Status: implementation complete; awaiting user UI and live-publication acceptance

## User Need

Allow a completed, ordered card-news image set to move naturally from local creation into the user's configured Buffer channels without losing ordering, hiding platform limitations, or risking duplicate publication.

## Goal

Verify Buffer's current multi-image publishing contract and add the smallest safe publishing boundary that reuses the existing Buffer connection and result-reconciliation behavior.

## Scope

- Inspect the existing Buffer gateway, manual SNS flow, entitlement checks, and reconciliation behavior.
- Verify the current official Buffer API contract for ordered multi-image posts and supported channels.
- Define a card-news delivery request with ordered assets, target channels, validation, and explicit results.
- Preserve the completed local card-news result when publishing validation or an external request fails.
- Add focused automated tests before any user-authorized live publishing check.

## Explicit Non-goals

- No real SNS publication or production mutation without explicit user approval.
- No automatic RSS-triggered publishing in this stage.
- No Google Drive archive unless the selected Buffer transport demonstrably requires and supports it.
- No direct Instagram, Threads, Bluesky, or other provider-specific authentication path.
- No broad redesign of the existing SNS surface.

## Proposed Design

1. Treat card-news generation, asset transport, and Buffer publication as separate capabilities.
2. Extend the existing Buffer gateway only if the official API accepts an ordered multi-image payload using externally reachable asset URLs.
3. Keep asset hosting behind a transport interface so WordPress temporary media, application-owned storage, or another verified implementation can be selected without changing the card-news domain model.
4. Validate channel capabilities before confirmation and reject unsupported combinations with an actionable explanation.
5. Reuse the existing publish reconciliation rules for timeout, duplicate, and ambiguous results.

## Implementation Stages

1. Verify official API and inspect existing boundaries.
2. Define capability and ordered-asset contracts with fixtures.
3. Implement the smallest safe gateway/service path supported by the evidence.
4. Add a confirmation-oriented UI only after the backend contract is stable.
5. Run focused tests and hand off manual checks; keep live publication out of automated verification.

## Decisions and Tradeoffs

- 2026-09-05: local ZIP export remains a complete product outcome; Buffer is an optional next action.
- 2026-09-05: Google Drive is not assumed to be a public-media transport merely because Google integration already exists.
- 2026-09-05: Google Drive ACLs can keep upload, modification, and deletion under the authenticated owner/application while granting anonymous read access with `type=anyone` and `role=reader`. Buffer compatibility still depends on the resulting browser download URL returning the image bytes directly without authentication.
- 2026-09-05: real publication is excluded from normal verification because it has external side effects and is non-idempotent.
- 2026-09-05: Buffer's current GraphQL API accepts an ordered `assets` list but has no file-upload endpoint. Every asset must be a public, direct, stable HTTPS URL that remains available until publication. Google Drive preview/share links and expiring signed URLs are therefore not used as transport. Evidence: [Create Image Post](https://developers.buffer.com/examples/create-image-post.html), [Hosting Media](https://developers.buffer.com/guides/hosting-media.html).
- 2026-09-05: the first transport reuses the existing WordPress temporary-media path. Users without WordPress retain the complete local ZIP workflow; adding application-owned public storage would require separate privacy, retention, and cost decisions.
- 2026-09-05: channel image-count validation follows Buffer's published network limits before any upload. Card order remains the generated manifest order. Evidence: [Attaching media](https://support.buffer.com/en-us/articles/attaching-images-videos-and-other-media-to-your-posts-eudySt0TnS).
- 2026-09-05: PNG, JPG, and WebP are accepted for the card-news publishing path. AVIF remains valid for local export but is rejected before remote upload because Buffer does not list it as a supported upload type.
- 2026-09-05: a 9:16 card set is rejected for Instagram carousel publishing; the user can create a 1:1 or 4:5 set or use the local download path.
- 2026-09-05: the existing card-composition AI call also proposes one concise, platform-neutral SNS caption and three to five relevant hashtags. The application, not the model, appends the verified source URL so it cannot be invented, changed, or omitted. Users receive the combined text in one editable field; direct manuscripts simply omit the unavailable link.
- 2026-09-05: Buffer remains an implementation detail in the primary action language. The result surface uses `SNS 발행`, changes the action to a disabled `발행 완료` after confirmed success, distinguishes accepted-but-not-yet-confirmed requests, and limits partial retry to channels that did not succeed.

The temporary file was deleted immediately after verification. This proves Drive is a viable transport candidate for immediate Buffer publication, subject to a real Buffer fetch check and lifecycle cleanup rules.
