## User Need

Users should be able to treat RSS as a Card News content source rather than as an automatic publishing rule. Connected Naver and WordPress blogs are convenient default feeds, and users can add other public feeds, choose an article, create cards, and publish them manually.

## Goal and Proposed Scope

- Use configured Naver and WordPress RSS as default sources while allowing either source to be excluded from Card News.
- Register up to 20 additional public HTTPS RSS sources with a user-facing name and enabled state.
- Present enabled feeds as named source tabs in the existing Card News selection flow.
- Run only while the desktop app is running.
- Add only previously unseen public articles to the `cardnews` Sheet.
- Treat `entry_key` deduplication as the boundary that protects existing ledger rows.
- Avoid a Sheet write when a feed contains no new entries.
- Batch multiple newly discovered entries into as few Google API requests as practical.
- Preserve the last successful local/feed state when RSS or Google Sheets is temporarily unavailable.
- Make collection lifecycle and failures observable in logs without turning routine polling into noisy user-facing alerts.

## Explicit Non-goals

- No automatic card composition or image generation.
- No scheduled or automatic SNS publication.
- No source-triggered card creation or publication.
- No always-on cloud worker while the desktop app is closed.
- No rewriting, reconciling, or resetting existing ledger rows from repeated RSS results.
- No ZIP import or WordPress-independent public asset transport in this stage.
- No schedule, reservation queue, cadence controls, or periodic SNS publishing.

## Decisions Already Made with the User

- Re-reading RSS must add only new articles; an existing ledger row remains untouched.
- User-managed workflow and publishing states must survive every later RSS scan.
- The management Sheet is an index and control ledger; images, prompts, and detailed generation state remain local.
- Google API rate limits matter. Polling and Sheet mutation must be separated so an unchanged feed causes no write.
- Keep this stage limited to intake. Scheduling follows only after intake, restart recovery, and duplicate prevention are proven.
- Discuss and agree on the operating policy before material implementation.
- The final user flow for this slice is `RSS 등록 → 목록 → 제작 → 수동 발행`; periodic publishing is a separate future decision.
- Source enable/disable controls affect only Card News listing and intake. They never authorize creation or publishing.

## Proposed Design Boundary

1. A single lifecycle-owned collector obtains configured feed sources after app readiness.
2. Feed reads produce normalized ledger candidates using the existing `entry_key` rules.
3. The collector compares candidates with known ledger identities without modifying matching rows.
4. Unseen candidates are appended in one bounded batch operation where possible.
5. A failed read or append retains the last valid state and is retried according to an agreed backoff policy.
6. Collection stops with the app; no external scheduler is implied.
7. The settings surface stores only built-in source selection plus custom feed name, HTTPS URL, and enabled state.

## Agreed Operating Policy

- Wait one minute after UI server readiness before the first collection, then collect every 30 minutes while the app remains running.
- Scan Naver and WordPress independently so one feed failure does not hide healthy results from the other.
- Let each feed expose its available window and send the combined result through one ledger upsert batch.
- Do not introduce a separate retry queue in this stage. Preserve current state and retry at the next regular interval.
- Keep routine collection out of the UI. Log new-row additions and partial/fatal failures without logging unchanged scans.
- Keep manual source refresh as both a source-list refresh and ledger intake through the existing synchronization boundary.

## Alternatives and Tradeoffs

- A short fixed interval discovers posts sooner but adds needless RSS traffic and increases correlated retries after network recovery.
- Immediate startup collection feels responsive, but it competes with the app's existing startup checks; a small readiness delay may reduce the noisy startup experience.
- Writing every scan makes synchronization simple but wastes Google API quota. Identity comparison followed by append-only writes is preferred.
- A UI-configurable interval adds flexibility but expands settings and validation before there is evidence users need it.
- Cloud scheduling would work while the app is closed but introduces deployment, credentials, ownership, and operating-cost decisions beyond this stage.
- A single unified source record for built-in and custom feeds would look architecturally neat, but it would duplicate credentials and connection ownership. Built-in selection and custom RSS registration therefore remain separate configuration fields and converge only in feed discovery.

## Implementation Result

- Added one shared bounded RSS fetcher for both interactive Card News source discovery and background intake.
- Added an overlap-safe intake service that skips all work until Google Sheets is configured, accepts partial feed success, and sends discovered items through one existing ledger batch.
- Added an app-lifetime scheduler with a one-minute initial delay and a 30-minute recurring interval.
- Connected scheduler start to UI server readiness and stop/restart to UI server reload so configuration reloads do not duplicate timers.
- Kept unchanged-feed scans free of Sheet writes; the ledger store reads identities and appends only unseen rows while leaving every existing field untouched.
- Added a minimal Card News settings tab for independently enabling connected Naver/WordPress feeds and registering named custom HTTPS RSS sources.
- Unified built-in and custom feeds behind one source definition boundary while preserving legacy item identities for existing Naver/WordPress ledger rows.
- Updated the Card News source selector to show each enabled feed by name and kept creation and SNS publication explicitly manual.
