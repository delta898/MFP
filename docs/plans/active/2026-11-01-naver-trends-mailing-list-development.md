## User need

The user wants to offer a daily Naver Trends email to people who subscribe by topic category, with useful verified links and a working unsubscribe path.

## Goal and scope

Explore and implement an end-to-end, low-operator-intervention daily Naver Trends mailing flow that reuses the existing trends collection pipeline, manages subscriber preferences and consent, prepares a useful email with verified links, delivers it quickly after collection, and honors unsubscribes automatically.

The initial rollout may use operator review during testing, but the intended steady state is fully automatic from signup through delivery and unsubscribe. The user prioritizes fast delivery after Naver's previous-day results refresh around 07:30 and wants to avoid omissions caused by human availability or forgetfulness.

This implementation slice covers first-party signup intake, category preferences, explicit consent, double opt-in, and unsubscribe state changes. Daily campaign generation, scheduled dispatch, link verification, delivery recovery, and monitoring remain future stages of the overall feature.

## Explicit non-goals

- No production mailing, subscriber import, or external service mutation without explicit scope and approval.
- No changes to the existing Blog UI unless explicitly requested; the default Blog surface policy remains in force.
- No release/version changes, commit, merge, push, or deployment as part of feature setup.

## Proposed design

The public site submits to the existing Trends Worker, which validates and forwards to a dedicated Supabase Edge Function. Supabase schema `mailing` is the canonical subscriber store; Brevo sends confirmation email. Double opt-in is required, raw action tokens are never stored, and unsubscribe requests mutate the canonical status. Keep this workflow separate from license mail and trend data APIs. Campaign dispatch is explicitly outside this implementation slice.

The next stage uses an authenticated date-specific signal from the Development collector after a successful trends upsert. A private Cloudflare Workflow re-reads the matching Development Supabase data and records collection readiness. This is event-triggered because scheduled Workflow triggers are unavailable on the current Cloudflare plan. Future stages separately create and approve a common dated edition, add only AI-written greeting/brief introduction, select a limited set of links deterministically from verified records, build each active subscriber's category-specific content, and deliver with per-date/per-subscriber idempotency. The shared edition is public-archive material; individualized recipient sections remain private. A Telegram summary reports completion and actionable failures. See [Naver Trends Newsletter Automation](../../architecture/trends-newsletter-automation.md) for the full flow, cost notes, environment boundaries, and remaining decisions.

## Affected boundaries and stages

Current Production topology runs the Playwright Trends Collector on the operator Mac Studio and the Trends API on Cloudflare Workers. The production collector requires `--confirm-production` for noninteractive writes. Reliable unattended campaign delivery still needs collection scheduling, completion/quality checks, retries, delivery idempotency, and recovery. This stage implements only subscriber lifecycle endpoints and does not claim the daily mailing loop is complete.

- User chose double opt-in for the website signup: a confirmation email link must be clicked before a new or reactivated subscription becomes active.
- Delivery should follow quickly after the previous day's Naver Trends refresh, which typically occurs around 07:30.
- Signup/subscriber design recommendation: make Supabase the canonical subscriber and consent store, while treating Google Forms as an intake channel only. A Google Forms installable form-submit trigger can forward each response to a small authenticated Supabase Edge Function; the Function validates and normalizes values, records the source response ID idempotently, then creates a pending subscription and sends a verification email. Only verified, active subscriptions enter the mailing audience. This avoids treating a raw form response as proof of mailbox ownership.
- Alternative Google Forms integration: Forms API watches publish to Google Cloud Pub/Sub and the receiver fetches responses from Forms API. This is a first-party push path but requires Cloud Pub/Sub, Google API credentials, watch renewal (watches expire after one week), and a receiver. For this project's small first-party intake, Apps Script is the lower setup option, though it runs as the installing Google account and needs operational monitoring/re-authorization planning.
- The linked Google Sheet should be an operator-facing audit/export view, not the source of truth. Editing/deleting spreadsheet rows should not silently subscribe/unsubscribe people or override verified consent.
- Common newsletter signup pattern is a small website form (often inline in a site footer or a dedicated subscribe page), followed by an immediate on-page acknowledgement. Many mailing services support single opt-in and double opt-in; double opt-in sends a confirmation email and activates the subscriber only after a click. For this feature, the recommended flow is a simple first-party page, clearly stated daily Naver Trends purpose and category preferences, then double opt-in. The extra click costs some signups but validates mailbox control and provides a strong consent trail for an automated list.
- The signup page should ask for as little as possible: email, optional display name, category choices, and an explicit newsletter consent action. It should explain expected frequency (daily, after morning collection), content type, and how to stop receiving mail. Do not subscribe via a prechecked/implicit marketing consent or by submitting unrelated feedback.
