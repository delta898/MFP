# v0.4.3 Card News Main Development Record

## Branch
- Branch: `codex/feat/v0.4.3-card-news-main`
- Base branch: `dev`
- Start date: 2026-09-04
- Status: manual feature complete; ready for `dev` integration

## User Need
BlogGenius users should be able to turn a public article or a manuscript into a coherent set of card-news images, edit the result, and keep it locally even when automatic SNS publishing is not available. The feature should later grow into multi-channel publishing and RSS-driven automation without coupling card generation to one platform or storage provider.

## Goal
Deliver a useful card-news creation workflow for v0.4.3 in reviewable stages. Creation, rendering, storage, and distribution remain separate boundaries so that local export is always useful and optional Buffer publishing can be added after its asset requirements are verified.

## Scope
- Add Card News as its own top-level product surface.
- Support source input from configured blog feeds, a directly entered public URL, and pasted manuscript text.
- Use RSS as the source of truth for the current public articles on configured blogs, then fetch the selected public URL when full text is needed.
- Generate a structured set with cover, body, and closing cards.
- Ask the configured image AI to generate the complete card, including visible Korean text, as the initial default.
- Preserve each card's intended semantic copy separately so a user can revise the wording and regenerate only that card.
- Defer deterministic BlogGenius text rendering to an optional later phase.
- Preserve projects and the last valid generated result across partial failures.
- Support local image export independently of SNS publishing.
- Support optional ordered multi-image Buffer publishing through the shared Google Drive temporary-media transport.

## Explicit Non-goals for the Initial Stages
- Automatic card-news creation or publishing from blog completion events.
- General third-party RSS automation.
- Scraping authenticated, blocked, or anti-bot pages.
- Direct Instagram, Threads, or Bluesky account integration.
- Assuming Google Drive is a reliable public image CDN without an explicit compatibility check.
- Storing user-generated assets in application-owned cloud storage without an agreed retention, privacy, cost, and cleanup policy.

## Product Direction Agreed with the User
- Card News belongs in the left main navigation rather than inside the Blog form.
- Card News settings contain defaults; project-specific choices remain in the creation flow.
- A configured blog is a fixed RSS source. The current public platform state, rather than BlogGenius publish history, determines which articles are selectable.
- Direct URL input may reject pages that require authentication or prevent normal public retrieval.
- Local export alone is a meaningful product outcome; users can upload the images themselves.
- Automatic workflows come after the manual creation path is stable.
- Plans and release scope may change as technical checks and user review reveal better boundaries.

## Proposed Architecture

### Source Contract
Normalize all inputs into a source snapshot with provenance:
- `feed_item`: configured feed, stable item identity, canonical URL, publication time
- `url`: canonical public URL and extraction result
- `manuscript`: user-provided text without a remote dependency

RSS performs discovery and duplicate identity. A public article URL supplies the latest full text when a feed contains only a summary.

### Card News Project
A durable project owns:
- source snapshot and attribution
- card outline and ordered card records
- design profile and output dimensions
- editable semantic text
- generated visual assets and rendered outputs
- export and delivery results

### Rendering Boundary
The initial renderer delegates the complete visual card, including visible Korean text, to the configured image model. BlogGenius still keeps semantic card copy, visual intent, and provenance outside the generated bitmap so users can revise the intended wording and regenerate an individual card. Deterministic text composition remains a separate optional capability for a later phase rather than a v0.4.3 prerequisite.

### Asset Boundary
Asset destinations are capability-based:
- local export
- Google Drive archive
- public publishing transport, with candidate implementations such as Drive public links, WordPress temporary media, or a future dedicated temporary store

Storage and distribution must not be represented as the same capability.

### Distribution Boundary
Buffer remains the preferred multi-channel adapter initially. Channel-specific limits and transformations belong in a capability matrix. The existing single-image `imageUrl` request is treated as an application limitation to replace with an ordered asset contract.

### Card News Management Ledger
The configured Google Spreadsheet will contain a `cardnews` management tab. It is a human-readable queue and index, not an asset store or a replacement for local manifests.

- One row represents one source item. `entry_key` is derived from RSS GUID first and normalized canonical URL second, so repeated RSS collection upserts instead of duplicating the item.
- The row records source identity, workflow status, aggregate publishing status, the active local `generation_id`, scheduling metadata, and user-facing channel/link summaries.
- Generated images, prompts, structured card data, and channel delivery details remain in the local generation manifest. The Sheet stores no local absolute path; `generation_id` is the portable join key.
- The Sheet is the management view, while local manifests remain authoritative for asset existence and detailed generation state. Failed Sheet writes enter a small local sync outbox and are retried; a temporary Google outage must not discard a completed generation or publication result.
- Workflow and publishing state remain separate because a completed card set can still be unpublished, scheduled, partially delivered, or failed.
- Initial columns are intentionally bounded: `entry_key`, `상태`, `발행 상태`, `원문 플랫폼`, `글 제목`, `원문 URL`, `RSS GUID`, `RSS 발행일시`, `수집일시`, `generation_id`, `카드 수`, `발행 채널`, `게시물 링크`, `예약일시`, `처리일시`, `마지막 오류`.
- The app owns identity and transition fields. Users may change only explicitly supported control fields such as status, exclusion, or scheduling; synchronization must preserve unrelated user columns.
- Sheet readiness follows the existing isolated `SNS` pattern: app startup attempts to create or repair `cardnews`, but a failure does not block unrelated BlogGenius features. Entering Card News or starting its automation performs a strict readiness check with actionable guidance.
- Periodic RSS collection runs only while the desktop app is running in the initial implementation. Spreadsheet storage alone does not provide an always-on scheduler; cloud or agent execution remains a later product decision.

## Proposed Stages
1. Feasibility and contracts
   - inspect source, Google OAuth, asset, Buffer, and rendering boundaries
   - verify assumptions with automated, non-publishing tests
   - define bounded PoCs that require later approval for remote side effects
2. Source and project foundation
   - configured blog feeds, direct URL, pasted manuscript
   - source preview and durable project state
3. Composition and rendering
   - outline generation, semantic copy editing, and complete-card AI generation
   - card-level retry while preserving the last valid result
4. Export and delivery
   - ordered image files and bundle export
   - capability-based temporary public-media delivery
5. Buffer multi-image publishing
   - only after public asset transport is proven
   - per-channel validation, status, retry, reconciliation, and cleanup
6. Later automation
   - own-blog feed monitoring first, general RSS rules afterward

## Revised Management-Ledger Stages

1. Sheet contract and bootstrap
   - define the `cardnews` schema, status values, header repair, and dropdown validation
   - create the tab during startup readiness without making unrelated features depend on it
   - add strict Card News readiness for management operations
2. Ledger gateway and state model
   - add append/upsert/list/update operations with stable `entry_key` deduplication
   - keep workflow status and publishing status independent
   - preserve unknown user columns and reject invalid transitions
3. Current workflow synchronization
   - register selected RSS items and direct sources
   - link generation manifests by `generation_id`
   - write aggregate channel results and post links after confirmed publication
   - preserve the last valid ledger and local state when Sheets is temporarily unavailable, then retry through a local sync outbox
4. Management UI
   - add compact filters for items not yet made, in progress, ready, and published
   - show source, local card result, channels, and external post links without exposing storage internals
   - keep the default creation path as simple as the current source-selection flow
5. RSS intake and scheduling
   - periodically upsert configured-blog RSS items while the app is running
   - add opt-in scheduling only after restart recovery, duplicate prevention, and retry rules are verified
   - Stage 13 isolates RSS intake from scheduling so collection behavior can be verified before any automatic action is introduced. See `docs/plans/active/2026-09-05-v0.4.3-card-news-13-rss-intake-development.md`.
6. Import expansion
   - import an ordered ZIP as a locally prepared generation and attach it to a ledger row
   - general RSS rules and always-on execution remain later stages
   - Stage 14 implements the local ZIP import and manual-publication handoff. See `docs/plans/active/2026-09-05-v0.4.3-card-news-14-zip-import-development.md`.

## Alternatives and Tradeoffs
- BlogGenius publish history was rejected as the public article source of truth because drafts may never be published and users may edit posts directly on the platform.
- Direct social APIs do not remove the need for public media URLs on Meta publishing paths and would add provider-specific authentication and lifecycle work.
- Google Drive is attractive because Google is already connected and `drive.file` is available, but a browser download link is not automatically a stable CDN URL for Buffer.
- Deterministic text rendering would improve exact copy control but adds bundled-font, layout, overflow, and cross-platform rendering work. The initial release prioritizes model-driven visual quality and card-level regeneration instead.
- WordPress temporary media is immediately familiar but makes automated distribution depend on optional WordPress configuration.
- Application-owned object storage would be reliable but introduces product-level data ownership, retention, privacy, and cost decisions.

## Verification Strategy
- Use contract and unit tests for source normalization, project state, layout validation, channel capabilities, failure preservation, and cleanup decisions.
- Use fixtures for RSS, public HTML, image model responses, Drive, and Buffer during normal development.
- Do not publish to real SNS channels or mutate production services without explicit user approval.
- Run focused UI regression checks per reviewable slice; the user performs final visual and exploratory UI acceptance.
- Run the full unit suite before the completed parent branch is proposed for merge into `dev`, unless the user explicitly changes that merge-time scope.

## Remaining Risks and Deferred Work
- Model-dependent Korean text accuracy and within-set visual consistency remain subject to the configured image model; individual regeneration and local replacement are the recovery paths.
- Google Drive is a temporary delivery transport, not a permanent archive or CDN. Ambiguous Buffer timeouts intentionally retain files to avoid breaking a post whose delivery status is unknown.
- Automatic creation and scheduled publication are explicitly deferred.
- Optional deterministic text rendering, Bitly URL shortening, and further visual/accessibility polish remain backlog candidates rather than v0.4.3 requirements.
- Stage 08 passed an explicitly authorized live Threads publication check using a Drive-hosted real image; normal automated verification performs no external publication.

## Final Result
The v0.4.3 manual Card News feature is complete. Users can discover or enter source content, generate and revise card compositions and images, preserve local results, export/import ordered ZIP bundles, manage source-to-generation/publishing state through the `cardnews` Sheet ledger, and publish ordered multi-image posts through Buffer without requiring WordPress. Automatic generation and scheduling remain out of scope. Final parent regression evidence is recorded by the finalization stage before `dev` integration.
