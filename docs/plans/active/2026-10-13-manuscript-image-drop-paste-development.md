# 원고 이미지 드롭·붙여넣기 개발 기록

- Branch: `codex/feat/manuscript-image-drop-paste`
- Start date: 2026-10-13
- Base/parent branch: `dev`
- Status: 구현 및 자동 검증 완료; 사용자 UI 확인 대기

## 사용자 필요와 목표

원고 편집기에서 이미지 파일을 드래그해 놓거나 클립보드의 이미지를 붙여넣어 원고에 배치하고 싶다. 기존 BlogGenius 이미지 블록과 Draft 이미지 관리 흐름을 유지하면서 입력을 간편하게 한다.

## 범위

- Tiptap 원고 편집기의 세 입력 경로(AI, 폴더, 붙여넣기)에서 공통 지원
- 본문에 이미지 파일을 드롭하면 놓은 포인터 위치에 맞춰 자체 이미지 블록 추가
- 이미지 블록 미디어 영역에 드롭하면 기존 동작대로 해당 블록의 이미지 교체
- 클립보드 이미지 데이터를 붙여넣으면 현재 선택 위치에 자체 이미지 블록 추가
- PNG, JPEG, WebP, AVIF 및 기존 장당 20MB 제한 유지
- 잘못된 형식, 다중 이미지, Draft/슬롯 준비 실패 시 원고와 기존 이미지를 보존하고 오류 안내
- 계약 및 UI 브라우저 회귀 검증

## 비범위

- 웹 URL에서 이미지를 가져오기 또는 원격 페이지 이미지 추출
- 여러 파일을 한 번에 배치
- 일반 Markdown에 이미지 URL/데이터를 넣는 방식 변경
- 이미지 변환, HEIC 지원, 이미지 업로드 한도 변경
- 기존 Blog Beta 밖의 UI 변경

## 설계와 경계

- 이미지 표현은 기존 `manuscriptImage` 블록 및 `[[IMAGE ...]]` Markdown 규격을 사용한다.
- 편집기 경계에서 clipboard/drop 파일을 검증하고, 이미지 블록 생성과 파일 import는 기존 Draft 이미지 API 및 service를 사용한다.
- 새 이미지 블록은 Markdown 변경으로 Draft preview/slot manifest와 동기화한 뒤 반환된 `blockId`/slot에 파일을 import한다. 비동기 preview 동안 입력 파일을 잃지 않도록 pending 입력과 편집 상태의 소유권을 명시한다.
- 기존 이미지 카드 위 drop은 교체 의미를 유지하고, 나머지 편집기 본문 drop은 drop 좌표를 이용해 새 블록을 삽입한다.
- 선택지 충돌이나 업로드 오류가 기존 원고 내용을 삭제하지 않도록 실패 시 새로 삽입한 빈 블록만 정리한다.

## 구현 단계

1. 현재 block node, Draft preview 동기화, import API 계약을 확인한다.
2. 이미지 파일 clipboard/drop을 공통으로 추출·검증하는 편집기 입력 처리를 구현한다.
3. 새 블록 삽입 후 Draft slot 생성 및 파일 import를 조정한다.
4. 브라우저 회귀에서 세 입력 경로, 기존 블록 교체, 새 블록 위치, 실패 보존을 검증한다.

## 진행 기록

- 2026-10-13: `dev`에서 깨끗한 작업 트리를 확인하고 feature branch를 생성했다. 기존 drop은 이미지 블록의 미디어 영역에 한 장을 놓는 경우에만 동작한다. `handlePaste`는 Markdown 텍스트 전용이고 클립보드 이미지 파일을 처리하지 않는다. 기존 import service는 파일 signature, 형식, 20MB 제한을 검증한다.
- 2026-10-13: Tiptap 편집기의 세 입력 모드(AI, 폴더, 붙여넣기)에 이미지 파일 붙여넣기와 본문 drop을 연결했다. 파일 형식과 20MB를 검사한 다음 `manuscriptImage` 블록을 만들고, 현재 Draft preview에서 해당 `blockId`의 슬롯을 확인해 기존 import API로 올린다. 서버 슬롯 동기화와 업로드 동안 기존 이미지 작업 잠금을 소유해 동시 작업을 막는다.
- 2026-10-13: 캔버스에 파일을 끌어오면 추가 위치 안내를 표시한다. 본문에서는 커서/포인터가 속한 최상위 블록 뒤에 이미지 블록을 추가해 목록 내부의 중첩 Markdown 지시문이 되지 않게 했다. 편집 영역 바깥 캔버스 여백에 놓은 파일은 문서 끝에 추가한다. 이미지 블록 미디어 영역 drop은 기존 이미지 교체 동작을 유지한다.
- 2026-10-13: 브라우저 fixture가 Markdown의 이미지 ID, 제목, 프롬프트를 Draft 슬롯에 반영하도록 갱신했다. 새 블록 업로드 뒤에도 이미지 제목/프롬프트 보존 동작을 fixture에서 재현하고, 붙여넣기·본문 drop의 블록 추가/업로드/삭제를 검증하도록 회귀 시나리오를 추가했다. fixture가 기존 프롬프트 편집 결과를 반환하게 되면서 기대값도 최신 편집 내용으로 수정했다.
- 2026-10-13: 첫 브라우저 실행에서 편집기 소스가 변경됐지만 앱이 읽는 제품 번들(`ui/scripts/vendor/manuscript-editor.js`)이 갱신되지 않은 점을 확인했다. 번들을 다시 빌드해 검증했으며, 붙여넣기/드롭 시 루트 이미지 블록이 생성되고 기존 본문이 유지됨을 확인했다.
- 2026-10-13: 첫 전체 브라우저 smoke는 새 붙여넣기/드롭 시나리오를 통과했지만, 이후 기존 로컬 원고 가져오기 구간에서 5초 대기 제한에 걸려 실패했다. 이어 실행한 전체 smoke는 다시 성공했다.
- 2026-10-13: 사용자 확인에서 일반 파일 드롭이 동작하지 않는다는 피드백을 받았다. 원인은 본문 드롭 처리를 ProseMirror의 `handleDrop`에만 맡긴 경로로 판단했다. 캔버스의 capture 단계에서 파일을 직접 처리하고 편집기 좌표로 새 이미지 블록을 배치하도록 바꿨으며, 이미지 블록 미디어 영역 드롭은 기존 교체 핸들러가 계속 받도록 했다. 번들을 재빌드하고 계약 테스트 및 전체 브라우저 smoke를 다시 통과했다.
- 2026-10-13: 사용자가 드롭 중 검은 가로 표시와 PNG 파일에서 빈 블록이 남는 문제를 확인했다. 가로 표시는 Tiptap 기본 Dropcursor이며, 새 이미지 블록은 포인터 좌표를 기준으로 현재 top-level 문단 뒤에 배치된다. 파일은 기존 커서 위치가 아니라 놓은 위치를 기준으로 처리된다. `StarterKit`의 dropcursor를 끄고, 20 MiB 이미지가 base64 JSON으로 약 27 MiB가 되는 점을 반영해 원고 이미지 import 요청 한도를 30 MiB로 높였다(기존 15 MiB는 PNG가 더 쉽게 초과할 수 있음). 업로드 실패 시 새로 추가한 블록만 원고에서 제거하도록 했다.
- 2026-10-13: 변경한 런타임 요청 한도를 `src/ui-runtime/http-server-runtime.test.js`에서 검증했고, HTTP 런타임 및 이미지 계약 테스트 13/13, 편집기 번들 빌드, 전체 브라우저 smoke, `git diff --check`를 통과했다.
- 2026-10-13: 병합 전 검토에서 파일 메타데이터가 같은 여러 파일을 중복으로 간주해 하나로 줄일 수 있는 점을 발견했다. 입력 파일 배열을 그대로 유지해 단일 이미지 정책 검증이 여러 파일을 정확히 감지하도록 수정했다.

## 결과와 검증

- 자동 검증: `npm run build:manuscript-editor`, 변경된 JS의 `node --check`, `node --test src/ui-runtime/http-server-runtime.test.js scripts/manuscript-image-workspace-contract.test.js` (13/13 통과), `npm run test:ui-browser` (전체 통과), `git diff --check`. 브라우저 smoke는 클립보드 이미지 붙여넣기, 편집기 본문 drop, 새 Draft 슬롯 import, 이미지 블록 제거, 기존 미디어 drop 교체 경로를 확인했다.
- 수동 UI 확인: 실제 macOS에서 PNG/JPEG/WebP/AVIF를 이미지 블록 본문에 drop/paste하고, 이미지 미디어 위 drop 시 기존 이미지가 교체되는지 확인한다. 지원하지 않는 형식, 여러 이미지, 20MB 초과 파일에 안내가 나타나는지도 확인한다.
- 남은 위험: 캔버스 바깥 여백 drop의 문서 끝 추가와 운영체제/브라우저별 클립보드 파일 제공 방식은 자동 브라우저 smoke에서 직접 검증하지 않았다. 사용자 UI 확인에서 주요 운영체제·브라우저의 파일 드롭 및 붙여넣기 동작을 확인할 수 있다.
