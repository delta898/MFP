# Config Loader Reorganization

## Branch

- Branch: `codex/fbr/config-loader-reorganization`
- Start date: 2026-10-18
- Base/parent branch: `codex/fbr/source-layer-reorganization`
- Status: In progress

## User need and goal

`src/config-loader.js` remains a root-level, broad compatibility module after the previous configuration-asset migration. Reorganize its responsibilities by architecture layer and product Application, migrate callers to owned contracts, and remove the root loader when no production callers depend on it.

## Scope

- Inventory the loader's returned settings, startup side effects, direct imports, field-level consumers, tests, and packaging/build references.
- Keep filesystem/bootstrap configuration and runtime path selection in `src/host/configuration/`.
- Move environment selection to `src/host/configuration/environment/`, shared policy to the appropriate `src/services/`, and product-specific settings/workflow policy to `src/applications/<product>/`.
- Route UI and channel access through Application/service ports and composition; avoid introducing Application-to-Host dependencies.
- Preserve startup ordering, persisted config shape, defaults, environment/secret behavior, and current user-visible behavior.
- Remove `src/config-loader.js` and obsolete compatibility projections after production callers and tests migrate.
- Keep the canonical architecture document and `src/README.md` aligned with each completed slice.
- User-approved scope extension on 2026-10-19: continue the broader source-layer reorganization on this branch by separating Knowledge and Memory responsibilities into their owning service, adapter, storage, Host, and composition layers. Do not merge the two domains.
- User-approved scope extension on 2026-10-19: reorganize `license.js`, `license-feature-policy.js`, `publish-quota.js`, and `smart-usage/` by responsibility. Preserve entitlement and usage behavior while separating provider-neutral licensing policy/contracts, Supabase transport, Host-owned identity/credential access, and Application callers; remove the legacy facade after callers migrate.


- User-approved scope extension on 2026-10-19: reorganize `src/ui-api/` by layer and product vertical, moving HTTP routing/controller translation to `src/adapters/ui/<vertical>/`, moving composition out of route modules, then migrating each API service's workflow responsibility into its owning Application/service and removing `src/ui-api/` when no production caller remains. Do not delete active API behavior merely because its assembler is named `legacy`.
- User-approved scope extension on 2026-10-19: continue the source-layer migration through `src/ui-runtime/`. Classify each module independently; move transport helpers to `adapters/ui/`, server lifecycle to Host, feature workflows to Applications, shared services to `services/` or `utilities/`, and dependency wiring to `composition/`. Remove `src/ui-runtime/` after all live callers and tests have migrated; do not move the directory wholesale.
- User-approved scope extension on 2026-10-19: continue the source-layer migration through `src/ui-server.js`. Split Host process/startup lifecycle, UI protocol translation, and product/runtime composition by responsibility; migrate Host callers and remove the root composition module only when no production or test caller remains. Do not move the file wholesale or alter route/API behavior.
- User-approved scope extension on 2026-10-19: continue decomposition of `src/utils.js` by responsibility and layer. Migrate callers in the same slice, remove confirmed dead legacy helpers, update the architecture and source inventory, and delete the root facade only after all remaining Blog, SNS, Shopping, adapter, and composition callers have explicit owners. Do not move the file wholesale.

## Explicit non-goals

- No config schema or default changes without a separate user decision.
- No changes to persisted user configuration, credential ownership, provider integrations, product UX, or publishing behavior.
- No other unrelated cleanup, version changes, merge, push, or release work.

## Design and stages

1. Map every exported configuration field to its owner and every consumer to its entry boundary. Identify side effects and dynamic/package references.
2. Define the Host configuration loading contract and the Application/service configuration ports needed by active callers.
3. Extract one responsibility group at a time, migrate composition and callers in the same slice, and remove duplicate compatibility logic as each group is verified.
4. Verify startup and focused contracts for each slice; search for direct imports and stale root references.
5. Remove the root loader only after production callers, tests, and packaged startup paths use the new contracts. Update architecture/source maps and finalize this record.
6. For the approved Knowledge/Memory stage, migrate callers and tests alongside files, keep Recommendation lifecycle/policy separate, update the canonical architecture and source ownership map, and run focused contracts without starting the full suite.
7. For the approved Licensing stage, relocate provider-neutral feature/quota/smart-usage contracts and tests into `services/licensing/`, split the Supabase protocol adapter from licensing orchestration and Host credential resolution, migrate all callers, preserve key-storage paths and RPC semantics, remove the root compatibility facade, and update packaging/docs.

## Decisions and tradeoffs

- 2026-10-18: User asked for this work on a separate feature branch. The branch is based on the current `codex/fbr/source-layer-reorganization` tip.
- 2026-10-18: The loader must not be moved wholesale into Host because it currently combines Host bootstrap, environment values, shared service configuration, and product/Application policy. Caller paths must follow ownership rather than merely point to a new facade.
- 2026-10-19: Licensing will not be moved wholesale into `applications/account/` or left as a renamed provider facade. Shared entitlement/quota/usage policy belongs in `services/licensing/`, Supabase protocol in an adapter, key persistence in the existing storage adapter, and device identity/credential resolution at the Host boundary. Keep the current License method behavior as an injected port until all callers are migrated.
- Preserve existing behavior and config shape while relocating ownership. Ask the user before a change that materially alters product behavior, persistence, compatibility, or secret handling.
