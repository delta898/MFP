# BlogGenius Design Principles v1.0

## 문서 상태

- Version: `v1.0 Stable Principles`
- Status: Gate 1·2·3 사용자 승인 및 안정판 승격 완료
- Source stage: `codex/feature/design-system-01-principles`
- 적용 대상: BlogGenius 제품 UI 전반
- 목적: 개별 화면의 취향이 아니라 반복 가능한 제품·UX 판단 기준을 제공한다.

이 문서는 색상이나 픽셀 값을 정하지 않는다. 제품 경험에서 지켜야 할 원칙을 정의하고, 구체적인 시각 값은 별도의 style contract와 style pack이 담당한다. `v1.0`은 compatibility 기반, Warm Editorial 실제 적용과 Quiet Sage 확장성 검증의 세 필수 Gate를 통과한 안정판이다. 하위 실행·component 가이드는 실제 화면 적용을 통해 계속 발전시킨다.

## 원칙의 계층

BlogGenius의 디자인 기준은 다음 세 수준으로 관리한다.

1. **Product Experience Principles**: 스타일이 바뀌어도 유지되는 사용자 경험 기준
2. **Operational Guidelines**: 화면을 만들고 검토할 때 적용하는 실행 규칙
3. **Component and Pattern Guide**: 구현으로 검증된 컴포넌트·상태·흐름별 상세 규격

처음부터 모든 컴포넌트 규격을 확정하지 않는다. 아래 원칙과 실행 규칙을 먼저 합의하고, 상세 규격은 실제 화면을 이전하면서 검증된 것만 축적한다.

## Product Experience Principles

### 1. 사용자의 목적이 화면의 주인공이다

**의도**

사용자가 지금 하려는 일과 그 결과가 장식, 설정, 내부 구조보다 먼저 보여야 한다.

**실행 규칙**

- 화면마다 가장 중요한 사용자 작업과 결과 영역을 명확히 구분한다.
- 내부 provider, 저장 방식, prompt 같은 용어는 사용자의 결정에 필요할 때만 노출한다.
- 장식은 정보 위계와 이해를 돕는 범위에서 사용한다.
- 결과를 확인하는 화면에서는 생성 버튼보다 결과 자체가 시각적 중심이 된다.

**피해야 할 패턴**

- 동일한 중요도로 보이는 다수의 CTA
- 실제 작업보다 큰 장식 카드나 설명 영역
- 사용자가 알 필요 없는 내부 구현 용어

**리뷰 질문**

- 사용자가 3초 안에 이 화면의 주된 작업을 알 수 있는가?
- 가장 눈에 띄는 요소가 실제로 가장 중요한 요소인가?

### 2. 아름다움은 차분한 명료함에서 나온다

**의도**

BlogGenius의 시각적 완성도는 효과를 많이 사용하는 것이 아니라, 타이포그래피·간격·정렬·대비가 만드는 질서에서 나온다.

**실행 규칙**

- 크기, 굵기, 색상, 간격을 모두 강조 수단으로 동시에 사용하지 않는다.
- 카드와 구분선은 실제 정보 그룹을 표현할 때만 사용한다.
- 같은 화면에서 강조색의 역할을 제한한다.
- 여백은 남는 공간이 아니라 정보 관계를 표현하는 수단으로 사용한다.

**피해야 할 패턴**

- 의미 없이 중첩된 카드와 그림자
- 거의 같은 색상·간격·radius의 반복적인 변형
- 모든 영역에 badge, gradient, animation을 추가하는 방식

**리뷰 질문**

- 장식을 하나 제거해도 의미가 유지된다면 제거하는 편이 나은가?
- 정보 그룹과 시각적 그룹이 일치하는가?

### 3. 시작은 단순하게, 필요한 깊이는 가까이에 둔다

**의도**

처음 사용하는 사람은 빠르게 시작하고, 숙련된 사용자는 필요한 상세 설정에 접근할 수 있어야 한다.

**실행 규칙**

- 기본 경로에는 필수 결정만 둔다.
- 고급 설정은 문맥을 잃지 않는 위치에서 점진적으로 공개한다.
- 자동으로 안전하게 결정할 수 있는 값은 기본값을 제공한다.
- 사용자가 이미 입력한 내용이나 시스템이 알고 있는 정보를 반복해서 요구하지 않는다.

**피해야 할 패턴**

- 첫 화면에 모든 옵션을 펼쳐 놓는 구성
- 중요한 설정을 발견하기 어려운 깊은 계층에 숨기는 구성
- 같은 의미의 설정을 서로 다른 화면에서 중복 제공하는 구성

**리뷰 질문**

- 처음 사용하는 사람이 설명 없이 기본 작업을 완료할 수 있는가?
- 숙련 사용자가 원하는 세부 제어에 무리 없이 도달할 수 있는가?

### 4. 시스템 상태가 보이면 신뢰가 생긴다

**의도**

AI 생성, 발행, 수집, 저장처럼 시간이 걸리거나 외부 상태에 의존하는 작업은 현재 상태와 다음 행동을 명확히 보여줘야 한다.

**실행 규칙**

- AI 작업은 사용되는 모델 역할을 식별할 수 있게 한다.
- 실행 중에는 명확한 진행 상태를 보이고 중복 실행을 막는다.
- 성공, 부분 성공, 대기, 실패, 재시도를 서로 구분한다.
- 오류 문구는 무엇이 실패했는지와 사용자가 할 수 있는 다음 행동을 함께 설명한다.
- 실제 상태가 변하지 않았는데 낙관적인 완료 표현을 사용하지 않는다.

**피해야 할 패턴**

- 버튼 문구만 바뀌고 진행 여부는 알 수 없는 상태
- 실패 원인 없이 `오류가 발생했습니다`만 표시하는 방식
- 실행 중 같은 요청을 다시 시작할 수 있는 UI

**리뷰 질문**

- 사용자가 현재 진행 중인지 멈춘 것인지 구분할 수 있는가?
- 실패 후 가능한 다음 행동이 분명한가?

### 5. 사용자의 작업은 가능한 한 이어져야 한다

**의도**

일시적인 실패나 화면 이동이 이미 만든 결과와 입력을 불필요하게 지우지 않아야 한다.

**실행 규칙**

- 새 요청이 실패하면 마지막 정상 결과를 유지한다.
- 되돌리기 어렵거나 외부 상태에 영향을 주는 파괴적 작업은 대상과 영향을 명확히 보여주고 확인을 받는다.
- 즉시 완전하게 복구 가능한 로컬 작업은 결과를 명확히 알리고 같은 맥락에서 바로 되돌릴 수 있게 하면 사전 확인을 생략할 수 있다.
- 저장되지 않은 변경과 저장 완료 상태를 구분한다.
- 재시도는 가능한 경우 기존 입력과 문맥을 보존한다.

**피해야 할 패턴**

- 로딩 시작과 동시에 기존 결과를 지우는 방식
- 실패 후 전체 폼을 초기화하는 방식
- 삭제·발행처럼 되돌리기 어려운 작업을 일반 행동과 동일하게 표현하는 방식

**리뷰 질문**

- 네트워크나 AI 요청이 실패해도 사용자가 다시 처음부터 시작하지 않는가?
- 되돌리기 어려운 작업임을 실행 전에 알 수 있는가?

### 6. 같은 의미는 같은 방식으로 표현한다

**의도**

사용자가 한 화면에서 배운 조작과 상태 표현을 다른 화면에서도 그대로 사용할 수 있어야 한다.

**실행 규칙**

- 동일한 역할의 버튼, 입력, 상태, 카드에는 공통 component와 semantic token을 사용한다.
- feature 이름이 아니라 사용자 의미를 기준으로 component variant를 정한다.
- 예외가 필요하면 임의 CSS보다 명시적인 variant와 이유를 남긴다.
- 같은 상태 이름과 색상이 화면마다 다른 의미로 쓰이지 않게 한다.

**피해야 할 패턴**

- 화면마다 별도로 만든 저장 버튼과 로딩 표현
- 같은 강조색을 선택, 성공, 링크 등 여러 의미에 혼용하는 방식
- source order나 `!important`에 의존하는 예외 덮어쓰기

**리뷰 질문**

- 이미 존재하는 component나 pattern으로 표현할 수 있는가?
- 새 예외가 제품 전체에서 재사용할 의미를 가지고 있는가?

### 7. 접근성과 반응형 동작은 기본 품질이다

**의도**

키보드, 다양한 화면 크기, reduced motion, 충분한 대비는 별도 옵션이 아니라 모든 스타일이 충족해야 할 기본 계약이다.

**실행 규칙**

- 모든 상호작용 요소는 키보드 focus를 명확히 표시한다.
- 색상만으로 상태를 구분하지 않는다.
- 좁은 화면에서도 주 작업과 상태를 잃지 않는다.
- motion은 의미가 있을 때만 사용하고 reduced-motion 설정을 존중한다.
- 텍스트 확대와 긴 한국어 문구를 고려한다.

**피해야 할 패턴**

- 대체 focus 표시 없이 outline을 제거하는 방식
- hover에서만 알 수 있는 정보
- 고정 폭 때문에 행동이나 상태가 잘리는 레이아웃

**리뷰 질문**

- 마우스 없이 주요 흐름을 완료할 수 있는가?
- 작은 화면과 긴 문구에서도 우선순위가 유지되는가?

### 8. 스타일은 달라져도 제품은 낯설어지지 않는다

**의도**

새로운 style은 BlogGenius의 성격을 확장할 수 있지만 기능, 정보 구조, 상태 의미를 바꾸지 않아야 한다.

**실행 규칙**

- 초기에는 별도 theme 축을 두지 않고 하나의 style이 하나의 완결된 시각 체계를 제공한다.
- style은 합의된 token contract 안에서 색상 모드, 서체, radius, elevation, density, motion을 표현한다.
- component 구조와 접근성 상태는 style pack 밖에서 관리한다.
- 스타일 변경은 사용자의 진행 중 작업을 초기화하지 않는다.

**피해야 할 패턴**

- style별로 다른 DOM이나 JavaScript 흐름을 유지하는 방식
- 특정 style 이름을 feature CSS에 직접 하드코딩하는 방식
- style 변경에 따라 버튼의 의미나 위치가 달라지는 방식

**리뷰 질문**

- style을 제거하거나 교체해도 기능과 상태가 동일하게 동작하는가?
- 이 차이는 style token으로 표현할 수 있는가, 아니면 별도 component variant가 필요한가?

## Operational Guidelines

### 결정 행동의 위치와 위계

- 완료형 form과 dialog는 사용자의 실제 주된 목적과 되돌리기 어려운 정도로 action 위계를 정하고, 하나의 action group에서 여러 filled button이 같은 강도로 경쟁하지 않게 한다.
- 결과나 성격이 다른 secondary·dismissive·danger action은 primary와 구분하되, toolbar·반복 row·navigation·좁은 화면에 기계적인 한 방향 정렬을 강제하지 않는다.
- 반응형 재배치 후에도 중요 action의 발견 가능성, 논리적인 keyboard 순서와 접근성 의미를 유지한다.

구체적인 action variant, dialog action 수, 배치, keyboard 순서와 확인 흐름은
[Design Component and Pattern Guide](./design-component-patterns.md#action-variants)가 단일 상세 계약으로 소유한다.

## Design System Engineering Principles

- **Semantic first**: 화면과 component는 원시 색상값보다 의미 기반 token을 사용한다.
- **Behavior is invariant**: style은 기능, 데이터, 접근성 의미를 소유하지 않는다.
- **One style, one theme**: 초기에는 style과 theme를 별도 조합 축으로 나누지 않고 하나의 검증 단위로 관리한다.
- **Components before exceptions**: 반복되는 규칙은 공통 component나 pattern으로 승격한다.
- **Incremental migration**: 전체 재작성 없이 공통 shell과 합의된 Beta surface부터 이전한다.
- **Validated contracts**: 누락 token, 금지된 원시 값, 주요 상태와 반응형 동작을 자동 검증한다.

## 원칙 변경 규칙

- 원칙은 개별 화면을 정당화하기 위해 쉽게 바꾸지 않는다.
- 새로운 원칙은 기존 원칙으로 판단할 수 없는 반복적인 문제에만 추가한다.
- component guide와 style 값은 구현 경험에 따라 자주 개선할 수 있다.
- 사용자-visible 행동이나 다중 style contract를 바꾸는 결정은 사용자 합의 후 반영한다.

## 검토 이력

- 2026-09-06 Gate 1: Product Experience Principles 8개를 모두 `유지`하기로 사용자와 합의했다. compatibility 화면 검토에서 완료 행동의 좌측 배치와 강한 secondary button이 서로 경쟁하는 문제를 확인해 `결정 행동의 위치와 위계` 운영 가이드를 추가했다. 현재 외형은 foundation 단계에서 즉시 바꾸지 않고 첫 정식 style 적용 시 공통 action pattern으로 검증한다.
- 2026-09-07 Gate 2: 첫 정식 style `따뜻한 에디토리얼`을 공통 shell과 Blog Beta에 적용하고 Product Experience Principles 8개를 모두 `유지`하기로 합의했다. action hierarchy, refresh와 selection control 규칙은 하위 component guide로 구체화했다. 빠른 글 작성의 과밀도와 tab별 시작 문법 차이는 원칙의 결함이 아니라 적용 gap으로 판단해 독립 P1 일감으로 분리했다.
- 2026-09-07 Gate 3: 두 번째 style `고요한 세이지 스튜디오`로 palette, density, radius와 elevation 축을 달리해 확장성을 검증하고 Product Experience Principles 8개를 모두 `유지`하기로 사용자와 합의했다. 두 style이 동일 DOM·기능·상태·입력을 유지했고 첫 style 또는 compatibility에 가려졌던 공통 feedback, trend surface와 embedded widget 결합을 semantic contract로 교정했다. Design Principles와 다중 Style Contract를 `v1.0`으로 승격했다.

## v1.0 검증 기준선과 이후 검토

Compatibility 기반, 첫 정식 style 적용, 두 번째 style 확장성 검증의 세 Gate는 모두 자동 검증과 사용자 승인을 거쳐 완료됐다.
당시 상세 목적·완료 조건·결과는
[디자인 시스템 1단계 개발 기록](../plans/archive/2026-09-06-design-system-01-principles-development.md)과 각 후속 단계 개발 기록에 보존한다.

이후에는 다음 중 하나가 발생할 때 원칙과 하위 계약을 다시 검토한다.

- 기존 원칙으로 일관되게 판단할 수 없는 문제가 여러 surface에서 반복될 때
- 사용자-visible 행동, 정보 구조 또는 접근성 계약을 변경할 때
- 필수 semantic token의 의미나 style이 소유할 수 있는 범위를 변경할 때
- 새로운 style 또는 제품 surface 적용에서 기존 원칙과 실제 사용성 사이 충돌이 확인될 때

검토 결과는 실제 코드·자동 검증·사용자 확인 근거와 함께 해당 feature 개발 기록에 남긴다. 개별 화면의 예외를
정당화하기 위해 원칙을 바꾸지 않으며, 제품 경험 또는 다중 style contract 변경은 사용자 합의 후 반영한다.
