# 블로그 Beta AI 원고 생성 취소 계약

- 날짜: 2026-09-23
- 상태: 사용자 승인, 단계별 구현 중 (2026-09-23)
- 적용 범위: `블로그 Beta` AI 원고 생성. 다른 AI 작업과 발행은 후속 확장 대상.
- 개발 기록: `../plans/active/2026-09-23-ai-generation-cancellation-main-development.md`

## 문제와 현재 근거

현재 브라우저는 `/api/v1/blog/manuscript-drafts/ai`에 장시간 POST를 보내고 응답을 기다린다. 서버의 실행 coordinator는 단일 lease와 `busy` 상태만 보유하며 중단 신호는 없다. 요청 연결만 끊으면 `executeQuickPublish`와 그 아래의 모델 호출·재시도가 계속될 수 있다.

생성은 참고자료 수집 → 텍스트 모델 호출 → `contents.md` 작성 → 이미지별 모델 호출/폴링/다운로드 → preview session 등록 → 원고 Draft 생성 순서다. 특히 `Core.prepareImages`는 이미지 오류를 기록하고 다음 이미지로 넘어가며, `buildMultiPlatformGeneratedContent`는 오류를 실패 결과로 변환한다. 취소를 일반 오류로 흘려보내면 후속 단계가 진행될 수 있다. 작업 폴더도 preview session 등록 전에 만들어지므로 현재의 session 삭제만으로는 생성 도중 취소한 파일을 정리할 수 없다.

KIE Market 이미지의 현재 구현은 `createTask` → `recordInfo` 폴링 → 결과 다운로드다. [KIE 공식 시작 안내](https://docs.kie.ai/)와 [통합 작업 조회 문서](https://docs.kie.ai/market/common/get-task-detail)는 비동기 제출·조회 흐름을 설명한다. 2026-09-23에 확인한 공개 문서에서는 이 Market 작업을 취소하는 공식 endpoint를 찾지 못했다. 이는 *미지원 확정*이 아니며, 확인되지 않은 endpoint를 추측해 호출하지 않는다.

## 제안 결정

### 1. 앱 내부에서도 생성 작업을 비동기 작업으로 다룬다

- 생성 시작 요청은 서버가 작업을 등록하고 `operationId`를 반환한 뒤 즉시 끝난다. 생성 실행 Promise는 서버에서 추적하며 반드시 성공·실패·취소를 포착한다.
- 상태 조회는 해당 `operationId`의 상태, 단계, 시작/완료 시각, 취소 가능 여부, 종료 결과를 돌려준다. UI는 이를 폴링하고 페이지 이동/새로고침 후에도 같은 앱 프로세스가 살아 있다면 현재 작업을 다시 표시할 수 있다.
- 취소 요청은 별도 endpoint로 보낸다. 반환값은 취소 *접수*이지 취소 *완료*가 아니다. 최종 상태는 상태 조회로 확인한다.
- API 경로는 기존 원고 Draft 하위의 `operations`로 묶는다. 구체적인 요청·응답 형태와 HTTP 상태 코드는 첫 sub-feature의 계약 테스트에서 고정한다. 기존 동기 endpoint를 교체할지 호환 경로로 유지할지는 호출처 전수 확인 후 결정한다.
- 서버는 충돌이 없는 무작위 작업 ID를 발급하고 현재 프로세스 안에서 활성 작업 및 짧은 기간의 종료 결과를 보관한다. 원고 Draft 자체는 기존 저장소가 소유한다. 앱 재시작을 넘는 작업 복구는 이번 범위가 아니다.

첫 sub-feature에서 추가한 서버 API:

| 요청 | 의미 |
| --- | --- |
| `POST /api/v1/blog/manuscript-drafts/ai/operations` | 작업 등록 후 `202`와 작업 ID·초기 상태 반환 |
| `GET /api/v1/blog/manuscript-drafts/ai/operations/current` | 현재 진행 중인 AI 원고 작업 조회; 없으면 `null` |
| `GET /api/v1/blog/manuscript-drafts/ai/operations/{id}` | 해당 작업의 상태·종료 결과 조회 |
| `POST /api/v1/blog/manuscript-drafts/ai/operations/{id}/cancel` | 취소 접수 또는 이미 완료/취소 불가 상태 반환 |

종료 상태는 현재 프로세스에서 10분 동안 최대 20건 보존한다. 이 API는 아직 UI에서 사용하지 않으며 기존 동기 생성 API도 유지한다.

### 2. 상태 전이와 취소 가능 구간을 명시한다

```text
accepted → running → completed
                   ↘ failed
                   ↘ cancel_requested → canceled
```

- `cancel_requested` 동안은 기존 작업이 여전히 `busy`이며 새 생성·발행을 허용하지 않는다. 실제 실행이 중단되고 정리까지 끝난 뒤 `canceled`가 되고 lease가 해제된다.
- 취소는 동일 작업에 여러 번 요청해도 안전하다. 이미 종료된 작업에 대한 요청은 종료 상태를 반환하고 다른 작업을 건드리지 않는다. 다른 작업 ID를 취소 대상으로 바꾸지 않는다.
- 원고 Draft의 영속 생성 직전을 **commit 경계**로 둔다. 그 전에는 취소 가능하다. commit에 들어간 뒤에는 `canCancel: false`로 안내하고, 취소 요청은 `too_late`로 응답하며 정상 완료/실패 정리를 끝낸다. 영속 생성 중 강제 중단으로 반쪽 Draft를 남기지 않는다.
- 취소는 단일 오류 코드(`AI_GENERATION_CANCELED`)로 전파한다. 타임아웃·모델 실패·사용자 취소를 UI와 로그에서 구분한다. 하위 단계의 일반 오류 catch는 이 코드를 삼키지 않고 상위로 다시 던진다.
- 페이지를 닫거나 네트워크가 끊긴 것은 명시적 취소로 간주하지 않는다. 작업 상태 조회로 재결합하거나 사용자가 취소를 요청할 수 있게 한다.

### 3. 하나의 중단 신호를 하위 호출까지 전달한다

- 작업마다 `AbortController` 하나를 둔다. signal을 참고자료 수집, AI 텍스트/이미지 transport, 재시도 대기, KIE 폴링·다운로드까지 전달한다. 중단 이후 새 단계나 새 모델 호출을 시작하지 않는다.
- HTTP가 중단 신호를 지원하면 현재 호출을 끊는다. 중단할 수 없는 부분은 반환 직후 신호를 검사해 후속 단계와 결과 반영을 막는다. 브라우저의 `AbortController`는 화면 대기 중단에만 쓰고 서버 취소의 근거로 삼지 않는다.
- 모델 선택은 작업 시작 시점에 snapshot으로 고정한다. 사용자가 설정을 바꿔도 진행 중인 작업의 모델이 중간에 바뀌지 않는다. 새 설정은 취소 완료 후 시작하는 새 작업에 적용한다.
- 진행 단계는 내부 transport 이름 대신 `준비 중`, `글 작성 중`, `이미지 준비 중`, `마무리 중` 정도의 사용자 언어로 제한한다.

### 4. 결과와 임시 자산은 작업 단위로 소유한다

- 생성용 작업 디렉터리를 시작 시 고유하게 확보하고 소유권을 기록한다. 성공 시 Draft에 필요한 데이터만 가져오고 임시 preview/session을 정리한다. 취소·실패 시 그 작업이 만든 파일만 안전하게 폐기한다.
- 취소된 작업의 늦은 응답은 원고 Draft나 화면의 마지막 유효 preview를 덮어쓰지 않는다. UI는 `operationId` 일치 검사로 응답을 수락한다.
- 생성 중 입력값과 이전에 유효했던 원고는 취소 후에도 남긴다. 취소 자체를 오류 배너로 보여주지 않는다.
- 임시 파일 정리는 경로 소유권 확인 후에만 수행한다. 공용 workspace나 이전 Draft의 파일을 지우지 않는다.

### 5. KIE 원격 작업은 별도 상태로 취급한다

- `createTask`가 진행 중일 때 취소가 들어오면, 이미 원격 접수가 되었는지 불분명한 채 제출 HTTP를 끊지 않도록 응답/제한시간까지 기다려 `taskId` 획득을 우선한다. 이 짧은 구간은 UI에 `취소 요청 중`으로 표시한다.
- `taskId`를 받은 뒤에는 로컬 폴링·다운로드·결과 적용을 중단하고 작업 저널에 `locally_canceled`와 원격 상태 미확인 여부를 남긴다. 이는 KIE 측 실행 종료를 뜻하지 않는다.
- 공식 취소 API의 지원이 확인되면 그때만 원격 취소 adapter를 추가한다. 실패/미확인 시에도 로컬 결과 차단은 보장하지만 원격 계산이나 크레딧 환급을 보장하지 않는다.
- 제출 요청이 시간 초과되어 `taskId`를 받지 못한 경우 원격 접수 여부는 알 수 없다. 작업 로그에는 불확실성을 남기되, 없는 ID로 원격 취소를 시도하지 않는다.

## 검증 기준

- 시작 → 상태 조회 → 완료, 취소 접수 → 중단/정리 → 취소 완료, 취소와 완료의 경합, 중복 취소, 다른 작업 ID 취소를 계약 테스트로 검증한다.
- Gemini·OpenAI 호환 텍스트/이미지에서 진행 중 요청과 재시도 대기 모두 즉시 중단되고 이후 호출 수가 늘지 않는지 검증한다.
- KIE 제출 전/중/후, 폴링 중, 결과 다운로드 중 취소를 가짜 HTTP 클라이언트로 검증한다. 취소가 이미지별 오류로 흡수되지 않는지도 확인한다.
- preview 등록 전후 취소에서 새 Draft가 생기지 않고 작업 소유 임시 파일만 정리되는지 검증한다.
- 브라우저에서 긴 생성 중 취소, 모델 변경 후 재실행, 이전 성공 원고 보존, 페이지 이동 후 상태 복귀를 검증한다.
- 실제 유료 모델과 원격 서비스를 호출하는 검사는 별도 사용자 승인을 받는다.

## 대안과 미해결 사항

- **장시간 POST 유지 + 별도 취소 endpoint:** 변경량은 적지만 첫 요청과 취소·상태 동기화가 이원화되고 페이지 이동/새로고침 복구가 약하다. 비동기 작업 API를 권장한다.
- **브라우저 요청만 중단:** 서버의 재시도·이미지 생성·파일 쓰기를 멈추지 못하므로 제외한다.
- **취소 즉시 잠금 해제:** 이전 작업이 나중에 결과를 쓸 수 있어 제외한다.
- **KIE 원격 취소 추정 호출:** 문서화된 계약을 찾기 전에는 제외한다.
- 사용자는 비동기 시작 API 방향과 KIE 제출 요청 중 ID 확보를 기다리는 원칙에 동의했다. 단, ID 확보는 로컬 추적·중단을 위한 것이며 원격 취소를 뜻하지 않는다고 명확히 했다.
