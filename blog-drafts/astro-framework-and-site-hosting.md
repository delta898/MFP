# Astro란 무엇이고, BlogGenius 사이트에 왜 사용될까요?

웹사이트를 직접 만들거나 운영하다 보면 `Astro`라는 이름을 만나게 됩니다. BlogGenius의 사이트 만들기도 Astro를 사용합니다. Astro가 무엇인지, 어떤 사이트에 잘 맞는지, 다른 도구와는 어떻게 다른지 알아보겠습니다.

## Astro는 웹사이트를 만드는 도구입니다

Astro는 웹사이트의 페이지와 디자인, 콘텐츠를 작성하고 이를 웹 브라우저가 읽을 수 있는 결과물로 만들어 주는 웹 프레임워크입니다. 페이지 경로와 레이아웃을 구성하고, 재사용할 화면 요소를 만들며, Markdown 같은 콘텐츠를 웹페이지로 변환할 수 있습니다.

Astro는 웹사이트를 인터넷에 올려 주는 호스팅 서비스나 콘텐츠를 직접 관리하는 블로그 서비스와는 다릅니다. Astro는 사이트를 **만드는 도구**이고, Cloudflare는 만들어진 사이트를 **배포하고 방문자에게 전달하는 서비스**입니다. 쉽게 말하면 Astro가 웹사이트 파일을 만들고 Cloudflare가 그 파일을 인터넷에서 열 수 있게 제공합니다.

## BlogGenius에서는 Astro를 어떻게 사용하나요?

BlogGenius의 사이트 템플릿은 Astro 프로젝트로 구성되어 있습니다. 템플릿의 페이지와 콘텐츠를 준비한 다음 빌드하면 HTML, CSS, 이미지와 같은 정적 파일이 `dist` 폴더에 만들어집니다. BlogGenius는 이 결과물을 Cloudflare Static Assets에 배포합니다.

현재 기본 홈페이지 템플릿은 정적 사이트 출력 방식으로 설정되어 있습니다. 따라서 방문자가 페이지를 열 때마다 서버가 페이지를 새로 조립하는 대신, 미리 만들어 둔 파일을 전달하는 방식으로 동작합니다.

작업 흐름은 다음과 같습니다.

1. Astro 템플릿과 사이트 콘텐츠를 준비합니다.
2. 빌드 과정에서 페이지 파일을 생성합니다.
3. 만들어진 파일을 Cloudflare에 배포합니다.
4. 방문자는 Cloudflare가 제공하는 사이트 주소나 연결한 도메인으로 사이트를 방문합니다.

이 과정에서 Cloudflare 계정 연결, 기본 사이트 주소, 사용자 도메인 연결은 각각 별도의 역할을 합니다. Astro는 사이트 내용을 만들고, Cloudflare 배포 설정은 그 결과물을 어디에 공개할지 결정합니다.

## 정적 사이트 생성(SSG)이란?

SSG는 *Static Site Generation*, 즉 정적 사이트 생성의 약자입니다. 사이트를 배포하기 전에 페이지를 미리 HTML 파일로 만들어 놓는 방식입니다.

예를 들어 블로그 글 한 편을 작성하면 빌드 과정에서 그 글을 보여 주는 HTML 페이지가 만들어집니다. 누군가 글을 읽으러 올 때마다 데이터베이스에서 글을 가져와 페이지를 새로 만들 필요가 줄어듭니다. 완성된 파일을 CDN에서 전달할 수 있어 빠르고 운영 구조도 단순해집니다.

대신 콘텐츠를 바꾼 뒤에는 보통 다시 빌드하고 배포해야 변경 사항이 공개됩니다. 방문 시점마다 가격이나 재고, 로그인 사용자 정보처럼 달라지는 값을 보여줘야 한다면 추가 기능이나 서버 렌더링이 필요할 수 있습니다.

Astro는 정적 생성에 특히 잘 맞지만, 필요한 경우 서버에서 요청마다 페이지를 만드는 SSR(Server-Side Rendering)도 지원합니다. 다만 SSR을 사용하려면 Cloudflare Workers 같은 실행 환경과 어댑터 설정이 필요합니다. 현재 BlogGenius 기본 홈페이지 템플릿은 이런 서버 렌더링 대신 정적 출력을 사용합니다.

## Astro의 장점

### 1. 기본 페이지가 가볍고 빠릅니다

Astro는 기본적으로 페이지를 HTML과 CSS 중심으로 만들고, 필요하지 않은 브라우저용 JavaScript를 자동으로 보내지 않습니다. 상호작용이 필요한 부분에만 JavaScript를 추가할 수 있습니다. 페이지에 보여 줄 내용이 중심인 사이트에서 불필요하게 큰 스크립트를 줄이는 데 도움이 됩니다.

예를 들어 회사 소개 페이지의 글과 이미지는 정적인 HTML로 두고, 꼭 필요한 이미지 슬라이더만 별도의 JavaScript 컴포넌트로 작동하게 만들 수 있습니다. Astro 공식 문서에서는 이런 방식을 **아일랜드 아키텍처(Islands Architecture)**라고 설명합니다.

### 2. 검색 엔진이 읽기 좋은 결과를 만들 수 있습니다

페이지 내용이 빌드 시점에 HTML로 만들어지므로 브라우저나 검색 엔진이 처음부터 본문을 확인하기 쉽습니다. 검색 노출은 콘텐츠 품질, 제목과 설명, 링크 구조, 사이트 속도 등 여러 요소에 좌우되므로 Astro를 쓴다는 이유만으로 검색 순위가 보장되지는 않습니다. 다만 콘텐츠 중심 페이지를 명확한 HTML로 제공하기에 좋은 기반입니다.

### 3. 콘텐츠와 페이지를 함께 관리하기 편합니다

Astro는 Markdown, MDX, JSON, YAML 등 여러 콘텐츠 형식과 콘텐츠 컬렉션 기능을 지원합니다. 블로그 글, 상품 정보, 문서처럼 비슷한 구조의 자료를 모아 관리하고, 필수 항목을 검증하거나 목록과 상세 페이지를 자동으로 만들 수 있습니다.

### 4. 익숙한 UI 도구를 필요한 만큼 사용할 수 있습니다

사이트 전체를 하나의 JavaScript 앱으로 만들지 않고, 상호작용이 필요한 일부에 React, Vue, Svelte 같은 UI 프레임워크를 붙일 수 있습니다. 이미 있는 화면 요소를 활용하거나 복잡한 위젯을 필요한 부분에만 적용하기 좋습니다.

### 5. 정적 호스팅과 잘 맞습니다

정적 파일을 CDN에서 제공하면 페이지 요청 때마다 애플리케이션 서버가 실행될 필요가 없습니다. 단순한 회사 사이트나 블로그처럼 요청마다 달라질 내용이 많지 않은 사이트는 배포와 제공 구조를 단순하게 유지할 수 있습니다.

## Astro는 어디에 잘 어울릴까요?

Astro는 페이지마다 내용과 디자인이 있고, 방문자별로 달라지는 정보는 많지 않은 사이트에 특히 잘 맞습니다.

- 회사·제품 소개 페이지와 랜딩 페이지
- 개인 포트폴리오와 프로젝트 소개
- 블로그, 매거진, 뉴스레터 아카이브
- 도움말, 매뉴얼, 기술 문서
- 제품 카탈로그와 콘텐츠 모음
- 정적 사이트 생성 방식으로 운영하려는 지식 정리 사이트

반대로 로그인한 사용자별 대시보드, 실시간 협업 도구, 복잡한 업무 앱처럼 화면 대부분이 사용자 동작과 서버 데이터에 따라 즉시 바뀌는 서비스라면 서버 기능이나 별도의 프런트엔드 앱이 더 중요해질 수 있습니다. Astro로도 서버 렌더링과 동적 기능을 구성할 수 있지만, 그런 요구가 중심이라면 처음부터 해당 기능을 주력으로 하는 프레임워크와 비교해 보는 편이 좋습니다.

## 다른 웹 프레임워크와는 무엇이 다를까요?

| 도구 | 잘 맞는 경우 | Astro와 비교할 때 생각할 점 |
| --- | --- | --- |
| **Astro** | 콘텐츠 중심 웹사이트, 정적 사이트, 필요한 곳에만 상호작용 추가 | HTML을 기본으로 두고 브라우저 JavaScript를 선택적으로 추가하는 접근이 특징입니다. |
| **Next.js** | React 기반 웹 앱, 서버 기능과 정적 페이지를 함께 구성하는 제품 | 풀스택 React 앱에 강점이 있습니다. 사용자별 데이터나 앱 동작이 중심이면 적합할 수 있고, 단순 콘텐츠 사이트에는 필요한 기능이 더 많게 느껴질 수 있습니다. |
| **Eleventy (11ty)** | 템플릿과 Markdown 중심의 단순하고 유연한 정적 사이트 | 여러 템플릿 언어를 선택할 수 있고 구조가 간결합니다. Astro처럼 UI 프레임워크 컴포넌트를 아일랜드 방식으로 통합하는 흐름과는 초점이 다릅니다. |
| **Hugo** | 콘텐츠가 많고 빌드 속도가 중요한 정적 사이트 | Go 기반 정적 사이트 생성기로 빠른 콘텐츠 사이트를 만들 수 있습니다. Go 템플릿과 Hugo 생태계를 사용하는 방식에 익숙해져야 합니다. |
| **SvelteKit** | Svelte 기반 앱과 사이트, 서버 렌더링과 정적 출력을 함께 고려하는 경우 | 앱과 상호작용을 중심으로 구성하기 좋습니다. 정적 콘텐츠 위주 사이트에서는 Astro의 HTML 우선 방식이 더 간결할 수 있습니다. |

이 비교는 어느 도구가 항상 더 낫다는 뜻은 아닙니다. 사이트가 주로 **읽히는 콘텐츠**인지, 아니면 사용자가 로그인해 계속 **조작하는 애플리케이션**인지가 중요한 선택 기준입니다. 또한 각 프레임워크는 빌드 방식과 배포 환경을 다양하게 지원하므로, 특정 도구를 정적 사이트나 동적 앱 하나로만 한정할 수는 없습니다.

## Astro를 선택할 때 알아둘 점

- 콘텐츠를 바꾼 뒤 즉시 공개하려면 보통 새 빌드와 배포가 필요합니다.
- 요청마다 바뀌는 정보는 정적 파일만으로 처리하기 어렵습니다. API나 서버 렌더링, 브라우저 측 데이터 요청이 필요할 수 있습니다.
- JavaScript를 전혀 쓸 수 없는 것은 아닙니다. 다만 상호작용을 직접 추가할수록 그 부분의 코드와 동작도 관리해야 합니다.
- 빌드 결과가 정상인지 확인하는 과정이 중요합니다. 잘못된 경로나 콘텐츠 데이터는 빌드 오류 또는 잘못된 페이지로 이어질 수 있습니다.
- 정적 사이트의 보안과 비용이 자동으로 해결되는 것은 아닙니다. 외부 API, 폼 처리, 인증, 데이터 저장 등은 별도로 설계해야 합니다.

## 요약

Astro는 콘텐츠가 중심인 웹사이트를 빠르고 가볍게 만들도록 설계된 웹 프레임워크입니다. 페이지를 미리 HTML 파일로 생성하고, 상호작용이 필요한 부분에만 브라우저 JavaScript를 추가할 수 있습니다. 블로그, 소개 페이지, 문서, 포트폴리오처럼 방문자에게 주로 콘텐츠를 보여 주는 사이트에 잘 어울립니다.

BlogGenius에서는 Astro 템플릿을 빌드해 정적 파일을 만들고, 그 결과물을 Cloudflare에 배포합니다. 그래서 Astro와 Cloudflare는 서로 대체하는 도구가 아니라, **사이트를 만드는 단계**와 **사이트를 인터넷에 제공하는 단계**를 각각 담당합니다.
